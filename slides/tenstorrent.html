Design Philosophy: A Grid, Not a Hierarchy

Tenstorrent is a throughput AI accelerator built from a homogeneous grid of Tensix cores on a 2-D Network-on-Chip (NoC). Work is expressed on 32×32 tiles, not scalars.

  • No cache hierarchy — a deliberate choice. There is no L2/L3, no coherence protocol.
  • Instead: large distributed SRAM, directly addressable across the chip — any component can read any core's SRAM over the NoC.
  • Data movement is explicit and programmer-controlled, never implicit caching.
Why drop caches?Caches spend area and power guessing reuse. For dense tensor work the reuse pattern is known, so the programmer schedules it directly.
Grid of Tensix cores + NoC, backed by device DRAM, with Ethernet links at the edges.

No Cache: Distributed SRAM over the NoC

The tradeA CPU/GPU hides the memory hierarchy behind caches and coherence. Tenstorrent exposes a flat sea of SRAM over the NoC — more programmer work, but full control and no coherence overhead.

Inside One Tensix Core

  • 5 "baby" RISC-V cores: RV 0 = data-in / reader, RV 4 = data-out / writer, RV 1–3 drive the compute engine
  • Compute engine, 3 units: FPU = matrix engine (32×32 tile matmul), SFPU = vector engine, ThCon = scalar / packer-unpacker
  • 2 NoC routers — two independent NoCs for L1 ↔ DRAM ↔ neighbor traffic
  • ~1–1.5 MB local SRAM (L1) — no per-core cache
Division of laborThree kernel roles (reader / compute / writer) map onto distinct RISC-V cores running concurrently.

The Grid & the 2-D Torus NoC

A device is a 2-D grid of elements — e.g. roughly 10×12 on Wormhole, of which ~80 are designated Tensix compute cores (the rest are DRAM, Ethernet, and PCIe tiles).

  • A 2-D torus NoC wraps edges so traffic has no dead ends
  • It moves tiles between cores and between cores and DRAM
  • Every core can reach any SRAM on the chip — the basis for Lab 2's multi-core split and reuse patterns
Two NoCsThe two routers per core form two independent NoCs, so reads and writes can use separate networks and run in opposite directions.
Cores wired by a torus NoC; red dashed = wrap-around edges.

Ethernet Scale-Out & Galaxy

Starting with Wormhole, each chip carries 16 × 100 Gb Ethernet ports. Chips link directly into large 2-D meshes — the on-chip NoC effectively extends across chips.

  • A core on one chip can stream tiles to a core on another over Ethernet
  • Many chips combine into "Galaxy" systems for very large models
  • Philosophy: scale OUT with commodity links, not a single giant die
One programming model, many scalesThe same tile + NoC abstraction spans a single core, a full chip, and a multi-chip Galaxy.

Flexible AI Data Formats

The engines support a wide range of precisions so models trade accuracy for throughput and SRAM footprint:

Tiles & Matmul as Tile Accumulation

Tensix hardware operates on 32×32 tiles. A matrix is reshaped into a grid of tiles:

\( M_t = M/32,\quad K_t = K/32,\quad N_t = N/32 \)

Each output C-tile is a sum of tile-products along K:

\( C_{mt,nt} = \sum_{kt=0}^{K_t-1} A_{mt,kt}\, B_{kt,nt} \)
  • A tile (bf16) = \( 2 \times 32 \times 32 = 2048\) bytes; tiles stored row-major
  • A index = mt*Kt + kt; B index = kt*Nt + nt
Inner loop over kt accumulates into one register tile.

Module 1 — Review

1. Why does Tenstorrent have no cache hierarchy, and what replaces it?

For dense tensor work the reuse pattern is known, so caches waste area/power and add coherence overhead. Instead the chip exposes large distributed L1 SRAM that any core can address over the NoC, with data movement scheduled explicitly by the program.

2. What are the five RISC-V cores and the three compute units in a Tensix core?

RV 0 = reader, RV 4 = writer, RV 1–3 drive compute. The compute engine has the FPU (32×32 matrix), SFPU (vector), and ThCon (scalar / pack-unpack), plus ~1–1.5 MB L1 and two NoC routers.

3. What did Wormhole and Blackhole each add over Grayskull?

Wormhole added 16 × 100 GbE ports for chip-to-chip scale-out (meshes / Galaxy). Blackhole moved to 6 nm and added 16 "big" RISC-V cores so the device manages more of its own data movement, cutting host round-trips.

The Layered Stack

Higher layers are more automated; lower layers give more control.

  • TT-Forge / TT-MLIR — compile whole models, no kernels written
  • TT-NN — call optimized ops from Python
  • TT-Metalium — write kernels by hand labs
  • Hardware — the Tensix grid
All open sourceThe entire stack is open and RISC-V-based — you can read every layer down to the kernels.

Layer: TT-Metalium

The low-level, open-source C++ SDK — bare-metal direct access to the hardware. This is what the labs use.

  • Direct control of RISC-V cores, the NoC, and the matrix / vector engines
  • Explicit memory & data movement — you place buffers and circular buffers yourself
  • You write reader / compute / writer kernels plus a host program
  • TT-LLK — a low-level kernel library of compute primitives sits just beneath it
AnalogyTT-Metalium is to Tenstorrent roughly what writing CUDA kernels (or even PTX) is to a GPU — but with the data movement fully exposed.
Why teach at this levelDropping to Metalium forces you to confront tiles, circular buffers, the NoC, and core placement directly — the whole point of the labs.

Layer: TT-NN

A Python + C++ operator library of pre-packaged, optimized ops, built on top of Metalium.

  • PyTorch-like API — tensors, ops, and modules feel familiar
  • Run models without writing kernels — the optimized kernels already exist underneath
  • Each op ultimately calls hand-tuned Metalium / TT-LLK code
Where most users liveIf you just want to run a model fast, TT-NN (or TT-Forge above it) is the normal entry point — not raw Metalium.

Layer: TT-Forge / TT-MLIR Compiler

An MLIR-based compiler that ingests models from PyTorch, JAX, and TensorFlow and lowers them automatically — no custom kernels needed.

  • Dialects: TTIR → TTNN / TTKernel
  • Optimization passes: operator fusion, sharding across cores, and layout (tiling) selection
  • Finally lowers to TT-Metalium
The automated pathTT-Forge is the general, hands-off route: bring a trained model, get it running on the grid.

Runtime / deployment tools wrap the stack for serving:

  • TT-Inference-Server — OpenAI-compatible model serving
  • TT-Forge Models — validated model catalog
  • TT-Studio — web UI to deploy
  • tt-smi / tt-topology — monitoring & topology
Where the labs sitThe matmul labs are pure TT-Metalium — the lowest level. You control kernels, CBs, the NoC, and cores directly. Most users would instead reach for TT-NN or TT-Forge; the labs deliberately drop to Metalium to teach the hardware.

Module 2 — Review

1. Order the stack from hardware up, and say what each layer does.

Hardware (Tensix grid) → TT-Metalium (bare-metal C++ kernels) → TT-NN (Python op library) → TT-Forge / TT-MLIR (compiles whole PyTorch/JAX/TF models down to Metalium). Runtime tools (TT-Inference-Server, TT-Studio) sit alongside for serving.

2. What dialects and passes does TT-MLIR use?

Dialects TTIR → TTNN / TTKernel, with passes for operator fusion, sharding across cores, and layout/tiling selection, before lowering to TT-Metalium.

3. Why do the labs use raw TT-Metalium instead of TT-NN?

To teach the hardware: at the Metalium level you must manage tiles, circular buffers, the NoC, and core placement by hand. Production users would typically use TT-NN or TT-Forge instead.

Single-Core Matmul

The Problem & the Tiled Idea

Compute C = A · B on one Tensix core:

\( A_{640\times320}\cdot B_{320\times640} = C_{640\times640} \)
  • With 32×32 tiles: Mt=20, Kt=10, Nt=20
  • One core produces all \(M_t\cdot N_t\) output tiles
  • Each output tile accumulates over Kt tile-products
Three kernels, one core
  • reader — streams A & B tiles DRAM → CBs
  • compute — tile matmul + accumulate → output CB
  • writer — output CB → DRAM
Loop tiling = localityTiling turns a giant matmul into many small ones that fit in fast L1 — the same idea as blocking for cache.

Circular Buffers & the Reader → Compute → Writer Pipeline

Circular buffer (CB)A FIFO queue in L1 connecting a producer and consumer kernel. Sized 2 * tile_size for double-buffering.
  • reader: DRAM → CB (cb_reserve_back → push)
  • compute: CB → engine → CB (wait_front / pop)
  • writer: CB → DRAM

CB indices by convention: cb_src0=0, cb_src1=1, cb_output=16.

Host API Lifecycle — Device & Buffers

TT-Metalium host (C++)

// 1. Open a device and get its command queue
auto mesh_device = MeshDevice::create_unit_mesh(device_id);
auto& cq = mesh_device->mesh_command_queue();

// 2. Tile dimensions
uint32_t Mt = M / TILE, Kt = K / TILE, Nt = N / TILE;
uint32_t tile_size = sizeof(bfloat16) * TILE * TILE;   // 32x32

// 3. DRAM buffers for src0, src1, dst
DeviceLocalBufferConfig dram_cfg{.page_size = tile_size,
                                 .buffer_type = BufferType::DRAM};
auto src0 = MeshBuffer::create(dram_cfg, /*...*/, mesh_device.get());
auto src1 = MeshBuffer::create(dram_cfg, /*...*/, mesh_device.get());
auto dst  = MeshBuffer::create(dram_cfg, /*...*/, mesh_device.get());

create_unit_mesh gives a single-device mesh; the command queue serializes host→device work.

Host API Lifecycle — Args, Launch & Read-Back

Lifecycle in one line open device → place DRAM buffers → build a Program (CBs + kernels + args) → enqueue write / workload / read.

Compute Kernel — Tile Matmul

mm.cpp — compute kernel (C++)

mm_init(cb_in0, cb_in1, cb_out);

for (uint32_t mt = 0; mt < Mt; mt++) {
  for (uint32_t nt = 0; nt < Nt; nt++) {
    tile_regs_acquire();                 // own the dst register tile
    for (uint32_t kt = 0; kt < Kt; kt++) {
      cb_wait_front(cb_in0, 1);          // A tile ready
      cb_wait_front(cb_in1, 1);          // B tile ready
      matmul_tiles(cb_in0, cb_in1, 0, 0, 0);  // C += A_kt * B_kt
      cb_pop_front(cb_in0, 1);
      cb_pop_front(cb_in1, 1);
    }
    tile_regs_commit();                  // hand dst to packer
    tile_regs_wait();
    pack_tile(0, cb_out);                // dst tile -> output CB
    cb_push_back(cb_out, 1);
    tile_regs_release();
  }
}

The inner kt loop accumulates into a single register tile before packing it out.

reader.cpp (C++)

// A tile id = mt*Kt + kt

Lab 1 — Review

1. Why split the work into reader / compute / writer kernels?

They map onto distinct RISC-V cores and run concurrently through circular buffers, overlapping DRAM movement with compute.

2. What tile indices feed one output tile (mt,nt)?

A tiles mt*Kt+kt and B tiles kt*Nt+nt for kt = 0…Kt-1, accumulated by matmul_tiles.

3. How do we validate correctness with bf16 inputs?

Untilize and compare to a CPU bf16 golden matmul using Pearson correlation, requiring > 0.97 rather than exact equality.
Lab 2
Multi-Core Matmul (SPMD)

By the end you can…

  • Explain SPMD static work assignment and how it differs from GPU dynamic scheduling
  • Use split_work_to_cores() to partition output tiles across a grid (incl. uneven splits)
  • Pass per-core tile ranges through SetRuntimeArgs over core ranges

SPMD: Static Work Assignment

The single core's output tiles are now partitioned across many cores. Each core runs the same kernels on its own slice of output tiles.

No dynamic schedulingUnlike a GPU's block scheduler, each core gets a fixed set of tiles at launch. A core that finishes early simply idles until the next launch — there is no oversubscription or work-stealing.
Each core owns a fixed range of output tiles.

split_work_to_cores() & Uneven Splits

split_work_to_cores() distributes the \(M_t\cdot N_t\) output tiles across the available cores, returning:

  • The number of cores to use
  • Two core groups (primary / secondary) for uneven splits
  • The work-per-core for each group
Example81 output tiles across 11 cores → 8 cores × 10 tiles + 1 core × 1 tile. The two groups absorb the remainder.
host (C++)

auto [num_cores,
      all_cores,
      core_group_1,   // primary
      core_group_2,   // remainder
      work_per_core_1,
      work_per_core_2] =
    split_work_to_cores(grid, Mt * Nt);

Two groups so an uneven split needs no per-core branching at runtime.

Per-Core Runtime Args Over Core Ranges

host (C++)

uint32_t work_offset = 0;
for (auto& [group, work_per_core] : {std::pair{core_group_1, work_per_core_1},
                                     std::pair{core_group_2, work_per_core_2}}) {
  for (const CoreCoord& core : corerange_to_cores(group)) {
    SetRuntimeArgs(program, reader,  core,
        {src0->address(), src1->address(), Mt, Kt, Nt, work_offset, work_per_core});
    SetRuntimeArgs(program, compute, core, {work_per_core});
    SetRuntimeArgs(program, writer,  core,
        {dst->address(), work_per_core, work_offset});
    work_offset += work_per_core;        // next core's start tile
  }
}
What the kernels receive Each kernel takes a tile range: a start tile id (work_offset) and a count (work_per_core). The reader uses modulo arithmetic on the start id to recover row/col; the compute outer loop is bounded by the count (inner kt loop unchanged); the writer offsets its DRAM writes.

Lab 2 — Review

1. How does Tenstorrent SPMD scheduling differ from a GPU's?

Work is assigned statically at launch — each core gets a fixed tile range with no dynamic scheduling, oversubscription, or work-stealing. An early-finishing core just idles.

2. Why does split_work_to_cores() return two core groups?

To handle uneven splits: most cores do work_per_core_1 tiles, a remainder group does work_per_core_2, so no per-core conditionals are needed at runtime.

3. What changes in the kernels vs. Lab 1?

Each kernel takes a tile range (offset + count). The reader derives row/col by modulo, the compute outer loop is bounded by the count, and the writer offsets its output tile ids. The inner kt accumulation is unchanged.
