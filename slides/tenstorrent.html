Other GPUs and AI Chips

AMD · Intel · Cerebras · Tenstorrent — the post-Moore accelerator landscape
This topic steps outside the NVIDIA GPU we studied and surveys four other data-center accelerators: AMD's CDNA data-center GPUs (Instinct MI300), Intel's Xe-HPC GPUs and Gaudi AI chips, Cerebras's wafer-scale engine, and Tenstorrent's Tensix dataflow grid. The unifying question is the same one the course keeps asking: how do you keep many compute engines fed with data? Each vendor answers with a different memory model, programming model, and scale-out strategy.

The takeaway Every accelerator here is a throughput machine bounded by data movement. What differs is where the memory hierarchy and the scheduler live — in hardware, in the runtime, or handed to the programmer — and how many chips stitch together to run one model.

Why a Diverse Accelerator Landscape?

Dennard scaling ended and Moore's Law slowed, so a single general-purpose design no longer wins on its own. The answer has been domain-specific accelerators — and a burst of competing designs for the same job (training and serving large models).

  • NVIDIA defined the template: many SIMT cores + tensor cores + HBM + NVLink, programmed in CUDA.
  • But CUDA is closed, supply is constrained, and cost is high — pulling hyperscalers and HPC labs toward alternatives.
  • Each challenger bets on a different design point: an APU with unified memory, a whole-wafer chip, a dataflow grid, an Ethernet-native AI ASIC.
Same physics, different betsAll of them face the memory wall. They just place the walls in different places.
Different architectures, one shared constraint.

Three Axes for Comparing Any Accelerator

We keep coming back to the same three questions. Hold them in mind for every chip in this topic.

Programming modelHow do you express work? SIMT threads (CUDA / HIP / SYCL), a graph compiler, or hand-scheduled kernels? Open or proprietary?
Memory modelCache hierarchy vs. scratchpad SRAM; discrete device memory vs. unified CPU+GPU memory vs. on-wafer SRAM only. Coherent or not?
Scale-outHow do many chips act as one? NVLink/Infinity Fabric, standard Ethernet, an on-chip NoC extended across chips, or a single wafer that needs almost no scale-out.
Reference point: NVIDIA SIMT + tensor cores in CUDA; L1/L2 cache + shared memory over HBM; scale-out over NVLink / NVSwitch. Read each of the following as a deliberate variation on that baseline.

CDNA & the Instinct MI300X

AMD splits its GPU line in two: RDNA for graphics, CDNA for the data center (compute only — no raster hardware). MI300X (CDNA 3, 2023) is the flagship training/inference GPU.

  • 304 compute units with 1,216 Matrix Cores — AMD's tensor-core equivalent (the CUs are grouped into XCD accelerator chiplets)
  • 192 GB HBM3 at ~5.3 TB/s — much more capacity than a same-era NVIDIA H100 (80 GB)
  • Chiplet package: ~150 B transistors across TSMC 5 nm + 6 nm dies on a base die
  • Infinity Fabric links 8 GPUs (~128 GB/s each) — AMD's answer to NVLink
Matrix CoresDedicated matmul units per CU, supporting FP16 / BF16 / FP8 / INT8 — direct analog to NVIDIA tensor cores.
Compute chiplets over a base die, ringed by HBM3.

MI300A: A Data-Center APU

The MI300A swaps two GPU chiplets for CPU chiplets: 24 "Zen 4" x86 cores + CDNA 3 GPU CUs in one package, sharing 128 GB of unified HBM3.

  • One coherent address space for CPU and GPU — no cudaMemcpy across a PCIe bus, no separate host/device copies
  • CPU and GPU see the same physical memory, cache-coherent over Infinity Fabric
  • Powers El Capitan (LLNL) — an exascale, #1-class supercomputer
Why it matters hereThis is the opposite memory bet from Tenstorrent/Cerebras: instead of removing sharing, AMD extends the coherent shared-memory model of this course to span CPU and GPU on one die.
CPU + GPU chiplets sharing coherent HBM.

Software: ROCm & HIP

ROCm is AMD's open GPU-compute stack; HIP is its programming language — deliberately a near clone of CUDA.

  • hipMalloc, hipMemcpy, <<<grid,block>>> launches — the CUDA mental model transfers directly
  • HIPIFY mechanically translates CUDA source to HIP
  • Libraries mirror NVIDIA's: rocBLAS / hipBLAS, MIOpen (vs. cuDNN), RCCL (vs. NCCL)
  • PyTorch and TensorFlow run on ROCm as an alternate backend
HIP kernel (C++) — compare to CUDA

__global__ void saxpy(int n, float a,
                       const float* x, float* y) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (i < n) y[i] = a * x[i] + y[i];
}
// host launch
hipMalloc(&d_x, n * sizeof(float));
saxpy<<<blocks, threads>>>(n, 2.0f, d_x, d_y);
StrategyMeet CUDA users where they are: same API shape, open source, so porting cost is low.

Module 1 — Review

1. What is CDNA, and what are Matrix Cores?

CDNA is AMD's compute-only data-center GPU architecture (separate from RDNA graphics). Matrix Cores are its per-CU matrix-multiply units — the analog of NVIDIA tensor cores — supporting FP16/BF16/FP8/INT8.

2. How does the MI300A differ from the MI300X?

The MI300A is an APU: it replaces two GPU chiplets with 24 Zen 4 x86 CPU cores and shares one coherent 128 GB HBM3 pool between CPU and GPU. The MI300X is GPU-only with 192 GB HBM3. The APU removes host/device copies via unified memory.

3. Why is HIP designed to look like CUDA?

To minimize porting cost: HIP mirrors CUDA's API and launch syntax, and HIPIFY auto-translates CUDA source, so the huge base of CUDA code and developer knowledge carries over to an open (ROCm) stack.

Xe-HPC: "Ponte Vecchio" / Data Center GPU Max

Intel's HPC GPU (Max 1550) is an extreme chiplet exercise: 47 tiles across 5 process nodes, bonded with EMIB + Foveros 3-D packaging.

  • 128 Xe-cores, each with XMX (Xe Matrix Extensions) engines — 1,024 XMX total, plus vector engines
  • 128 GB HBM2e (~3.3 TB/s) and a large ~408 MB L2 ("Rambo") cache
  • 16 Xe Link ports for GPU-to-GPU scale-out; 600 W OAM
  • Deployed in Aurora (Argonne): 63,744 GPUs, > 2 exaflops
Roadmap note (2025)Intel has since refocused its data-center accelerator roadmap, but Ponte Vecchio remains a landmark chiplet GPU and powers Aurora.
A GPU built as dozens of bonded chiplets.

Gaudi 3: An Ethernet-Native AI ASIC

Separately from its GPUs, Intel ships the Gaudi line (from its Habana acquisition) — a purpose-built training/inference ASIC, not a graphics-derived GPU. Gaudi 3 (2024):

  • 64 TPCs (Tensor Processor Cores, VLIW SIMD) + 8 MMEs — each MME a large 256×256 MAC matrix engine
  • 128 GB HBM2e (~3.7 TB/s), 96 MB on-die SRAM
  • 24 × 200 GbE RoCE ports on the chip — scale-out over standard Ethernet, no proprietary switch
Two engine typesMMEs do the dense matmuls; TPCs handle the flexible/vector ops around them — a deliberate split of labor.
Matrix engines + vector cores + integrated Ethernet.

Software: oneAPI & SYCL

oneAPI is Intel's open, cross-vendor stack; SYCL (with Intel's DPC++ compiler) is its language — single-source, standard C++, not a CUDA dialect.

  • Host and device code live in one C++ file; kernels are lambdas submitted to a queue
  • Targets Intel GPUs, CPUs, FPGAs — and, in principle, other vendors' hardware
  • Libraries: oneMKL, oneDNN, oneCCL
  • SYCLomatic migrates CUDA → SYCL

Gaudi uses a separate path: the Intel Gaudi software suite, natively integrated with PyTorch — not the oneAPI GPU path.

SYCL (single-source C++)

sycl::queue q;
q.submit([&](sycl::handler& h) {
  h.parallel_for(sycl::range<1>(n),
    [=](sycl::id<1> i) {
      y[i] = a * x[i] + y[i];   // SAXPY
  });
});
q.wait();
Different philosophyWhere HIP copies CUDA, SYCL is a vendor-neutral standard — one source, many backends.

Module 2 — Review

1. What is unusual about how Ponte Vecchio is built, and what are XMX engines?

It is an extreme chiplet design — 47 tiles across 5 process nodes, 3-D bonded with EMIB + Foveros. XMX (Xe Matrix Extensions) are the per-Xe-core matrix-multiply engines, Intel's tensor-core analog.

2. How does Gaudi 3 differ from a GPU, and how does it scale out?

Gaudi is a purpose-built AI ASIC (not graphics-derived): dedicated MME matrix engines plus TPC vector cores. It scales out over standard Ethernet using 24×200 GbE RoCE ports integrated on-die — no proprietary interconnect switch.

3. How does SYCL's programming model differ from HIP's?

SYCL is single-source standard C++ (kernels as lambdas on a queue) and is a vendor-neutral standard targeting many backends. HIP is a near-copy of CUDA's API. SYCL aims for portability; HIP aims for easy CUDA porting.

Cerebras — Wafer-Scale Engine

By the end you can…

  • Describe its scale: ~900,000 cores, 44 GB on-wafer SRAM, no external DRAM in the compute path
  • Explain weight streaming (MemoryX / SwarmX) and why it sidesteps the memory bottleneck

The Wafer-Scale Engine (WSE-3)

Instead of dicing a wafer into hundreds of chips, Cerebras keeps one whole wafer as a single processor — the largest chip ever built.

  • ~46,225 mm², 4 trillion transistors (TSMC 5 nm), 2024
  • ~900,000 small AI cores in a 2-D mesh
  • 44 GB of SRAM on the wafer — 48 KB private to each core, one cycle away; ~21 PB/s aggregate
  • No caches, no HBM in the compute loop — every core computes out of its adjacent SRAM
Yield trickSome cores are always defective on a full wafer; redundant cores + a reconfigurable mesh route around the bad ones.
The whole wafer is one processor, not hundreds of dies.

Weight Streaming vs. a GPU Cluster

A large model won't fit in 44 GB of SRAM, so Cerebras decouples memory from compute:

  • MemoryX — an external box holding all the weights
  • SwarmX — a fabric that streams weights layer-by-layer onto the wafer and reduces gradients on the way back
  • The wafer holds only activations; weights flow through it
The payoffBecause one wafer holds a whole layer, you avoid splitting a model across many chips — no tensor/pipeline parallelism and no slow inter-GPU network in the inner loop.

Module 3 — Review

1. What is a wafer-scale engine, and where does its memory live?

It keeps an entire ~300 mm wafer as one chip (WSE-3: ~900k cores, 4 T transistors). All working memory is on-wafer SRAM — 44 GB total, 48 KB private to each core, one cycle away — with no caches and no HBM in the compute path.

2. What problem does weight streaming (MemoryX / SwarmX) solve?

Model weights are far larger than 44 GB of SRAM. MemoryX stores the weights off-wafer and SwarmX streams them layer-by-layer onto the wafer (and reduces gradients back), so the wafer holds only activations and never has to fit the whole model.

3. Why does the wafer avoid the parallelism a GPU cluster needs?

A full layer fits on one wafer connected by a fast on-wafer mesh, so there is no need to split a layer across chips (tensor/pipeline parallelism) or move data over a slow inter-GPU network in the inner loop — weight-stream bandwidth becomes the main limit instead.

A Dataflow Grid, Not a Hierarchy

Control-flow (von Neumann)A program counter walks instructions in order; data is fetched on demand. This is what a CPU — and a GPU's SIMT lanes — do.
DataflowComputation is driven by the availability of data: the program is a graph of ops, each fires when its operands arrive, and data flows tile-to-tile across the fabric.

Tenstorrent is a homogeneous grid of Tensix cores on a 2-D Network-on-Chip. Work is expressed on 32×32 tiles.

  • No cache hierarchy — no L2/L3, no coherence protocol
  • Instead: large distributed L1 SRAM, directly addressable across the chip — any core can read any core's SRAM over the NoC
  • Data movement is explicit and programmer-scheduled, never implicit caching
Why drop caches?Caches spend area/power guessing reuse. For dense tensor work the reuse is known, so the program schedules it directly.
No caches; a flat sea of directly-addressable SRAM.

Inside One Tensix Core

  • 5 "baby" RISC-V cores: RV 0 = reader, RV 4 = writer, RV 1–3 drive the compute engine
  • Compute engine, 3 units: FPU = 32×32 matrix, SFPU = vector, ThCon = scalar / pack-unpack
  • 2 NoC routers — two independent NoCs for L1 ↔ DRAM ↔ neighbor traffic
  • ~1–1.5 MB local SRAM (L1) — no per-core cache
Division of laborThree kernel roles (reader / compute / writer) map onto distinct RISC-V cores running concurrently — dataflow in miniature.

Module 4 — Review

1. What makes Tenstorrent a dataflow architecture, and what replaces the cache?

Kernels fire when their input tiles arrive and stream results onward (reader→compute→writer), rather than a program counter driving a thread. There is no cache hierarchy — instead a large distributed L1 SRAM that any core can address over the NoC, with data movement scheduled explicitly.

2. What are the five RISC-V cores and three compute units in a Tensix core?

RV 0 = reader, RV 4 = writer, RV 1–3 drive compute. The compute engine has the FPU (32×32 matrix), SFPU (vector), and ThCon (scalar / pack-unpack), plus ~1–1.5 MB L1 and two NoC routers.

3. How does Tenstorrent scale out, and how is its software stack positioned?

Starting with Wormhole, chips carry 16×100 GbE ports and link into meshes ("Galaxy") over Ethernet — the NoC extends across chips. The stack (TT-Metalium → TT-NN → TT-Forge/TT-MLIR) is fully open source and RISC-V-based, positioned against closed CUDA.

Topic Summary & Takeaways

The GPU challengersAMD (CDNA / MI300, ROCm-HIP) and Intel (Xe-HPC, Gaudi, oneAPI-SYCL) track the NVIDIA template closely, competing on capacity, openness, and cost.
The clean breaksCerebras puts everything on one wafer of SRAM; Tenstorrent builds a cache-free dataflow grid of RISC-V tile engines. Both discard the classic GPU memory model.
One lensCompare any new chip on programming model, memory model, and scale-out — the three axes hold across all of them.
The connecting theme Every accelerator in this topic is a throughput machine bounded by data movement. The post-Moore landscape is diverse precisely because there are many valid places to put the memory hierarchy and the scheduler — in hardware, in a compiler, or in the programmer's hands. That trade-off, not any one vendor, is the lasting idea.
Tie back to the NVIDIA GPU unit and the shared-memory-multicore core of the course: AMD's APU even pushes coherence across CPU and GPU, while Cerebras and Tenstorrent abandon shared coherent memory altogether. The three comparison axes are the transferable skill — students should be able to slot a brand-new accelerator into that table.
