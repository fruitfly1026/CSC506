Tenstorrent Architecture & the TT-Metalium Model

A Tile-Based Throughput Accelerator

Tenstorrent is a PCIe accelerator with its own DRAM, separate from host memory — like a GPU, but the compute fabric is a grid of programmable Tensix cores connected by a network-on-chip (NoC).

  • Work is expressed on 32×32 tiles, not scalars
  • Each core runs explicit reader / compute / writer programs
  • You program data movement directly — nothing is implicit
TT-MetaliumThe low-level C++ host + kernel API. You place buffers, define circular buffers, and launch kernels on specific cores.
Grid of Tensix cores + NoC, backed by device DRAM.

Inside One Tensix Core

  • L1 SRAM — fast local memory; holds CB tiles + kernel code
  • 2 NoC routers — move data L1 ↔ DRAM ↔ neighbor cores
  • Tensix compute engine — matrix & vector tile math
  • 5 RISC-V "baby" cores:
    • RV 0 & RV 4 drive the routers → reader / writer data-movement kernels
    • RV 1–3 drive the compute engine → compute kernel
Division of laborThree kernel roles per core map onto distinct RISC-V cores running concurrently.

Host ↔ Device Data Flow

Host → DRAM over PCIe → cores pull into L1 → compute → results back.
  1. Host writes inputs to device DRAM over PCIe
  2. Reader kernels pull tiles DRAM → L1 via the NoC
  3. Compute kernel processes L1 → L1 on the Tensix engine
  4. Writer kernels push results L1 → DRAM
  5. Host reads outputs back DRAM → host
Key costDevice DRAM is far; L1 is near. Every lab is about moving fewer, larger tiles and reusing them in L1.

Tiles & the Tiled Layout

Tensix hardware operates on 32×32 tiles, not individual elements. A matrix is reshaped into a grid of tiles:

\( M_t = M/32,\quad K_t = K/32,\quad N_t = N/32 \)
  • Tile size (bf16): \( 2 \times 32 \times 32 = 2048\) bytes
  • Within a tile, elements are contiguous
  • Tiles are stored row-major across the matrix
Why tiles?A tile is the natural unit the engine multiplies, the NoC moves, and a CB buffers.
Each cell is a 32×32 tile; row-major tile ids.

Matmul as Tile Accumulation

Each output C-tile is a sum of tile-products along the K dimension:

\( C_{mt,nt} = \sum_{kt=0}^{K_t-1} A_{mt,kt}\, B_{kt,nt} \)
  • Outer loops over output tiles (mt, nt)
  • Inner loop over kt accumulates into one register tile
  • A index = mt*Kt + kt; B index = kt*Nt + nt

Circular Buffers & the Reader → Compute → Writer Pipeline

Circular buffer (CB)A FIFO queue in L1 connecting a producer and consumer kernel. Sized 2 * tile_size for double-buffering.
  • reader: DRAM → CB (cb_reserve_back → push)
  • compute: CB → engine → CB (wait_front / pop)
  • writer: CB → DRAM

CB indices by convention: cb_src0=0, cb_src1=1, cb_output=16.

Host API Lifecycle — Device & Buffers

TT-Metalium host (C++)

// 1. Open a device and get its command queue
auto mesh_device = MeshDevice::create_unit_mesh(device_id);
auto& cq = mesh_device->mesh_command_queue();

// 2. Tile dimensions
uint32_t Mt = M / TILE, Kt = K / TILE, Nt = N / TILE;
uint32_t tile_size = sizeof(bfloat16) * TILE * TILE;   // 32x32

// 3. DRAM buffers for src0, src1, dst
DeviceLocalBufferConfig dram_cfg{.page_size = tile_size,
                                 .buffer_type = BufferType::DRAM};
auto src0 = MeshBuffer::create(dram_cfg, /*...*/, mesh_device.get());
auto src1 = MeshBuffer::create(dram_cfg, /*...*/, mesh_device.get());
auto dst  = MeshBuffer::create(dram_cfg, /*...*/, mesh_device.get());

create_unit_mesh gives a single-device mesh; the command queue serializes host→device work.

Module 1 — Review

1. What are the five RISC-V cores in a Tensix core for?

RV 0 & RV 4 drive the two NoC routers (reader / writer data-movement kernels); RV 1–3 drive the Tensix compute engine (compute kernel).

2. What is a circular buffer, and why is it sized 2× a tile?

A FIFO queue in L1 linking a producer and consumer kernel. Sizing it for two tiles enables double-buffering so the reader can fill the next tile while the compute engine consumes the current one.

3. Trace the host API lifecycle from device open to result read-back.

create_unit_mesh → command queue → DRAM buffers → Program with CreateCircularBuffer / CreateKernel / SetRuntimeArgs → EnqueueWriteMeshBuffer → EnqueueMeshWorkload → EnqueueReadMeshBuffer.
Lab 1
Single-Core Matmul

By the end you can…

  • Apply loop tiling and reason about the host/device memory model
  • Implement a single-core tiled matmul with reader / compute / writer kernels
  • Debug with DPRINT, stack traces (tt-triage), and the device profiler
  • Optimize data movement through circular buffers and validate vs. a CPU golden result

The Problem & the Tiled Idea

Compute C = A · B on one Tensix core:

\( A_{640\times320}\cdot B_{320\times640} = C_{640\times640} \)
  • With 32×32 tiles: Mt=20, Kt=10, Nt=20
  • One core produces all \(M_t\cdot N_t\) output tiles
  • Each output tile accumulates over Kt tile-products
Three kernels, one core
  • reader — streams A & B tiles DRAM → CBs
  • compute — tile matmul + accumulate → output CB
  • writer — output CB → DRAM
Loop tiling = localityTiling turns a giant matmul into many small ones that fit in fast L1 — the same idea as blocking for cache.

Compute Kernel — Tile Matmul

mm.cpp — compute kernel (C++)

mm_init(cb_in0, cb_in1, cb_out);

for (uint32_t mt = 0; mt < Mt; mt++) {
  for (uint32_t nt = 0; nt < Nt; nt++) {
    tile_regs_acquire();                 // own the dst register tile
    for (uint32_t kt = 0; kt < Kt; kt++) {
      cb_wait_front(cb_in0, 1);          // A tile ready
      cb_wait_front(cb_in1, 1);          // B tile ready
      matmul_tiles(cb_in0, cb_in1, 0, 0, 0);  // C += A_kt * B_kt
      cb_pop_front(cb_in0, 1);
      cb_pop_front(cb_in1, 1);
    }
    tile_regs_commit();                  // hand dst to packer
    tile_regs_wait();
    pack_tile(0, cb_out);                // dst tile -> output CB
    cb_push_back(cb_out, 1);
    tile_regs_release();
  }
}

The inner kt loop accumulates into a single register tile before packing it out.

Reader & Writer — Index Math

reader.cpp (C++)

// A tile id = mt*Kt + kt

Lab 1 — Review

1. Why split the work into reader / compute / writer kernels?

They map onto distinct RISC-V cores and run concurrently through circular buffers, overlapping DRAM movement with compute.

2. What tile indices feed one output tile (mt,nt)?

A tiles mt*Kt+kt and B tiles kt*Nt+nt for kt = 0…Kt-1, accumulated by matmul_tiles.

3. How do we validate correctness with bf16 inputs?

Untilize and compare to a CPU bf16 golden matmul using Pearson correlation, requiring > 0.97 rather than exact equality.
Lab 2
Multi-Core Matmul (SPMD)

By the end you can…

  • Explain SPMD static work assignment and how it differs from GPU dynamic scheduling
  • Use split_work_to_cores() to partition output tiles across a grid (incl. uneven splits)
  • Pass per-core tile ranges through SetRuntimeArgs over core ranges

SPMD: Static Work Assignment

The single core's output tiles are now partitioned across many cores. Each core runs the same kernels on its own slice of output tiles.

No dynamic schedulingUnlike a GPU's block scheduler, each core gets a fixed set of tiles at launch. A core that finishes early simply idles until the next launch — there is no oversubscription or work-stealing.
Each core owns a fixed range of output tiles.

split_work_to_cores() & Uneven Splits

split_work_to_cores() distributes the \(M_t\cdot N_t\) output tiles across the available cores, returning:

  • The number of cores to use
  • Two core groups (primary / secondary) for uneven splits
  • The work-per-core for each group
Example81 output tiles across 11 cores → 8 cores × 10 tiles + 1 core × 1 tile. The two groups absorb the remainder.
host (C++)

auto [num_cores,
      all_cores,
      core_group_1,   // primary
      core_group_2,   // remainder
      work_per_core_1,
      work_per_core_2] =
    split_work_to_cores(grid, Mt * Nt);

Two groups so an uneven split needs no per-core branching at runtime.

Per-Core Runtime Args Over Core Ranges

host (C++)

uint32_t work_offset = 0;
for (auto& [group, work_per_core] : {std::pair{core_group_1, work_per_core_1},
                                     std::pair{core_group_2, work_per_core_2}}) {
  for (const CoreCoord& core : corerange_to_cores(group)) {
    SetRuntimeArgs(program, reader,  core,
        {src0->address(), src1->address(), Mt, Kt, Nt, work_offset, work_per_core});
    SetRuntimeArgs(program, compute, core, {work_per_core});
    SetRuntimeArgs(program, writer,  core,
        {dst->address(), work_per_core, work_offset});
    work_offset += work_per_core;        // next core's start tile
  }
}
What the kernels receive Each kernel takes a tile range: a start tile id (work_offset) and a count (work_per_core). The reader uses modulo arithmetic on the start id to recover row/col; the compute outer loop is bounded by the count (inner kt loop unchanged); the writer offsets its DRAM writes.

Lab 2 — Review

1. How does Tenstorrent SPMD scheduling differ from a GPU's?

Work is assigned statically at launch — each core gets a fixed tile range with no dynamic scheduling, oversubscription, or work-stealing. An early-finishing core just idles.

2. Why does split_work_to_cores() return two core groups?

To handle uneven splits: most cores do work_per_core_1 tiles, a remainder group does work_per_core_2, so no per-core conditionals are needed at runtime.

3. What changes in the kernels vs. Lab 1?

Each kernel takes a tile range (offset + count). The reader derives row/col by modulo, the compute outer loop is bounded by the count, and the writer offsets its output tile ids. The inner kt accumulation is unchanged.
Lab 3
Multi-Core with Multicast

By the end you can…

  • Identify the data-reuse opportunity that motivates multicast
  • Explain how a sender broadcasts an input block over the NoC to many receivers
  • Describe semaphore synchronization and CB sizing for a CoreGrid

From Reuse to Multicast

In Lab 2 many cores compute output tiles in the same row or column — and each one re-reads the same A row block or B column block from DRAM. That's redundant DRAM traffic.

  • Reuse (matmul_multicore_reuse): keep a block resident and reuse it across output tiles
  • Multicast (matmul_multicore_reuse_mcast): one core reads a block once, then broadcasts it over the NoC to many receiver cores
PayoffOne DRAM read feeds a whole row/column of cores → a big cut in DRAM traffic.

Sender / Receiver Kernels & Semaphores

Multicast splits the data-movement kernel into two roles:

  • Sender — reads the block from DRAM once, then issues a multicast NoC write to all receiver cores' L1
  • Receivers — wait for the block to arrive in their CB, then compute
SemaphoresA semaphore synchronizes sender ↔ receivers: receivers signal "ready for data," the sender multicasts, then signals "data valid" so receivers may consume.
CB sizing for a CoreGridCircular buffers are sized for the block the grid shares, not just one tile — enough L1 to hold the multicast block while it is reused.
Optional fusionThe compute kernel can fuse a bias add + activation after the matmul accumulation, avoiding an extra DRAM round-trip.

A multidimensional systolic variant is "coming soon" in the upstream examples.

Lab 3 — Review

1. What redundancy does multicast eliminate?

Many cores re-reading the same A row block or B column block from DRAM. With multicast, one sender reads it once and broadcasts it over the NoC to all receivers.

2. What role do semaphores play?

They synchronize the sender and receivers: receivers signal readiness, the sender multicasts the block, then signals that the data is valid before receivers consume it.

3. Why are CBs sized for the CoreGrid here?

The CB must hold the shared multicast block (not a single tile) so it can be reused across the grid's output tiles; compute may additionally fuse bias + activation.

ArchitectureA grid of Tensix cores (L1 + 2 routers + engine + 5 RISC-V) on a NoC, fed from device DRAM over PCIe; work in 32×32 tiles via CBs.
Labs 1 → 2Single-core tiled matmul, then SPMD static splitting of output tiles across cores with per-core runtime args.

The connecting theme Like the GPU unit, Tenstorrent is a throughput accelerator whose performance is bounded by data movement. The labs progressively move fewer, more-reused tiles — and they build toward the course's CUDA SpMV comparison, contrasting two ways to keep many simple engines fed.

You can now read TT-Metalium kernels, place buffers, and reason about why each optimization helps.

Tie back to the GPU unit: both are throughput machines; the difference is that TT-Metalium makes data movement fully explicit (reader/compute/writer + CBs + multicast), whereas CUDA hides more of it. The SpMV comparison later in the course revisits these trade-offs.
