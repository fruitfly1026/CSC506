Host, Device & the CUDA Program

Host the CPU Device the GPU Kernel a data-parallel function run on the device
Host — CPU
  • Runs ordinary C/C++ serial code
  • Allocates device memory, copies data, launches kernels
  • Orchestrates the program
Device — GPU
  • Massively data-parallel processor
  • Programmed in extended C/C++ (CUDA)
  • Has its own memory (separate, except on an SoC)
One program, two worldsA CUDA program contains both host code and device code. A kernel is a data-parallel function; invoking it spawns many lightweight, hardware-scheduled threads — much like running a graphics shader over many pixels.

Your First Kernel: Vector Add

"Executed N times in parallel by N CUDA threads" — each thread adds one element.

CUDA C — device kernel

__global__ void vectorAdd(const float* A,
                          const float* B,
                          float* C)
{
    int i = threadIdx.x;
    C[i] = A[i] + B[i];
}
CUDA C — host launch

int main() {
    // ... allocate & fill A, B, C ...
    vectorAdd<<<1, N>>>(A, B, C);
}
  • __global__ = declaration specifier: a kernel, runs on the GPU, called from the CPU
  • threadIdx.x = this thread's index within the block
  • <<<1, N>>> = execution configuration: 1 block of N threads
SPMDEvery thread runs the same code on a different i: one program, many data.

Part 4
The Thread Hierarchy

By the end you can…

  • Describe the grid → block → thread hierarchy and its 1D/2D/3D shapes
  • Compute a flattened thread ID in 1D, 2D, and 3D
  • Index a 2D matrix across one block and across many blocks
  • Explain block independence and automatic scalability

Grid → Blocks → Threads

  • A grid = one or more blocks (1D / 2D / 3D)
  • A block = an array of threads (1D / 2D / 3D), the same #threads in each block
  • Threads in a block can synchronize & share memory
  • Older GPUs: threads in different blocks cannot cooperate
  • Newer GPUs (Hopper, CC 9.0+): optional thread block clusters let blocks co-scheduled on a GPC share distributed shared memory
Shape the block to the data 1D → vector  ·  2D → matrix  ·  3D → volume
Figure adapted from UIUC ECE498AL / NVIDIA CUDA C Programming Guide.

Thread ID: Flattening the Index

A block can be 1D, 2D, or 3D. The flattened (linear) thread ID is computed from the thread coordinates and the block dimensions \((D_x, D_y)\).

Block shapeThread coordsFlattened ID
1D\((x)\)\(\text{ID} = x\)
2D, size \((D_x, D_y)\)\((x, y)\)\(\text{ID} = x + y\,D_x\)
3D, size \((D_x, D_y, D_z)\)\((x, y, z)\)\(\text{ID} = x + y\,D_x + z\,D_x D_y\)
Row-major flattenEach higher dimension multiplies by the product of all the lower dimensions — exactly how a multi-dimensional array is laid out in linear memory.

One-Block 2D Matrix Add

A single block of \(N \times N\) threads; each thread owns one matrix element. Flatten the 2D thread coordinate with the 2D formula.

CUDA C — kernel

__global__ void matrixAddition(
        const float* A, const float* B, float* C)
{
    int idx = threadIdx.y * blockDim.x
            + threadIdx.x;
    C[idx] = A[idx] + B[idx];
}
CUDA C — host launch

int main() {
    int blocks = 1;
    dim3 threadsPerBlock(N, N);
    matrixAddition<<<blocks,
                  threadsPerBlock>>>(A, B, C);
}
idxthreadIdx.y * blockDim.x + threadIdx.x is the 2D formula with \(D_x =\) blockDim.x.

The Thread Block (Hardware View)

blockIdx this block's coordinate in the grid blockDim #threads per block (each dimension)

A block reside on one core and its threads share that core's memory — which is why there is a hardware cap on threads per block.

ArchitectureMax threads / block
G80, GT200up to 512
Fermi, Kepler, Maxwell, Pascalup to 1024
Why a cap?All threads in a block live on a single core and share its registers / shared memory — a finite resource.
ConsequenceOne block is not enough for big data. We need many blocks, addressed with blockIdx and blockDim.

Multi-Block 2D Matrix Add

To cover an \(N \times N\) matrix, tile it with many blocks. Each thread computes its global (x, y) from block + thread indices.

CUDA C — kernel body

int x = blockIdx.x * blockDim.x + threadIdx.x;
int y = blockIdx.y * blockDim.y + threadIdx.y;
int idx = y * N + x;
C[idx] = A[idx] + B[idx];
CUDA C — launch configuration

dim3 threadsPerBlock(16, 16);
dim3 blocks(N / threadsPerBlock.x,
            N / threadsPerBlock.y);
Global indexblockIdx skips whole blocks of blockDim threads; threadIdx offsets within the block.

Worked Example: N = 32

16×16 threads per block, a 2×2 grid of blocks, so blockDim = 16. Take the x dimension: i = blockIdx.x*blockDim.x + threadIdx.x.

termrange
blockIdx.x0 … 1
blockDim.x16 (constant)
threadIdx.x0 … 15
i = blockIdx.x·16 + threadIdx.x= [0,1]·16 + [0,15]
minimin = 0·16 + 0 = 0
maximax = 1·16 + 15 = 31  →  i ranges 0…31, exactly covering N = 32. The same holds for j.

Block Independence → Automatic Scalability

Because blocks cannot cooperate, the hardware may run them in any order, on any number of cores. The same program scales across GPUs.

  • Same 8 blocks, same source code
  • 2 cores → blocks run in 4 waves
  • 4 cores → blocks run in 2 waves
  • More cores ⇒ less time, no code change
Write once, scale upBlock independence is the property that lets a kernel transparently use a bigger GPU.

CUDA Memory Model

  • Per-thread: registers + local memory (R/W)
  • Per-block: shared memory (R/W, fast)
  • Per-grid: global memory (R/W, large, slow)
  • Per-grid: constant memory (read-only)
Host accessThe CPU can read/write only global and constant memory — that's where transfers land.
Figure adapted from UIUC ECE498AL / NVIDIA CUDA C Programming Guide.

Allocating Device Memory

cudaMalloc takes the address of a pointer (so it can fill it in) and a byte size; cudaFree releases it.

CUDA C — allocate & free

float* deviceMemory = NULL;
int size = width * height * sizeof(float);

cudaMalloc((void**)&deviceMemory, size);

// ... use deviceMemory on the device ...

cudaFree(deviceMemory);
  • cudaMalloc((void**)&devPtr, size) — allocate size bytes in global memory
  • The (void**)& lets CUDA write the device address back into your pointer
  • cudaFree(devPtr) — release it
Size in bytesAlways multiply element count by sizeof(type) — CUDA deals in bytes, not elements.

Copying Data: cudaMemcpy

Signature: cudaMemcpy(dest, src, size, direction) — destination first, then source.

Direction constant
cudaMemcpyHostToHost

Matrix Multiply: P = M · N

How Much Work Is a Matrix Multiply?

We compute a square \(P = M \cdot N\). Each output element \(P_{ij}\) is a dot product of one row of M with one column of N.

In-class: for a 1000×1000 matrix multiply, how many operations?

1,000,000 output elements (dot products), each costing 1000 multiplies + 1000 adds.
⇒ \(10^6 \times 10^3 = 10^9\) multiplies and \(10^9\) adds = 1 billion multiplies + 1 billion adds.
Why GPUs careA million independent dot products is a perfect fit for thousands of parallel threads.

CPU Matrix Multiply

The classic triple-nested loop: outer two loops pick the output element, the inner loop accumulates the dot product.

C — host (serial)

for (int i = 0; i < width; i++) {
    for (int j = 0; j < width; j++) {
        float sum = 0;
        for (int k = 0; k < width; k++) {
            sum += M[i * width + k] * N[k * width + j];
        }
        P[i * width + j] = sum;
    }
}
Key idea for the portThe two outer loops are independent — every \(P_{ij}\) can be computed at the same time. That parallelism becomes our threads.

GPU Matrix Multiply — 3 Steps

1 memory transfers 2 write the kernel 3 invoke the kernel
CUDA C — host wrapper

void MatrixMultiplyOnDevice(float* M, float* N, float* P, int width) {
    int size = width * width * sizeof(float);
    float *devM, *devN, *devP;

    cudaMalloc((void**)&devM, size);   cudaMemcpy(devM, M, size, cudaMemcpyHostToDevice);  // (1)
    cudaMalloc((void**)&devN, size);   cudaMemcpy(devN, N, size, cudaMemcpyHostToDevice);  // (1)
    cudaMalloc((void**)&devP, size);

    // (3) call kernel: MatrixMultiplyKernel<<<blocks, threads>>>(devM, devN, devP, width);

    cudaMemcpy(P, devP, size, cudaMemcpyDeviceToHost);          // (1) copy result back
    cudaFree(devM);  cudaFree(devN);  cudaFree(devP);
}
Shape of every CUDA programAllocate & upload → launch → download & free.

Naive Matmul Kernel (Single Block)

CUDA C — device kernel

__global__ void MatrixMultiplyKernel(
        const float* devM, const float* devN,
        float* devP, const int width)
{
    int tx = threadIdx.x;
    int ty = threadIdx.y;
    float pValue = 0;
    for (int k = 0; k < width; k++) {
        float m = devM[ty * width + k];
        float n = devN[k * width + tx];
        pValue += m * n;
    }
    devP[ty * width + tx] = pValue;
}
  • Each thread computes one output element \(P_{ty,tx}\)
  • The two outer CPU loops became parallel threads; only the inner k loop remains
  • No sync needed: each thread owns its own pValue accumulator and its own output cell
Row × columndevM[ty*width+k] walks a row of M; devN[k*width+tx] walks a column of N.

Invoking the Kernel

One block of width × width threads — one thread per output element.

CUDA C — launch

dim3 threads(width, width);
dim3 blocks(1, 1);

MatrixMultiplyKernel<<<blocks, threads>>>(devM, devN, devP, width);
Single blockThe whole matrix is mapped to one block — set up to expose the limitations we discuss next.

Critique the Naive Kernel

1. What is the major performance problem?

Lots of global-memory access: each thread reads 2·width values from slow global memory but does only width mul + width add. The compute-to-memory ratio is roughly 1:1 — the kernel is memory-bound.

2. What is the major limitation?

It uses a single block, so it is capped by the max threads per block (512 or 1024). Only small matrices fit — e.g. at most ~32×32 with a 1024-thread cap.

3. What assumptions did we make?

The matrix is square and fits in one block. Fixing these (many blocks, tiling with shared memory) is the next session.

Device & Global Function Constraints

Recursion & launches
  • __device__ functions may recurse on compute capability ≥ 2.0; a __global__ kernel itself cannot be recursive
  • Dynamic parallelism (a kernel launching a kernel) requires compute capability ≥ 3.5
Dynamic allocation
  • malloc/free and new/delete are available in device code since compute capability ≥ 2.0 (allocated on the device heap)
  • Function-scope static local variables are not allowed in device code
Why the limits Thousands of threads share the SM's tiny on-chip state, so deep recursion or large heap use is costly — the features exist but should be used sparingly. [CUDA C++ Programming Guide — C++ Language Support; Dynamic Global Memory Allocation]

A float and a double overload exist for each.
Intrinsics — device only
  • Faster, but less accurate
  • Prefixed with __
  • e.g. __expf, __sinf, __logf, __cosf
Use when speed matters and a few ulp of error is acceptable.

The Streaming Multiprocessor (SM)

SM streaming multiprocessor SP streaming processor (CUDA core)
A GPU is an array of SMs
  • Each SM contains many streaming processors (SPs)
  • One or more warp schedulers
  • Shared memory / L1 and a register file, all on-chip

The Warp — Unit of Scheduling

warp = 32 threadswarpSize built-in
What a warp is
  • 32 threads from one block, with consecutive threadIdx
  • Run on the same SM
  • The unit of thread scheduling — hardware schedules warps, not threads
Zero-overhead warp scheduling
  • Each warp scheduler issues one warp's instruction per cycle; an SM has several schedulers (e.g. 4 on Kepler+), so multiple warps issue concurrently
  • Warps whose next instruction's operands are ready are eligible
  • Eligible warps selected by priority
  • All 32 threads of a warp execute the same instruction (SIMT)
  • Older GPUs (pre-Volta): the 32 lanes advance in lockstep under one shared program counter
  • Newer GPUs (Volta+): independent thread scheduling gives each thread its own PC — still SIMT, but divergent lanes can make progress independently
[CUDA C++ Programming Guide — Hardware Implementation / SIMT Architecture]

Interleaving Warps Hides Latency

When a warp stalls on a long-latency op (e.g. a global load), the scheduler switches to another ready warp — for free. The SM stays busy.

Key ideaGPUs hide latency with parallelism instead of reducing it with caches.
UIUC ECE498/AL.

Branch Divergence

All 32 threads of a warp share one program counter. If threads take different branches, the hardware runs both paths with lane masking.

divergent branch in a warp

if (threadIdx.x < 16) {
    // path A — lanes 0..15 active,
    //          lanes 16..31 masked off
    x = doA();
} else {
    // path B — lanes 16..31 active,
    //          lanes 0..15 masked off
    x = doB();
}
CostNot all ALUs do useful work while a path runs — the masked lanes idle.
Worst caseFully serialized 32-way divergence drops you to as low as 1/32 of peak throughput — one active lane per issue.
No divergence cost if all 32 lanes take the same branch.

In-class: Counting Warps

Q1A GT200 SM hosts 1024 threads. How many warps?
A: \( 1024 / 32 = 32 \) warps.
Q23 blocks × 256 threads — how many warps?
A: \( 3 \times 256 / 32 = 24 \) warps.
Q3A warp is 32 threads but an SM has only 8 SPs — what gives?
A: 8 threads enter the SPs per cycle, so it takes 4 cycles to dispatch a full warp.

In-class: Warps to Hide Latency

SetupA kernel has 1 global read (200 cycles) followed by 4 non-dependent mul/add ops. How many warps are needed to hide the read latency?
Work it out
  • Each op takes 4 dispatch cycles → 4 ops = \( 4 \times 4 = 16 \) cycles of independent work per warp
  • We must cover \( 200 \) cycles: \( 200 / 16 = 12.5 \)
  • Round up: \( \lceil 12.5 \rceil = \) 13 warps

Memory Hierarchy

UIUC ECE498/AL & NVIDIA CUDA C Programming Guide.

Registers

Per-thread, fast on-chip. The register file is split across all resident threads — so register use caps occupancy.

G80 budgetPer SM: 768 threads & 8K registers → \( 8192 / 768 = 10 \) registers/thread available.
Spill example
  • 11 regs × 256-thread blocks → \( 11 \times 256 = 2816 \) regs/block
  • \( 8192 / 2816 = 2 \) blocks → 512 threads → 16 warps
  • Fewer warps → less latency hiding
Special registersthreadIdx · blockIdx · blockDim · gridDim

Local Memory

What it is
  • Register / array spill space
  • Physically lives in global memory (off-chip)
  • Addressing resolved by the compiler
  • Stores are cached in L1 on SM 2.x+
Performance
  • Hurts via extra memory traffic + instruction count
  • But L1-contained spills are not always bad

Shared Memory

Per-block, fast on-chip, full-speed random access — the programmer-managed scratchpad.

G80 budgetPer SM: 16 KB shared, up to 8 blocks → \( 16/8 = 2 \) KB/block if fully occupied.
Occupancy exampleIf each block uses 5 KB → \( 16 / 5 = 3 \) blocks per SM (shared memory is the limiter).
This is the leverShared memory is what makes tiled matmul (Part E) fast — threads in a block cooperatively stage data on-chip.

Global & Constant Memory

Global memory
  • Long latency — 100s of cycles, off-chip
  • G80 86.4 GB/s, GT200 150 GB/s, up to 4 GB
  • Reads cached on 2.x+; writes invalidate the cache
Constant memory
  • Short latency / high bandwidth when all threads read the same location
  • Cached
  • Up to 64 KB

__syncthreads() — Block Barrier

A barrier within a block: a thread waits until all threads in the block reach the call before any continues.

classic barrier pattern

Mds[i] = Md[j];      // each thread loads
__syncthreads();     // wait for ALL loads
func(Mds[i], Mds[i+1]);   // now safe to read
                          // a neighbor's value
Use it whenThreads in a block produce data (into shared memory) that other threads in the same block will consume.
GuaranteeAfter the barrier, every shared-memory write made before it is visible to all threads in the block.

Barrier Walkthrough

Warps reach the barrier at different times; all continue only once the last warp arrives.

Same execution time helpsThreads doing similar work reach the barrier together → little waiting.
Only within a blockCross-block sync would break transparent scalability — blocks must run in any order, on any number of SMs.

Hazard: Conditional Barriers Deadlock

A barrier requires every thread in the block to reach it. Putting it inside a branch that only some threads take → the rest never arrive → hang.

deadlock — barrier in only one branch

if (cond) {
    __syncthreads();   // BAD: only some
}                      // threads reach it
fix — a barrier in BOTH branches

if (cond) {
    __syncthreads();   // all threads
} else {
    __syncthreads();   // reach a barrier
}
RuleEither all threads in the block execute a given __syncthreads(), or none do.
