Host, Device & the CUDA Program

Host the CPU Device the GPU Kernel a data-parallel function run on the device
Host — CPU
  • Runs ordinary C/C++ serial code
  • Allocates device memory, copies data, launches kernels
  • Orchestrates the program
Device — GPU
  • Massively data-parallel processor
  • Programmed in extended C/C++ (CUDA)
  • Has its own memory (separate, except on an SoC)
One program, two worldsA CUDA program contains both host code and device code. A kernel is a data-parallel function; invoking it spawns many lightweight, hardware-scheduled threads — much like running a graphics shader over many pixels.

Your First Kernel: Vector Add

"Executed N times in parallel by N CUDA threads" — each thread adds one element.

CUDA C — device kernel

__global__ void vectorAdd(const float* A,
                          const float* B,
                          float* C)
{
    int i = threadIdx.x;
    C[i] = A[i] + B[i];
}
CUDA C — host launch

int main() {
    // ... allocate & fill A, B, C ...
    vectorAdd<<<1, N>>>(A, B, C);
}
  • __global__ = declaration specifier: a kernel, runs on the GPU, called from the CPU
  • threadIdx.x = this thread's index within the block
  • <<<1, N>>> = execution configuration: 1 block of N threads
SPMDEvery thread runs the same code on a different i: one program, many data.

The Thread Hierarchy

Grid → Blocks → Threads

  • A grid = one or more blocks (1D / 2D / 3D)
  • A block = an array of threads (1D / 2D / 3D), the same #threads in each block
  • Threads in a block can synchronize & share memory
  • Threads in different blocks cannot cooperate
Shape the block to the data 1D → vector
2D → matrix
3D → volume
Adapted from UIUC ECE498AL and the CUDA C++ Programming Guide.

Thread ID: Flattening the Index

A block can be 1D, 2D, or 3D. The flattened (linear) thread ID is computed from the thread coordinates and the block dimensions \((D_x, D_y)\).

Block shapeThread coordsFlattened ID
1D\((x)\)\(\text{ID} = x\)
2D, size \((D_x, D_y)\)\((x, y)\)\(\text{ID} = x + y\,D_x\)
3D, size \((D_x, D_y, D_z)\)\((x, y, z)\)\(\text{ID} = x + y\,D_x + z\,D_x D_y\)
Row-major flattenEach higher dimension multiplies by the product of all the lower dimensions — exactly how a multi-dimensional array is laid out in linear memory.
Watch the orderCUDA's \((x, y)\) is (column, row), the reverse of matrix notation \((\text{row}, \text{column})\). x varies fastest, so threadIdx.x picks the column and threadIdx.y the row: element \(A[\text{row}][\text{col}]\) is thread \((x{=}\text{col},\ y{=}\text{row})\).
CUDA C++ Programming Guide.

One-Block 2D Matrix Add

A single block of \(N \times N\) threads; each thread owns one matrix element. Flatten the 2D thread coordinate with the 2D formula.

CUDA C — kernel

__global__ void matrixAddition(
        const float* A, const float* B, float* C)
{
    int idx = threadIdx.y * blockDim.x
            + threadIdx.x;
    C[idx] = A[idx] + B[idx];
}
CUDA C — host launch

int main() {
    int blocks = 1;
    dim3 threadsPerBlock(N, N);
    matrixAddition<<<blocks,
                  threadsPerBlock>>>(A, B, C);
}
CUDA C++ Programming Guide.

The Thread Block (Hardware View)

blockIdx this block's coordinate in the grid blockDim #threads per block (each dimension)
LimitValue
Max threads / block1024
Warp size32 threads

Why a cap?All threads in a block live on a single SM and share its registers and shared memory — a finite resource; threads execute in warps of 32. On an A100 SM: 64 FP32 cores + 192 KB L1/shared. On an H100 SM: 128 cores + 256 KB.
ConsequenceOne 1024-thread block is not enough for big data. We need many blocks, addressed with blockIdx and blockDim.

Block Independence → Automatic Scalability

Because blocks cannot cooperate, the hardware may run them in any order, on any number of cores. The same program scales across GPUs.

  • Same 8 blocks, same source code
  • 2 cores → blocks run in 4 waves
  • 4 cores → blocks run in 2 waves
  • More cores ⇒ less time, no code change
Write once, scale upBlock independence is the property that lets a kernel transparently use a bigger GPU.

Scheduling Threads — Warps & the SM

The Streaming Multiprocessor (SM)

SM streaming multiprocessor
A GPU is an array of SMs
  • Each SM contains many CUDA cores (FP32, INT32, FP64 units) and Tensor Cores
  • One or more warp schedulers
  • Shared memory / L1 and register files (one per partition), all on-chip
Blocks are assigned to SMs; threads run as warps.

GPC GPU Processing Cluster TPC Texture Processing Cluster (2 SMs) SM Streaming Multiprocessor

Full GH100: 8 GPCs × 9 TPCs × 2 SMs = 144 SMs.
H100 SXM5 enables 132 SMs, with 80 GB HBM3 and 50 MB L2.

4 partitions, each with its own warp scheduler: up to 4 warps issue per clock.
Per SM: 128 FP32, 64 INT32, 64 FP64 units, 4 Tensor Cores, 256 KB of registers.

Redrawn from the NVIDIA H100 whitepaper.

The Warp — Unit of Scheduling

warp = 32 threadswarpSize built-in
What a warp is
  • 32 threads from one block, with consecutive threadIdx
  • Run on the same SM
  • The unit of thread scheduling — hardware schedules warps, not threads
Zero-overhead warp scheduling
  • Warps whose next instruction's operands are ready are eligible; stalled warps are simply skipped — no save/restore cost
  • Eligible warps selected by priority
  • A modern SM has 4 warp schedulers, so up to 4 warps issue per cycle (not just one)
  • All 32 threads of a warp share one instruction stream (SIMT)
NVIDIA A100 & H100 whitepapers; CUDA C++ Programming Guide.

Interleaving Warps Hides Latency

When a warp stalls on a long-latency op (e.g. a global load), the scheduler switches to another ready warp — for free. The SM stays busy.

Key ideaGPUs hide latency with parallelism rather than relying mainly on large caches to reduce it.
UIUC ECE498AL.

Branch Divergence

A warp executes in SIMT lockstep. If threads take different branches, the hardware runs both paths with lane masking.

divergent branch in a warp

if (threadIdx.x < 16) {
    // path A — lanes 0..15 active,
    //          lanes 16..31 masked off
    x = doA();
} else {
    // path B — lanes 16..31 active,
    //          lanes 0..15 masked off
    x = doB();
}
CostThe masked lanes idle while each path runs. No cost if all 32 lanes take the same branch.
Worst caseA fully divergent warp serializes its distinct paths, so throughput falls toward the fraction of lanes active on each path — potentially a large slowdown.

Pre-Volta the 32 threads shared one program counter; Volta+ gives each thread its own PC (Independent Thread Scheduling), but a warp still issues one instruction at a time, so divergent paths are still serialized. We revisit divergence as an optimization lever in Session 2.

CUDA C++ Programming Guide; NVIDIA V100 whitepaper.

In-class: Counting Warps

Q1A block has 1024 threads (the max per block). How many warps?
A: \( 1024 / 32 = 32 \) warps.
Q23 blocks × 256 threads — how many warps?
A: \( 3 \times 256 / 32 = 24 \) warps.
Q3How long to issue one warp?
A: On modern GPUs, a dispatch unit issues 32 threads/clock, so a whole warp issues in one cycle.
CUDA C++ Programming Guide; NVIDIA A100 & H100 whitepapers.

CUDA Memory Model & Transfers

CUDA Memory Model

* Local memory is private to each thread but is stored off-chip in device memory.

  • Per-thread: registers (on-chip) + local memory (off-chip)
  • Per-block: shared memory (R/W, fast)
  • All threads, all kernels: global memory (R/W, large, slow)
Host accessThe CPU reads and writes global memory — that's where cudaMemcpy transfers land.
Adapted from UIUC ECE498AL and the CUDA C++ Programming Guide.

Registers

Per-thread, fast on-chip. The SM's register files (one per partition, 64K registers per SM in total) are split across all resident threads.

Modern budget (A100 / H100)
  • 65,536 (64K) 32-bit registers per SM
  • Up to 255 registers per thread
Special registersthreadIdx, blockIdx, blockDim, gridDim
CUDA C++ Programming Guide; NVIDIA A100 whitepaper.

Local Memory

What it is
  • Register / array spill space
  • Physically lives in global memory (off-chip)
  • Addressing resolved by the compiler
  • Cached in L1/L2 (details vary by architecture)
Performance
  • Hurts via extra memory traffic + instruction count
  • But L1-contained spills are not always bad

Shared Memory

Per-block, fast on-chip, full-speed random access — the programmer-managed scratchpad. It shares a physical block with L1 (192 KB/SM on A100, 256 KB/SM on H100).

Modern budgetConfigurable shared memory per SM: up to 164 KB (Ampere A100) / 228 KB (Hopper H100). Above 48 KB/block requires an explicit opt-in.
This is the leverShared memory is what makes tiled matmul (Part 7) fast — threads in a block cooperatively stage data on-chip.
CUDA C++ Programming Guide; NVIDIA A100 & H100 whitepapers.

Global & Constant Memory

Global memory
  • Long latency — 100s of cycles, off-chip HBM
  • A100 (HBM2) 1.55 TB/s, 40 GB; H100 (HBM3) > 3 TB/s, 80 GB
  • Cached through L2 (40 MB A100 / 50 MB H100) and L1
Constant memory
  • Short latency / high bandwidth when all threads read the same location
  • Cached
  • Total 64 KB
NVIDIA A100 & H100 whitepapers; CUDA C++ Programming Guide.

Part 6
Synchronizing Threads

__syncthreads() — Block Barrier

A barrier within a block: a thread waits until all threads in the block reach the call before any continues.

classic barrier pattern

Mds[i] = Md[j];      // each thread loads
__syncthreads();     // wait for ALL loads
func(Mds[i], Mds[i+1]);   // now safe to read
                          // a neighbor's value
Use it whenThreads in a block produce data (into shared memory) that other threads in the same block will consume.
GuaranteeAfter the barrier, every shared-memory write made before it is visible to all threads in the block.

Barrier Walkthrough

Warps reach the barrier at different times; all continue only once the last warp arrives.

Same execution time helpsThreads doing similar work reach the barrier together → little waiting.
Only within a blockCross-block sync would break transparent scalability — blocks must run in any order, on any number of SMs.

Hazard: Conditional Barriers Deadlock

A barrier requires every thread in the block to reach it. Putting it inside a branch that only some threads take → the rest never arrive → hang.

deadlock — barrier in only one branch

if (cond) {
    __syncthreads();   // BAD: only some
}                      // threads reach it
fix — hoist the barrier out of the branch

if (cond) {
    /* ... */          // divergent work only
}
__syncthreads();       // every thread reaches
                       // the SAME barrier
RuleEither all threads in the block execute a given __syncthreads(), or none do.

Synchronization at Every Level

__syncthreads() is the block-level barrier. CUDA has a synchronization tool at each level of the hierarchy.

LevelHowNotes
Warp__syncwarp(mask)Since Volta, threads of a warp are not guaranteed to run in lockstep

Part 7
Matrix Multiply: Naive → Tiled

How Much Work Is a Matrix Multiply?

We compute a square \(P = M \cdot N\). Each output element \(P_{ij}\) is a dot product of one row of M with one column of N.

In-class: for a 1000×1000 matrix multiply, how many operations?

1,000,000 output elements (dot products), each costing 1000 multiplies + 1000 adds.
⇒ \(10^6 \times 10^3 = 10^9\) multiplies and \(10^9\) adds = 1 billion multiplies + 1 billion adds.
Why GPUs careA million independent dot products is a perfect fit for thousands of parallel threads.
NVIDIA A100 & H100 whitepapers.

CPU Matrix Multiply

The classic triple-nested loop: outer two loops pick the output element, the inner loop accumulates the dot product.

C — host (serial)

for (int i = 0; i < width; i++) {
    for (int j = 0; j < width; j++) {
        float sum = 0;
        for (int k = 0; k < width; k++) {
            sum += M[i * width + k] * N[k * width + j];
        }
        P[i * width + j] = sum;
    }
}
Key idea for the portThe two outer loops are independent — every \(P_{ij}\) can be computed at the same time. That parallelism becomes our threads.

GPU Matrix Multiply — 3 Steps

1 memory transfers 2 write the kernel 3 invoke the kernel
CUDA C — host wrapper

void MatrixMultiplyOnDevice(float* M, float* N, float* P, int width) {
    int size = width * width * sizeof(float);
    float *devM, *devN, *devP;
    cudaMalloc((void**)&devM, size);   cudaMemcpy(devM, M, size, cudaMemcpyHostToDevice);  // (1)
    cudaMalloc((void**)&devN, size);   cudaMemcpy(devN, N, size, cudaMemcpyHostToDevice);  // (1)
    cudaMalloc((void**)&devP, size);
    // (3) call kernel: MatrixMultiplyKernel<<<blocks, threads>>>(devM, devN, devP, width);
    cudaMemcpy(P, devP, size, cudaMemcpyDeviceToHost);          // (1) copy result back
    cudaFree(devM);  cudaFree(devN);  cudaFree(devP);
}
Shape of every CUDA programAllocate & upload → launch → download & free.
CUDA C++ Programming Guide.

Naive Matmul Kernel (Single Block)

CUDA C — device kernel

__global__ void MatrixMultiplyKernel(
        const float* devM, const float* devN,
        float* devP, const int width)
{
    int tx = threadIdx.x;
    int ty = threadIdx.y;
    float pValue = 0;
    for (int k = 0; k < width; k++) {
        float m = devM[ty * width + k];
        float n = devN[k * width + tx];
        pValue += m * n;
    }
    devP[ty * width + tx] = pValue;
}
  • Each thread computes one output element \(P_{ty,tx}\)
  • The two outer CPU loops became parallel threads; only the inner k loop remains
  • No sync needed: each thread owns its own pValue accumulator and its own output cell
Row × columndevM[ty*width+k] walks a row of M; devN[k*width+tx] walks a column of N.
CUDA C++ Programming Guide.

Invoking the Kernel

One block of width × width threads — one thread per output element.

CUDA C — launch

dim3 threads(width, width);
dim3 blocks(1, 1);

MatrixMultiplyKernel<<<blocks, threads>>>(devM, devN, devP, width);
Single blockThe whole matrix is mapped to one block, so width × width ≤ 1024 (i.e. width ≤ 32) — set up to expose the limitations we discuss next.
CUDA C++ Programming Guide.

Critique the Naive Kernel

1. What is the major performance problem?

Lots of global-memory access: each thread reads 2·width values from slow global memory but does only width mul + width add. The compute-to-memory ratio is roughly 1:1 — the kernel is memory-bound.

2. What is the major limitation?

It uses a single block, so it is capped by the max threads per block = 1024. Only small matrices fit — a square tile of at most 32×32 = 1024 threads.

3. What assumptions did we make?

The matrix is square and fits in one block. Fixing these — many blocks, then tiling with shared memory — comes next.
CUDA C++ Programming Guide.

Naive Multi-block Matmul

Each thread computes one element of P by streaming an entire row of M and column of N from global memory.

CUDA C — naive kernel

int col = blockIdx.x*blockDim.x + threadIdx.x;
int row = blockIdx.y*blockDim.y + threadIdx.y;
float pValue = 0;
for (int k = 0; k < width; k++)
    pValue += devM[row*width + k]
            * devN[k*width + col];
devP[row*width + col] = pValue;

The Bandwidth Bottleneck

Every pValue += does 2 global loads (4 B each) for 2 FLOPs — far too much memory traffic.

A100 numbers
  • Peak FP32 compute: 19.5 TFLOPS
  • At 4 B loaded per FLOP that would need ≈ 78 TB/s
  • But HBM2 bandwidth is only 1.55 TB/s
ResultIf every load goes to DRAM, memory caps you at \( \approx \) 390 GFLOPS — only about 2% of peak.
FixWe must cut global-memory access — reuse data on-chip via shared memory.
NVIDIA A100 whitepaper.

The Tiling Idea

Break P into TILE_WIDTH × TILE_WIDTH tiles — one tile per block. Each phase:

  • Load a tile of M and a tile of N into shared memory
  • __syncthreads() — wait for the loads
  • Accumulate the partial dot product from the tiles
  • __syncthreads() — before overwriting the tiles next phase
UIUC ECE498AL.

Tiled Kernel

CUDA C — shared-memory tiled matmul

__shared__ float sM[TILE_WIDTH][TILE_WIDTH];
__shared__ float sN[TILE_WIDTH][TILE_WIDTH];
int bx = blockIdx.x;  int by = blockIdx.y;
int tx = threadIdx.x; int ty = threadIdx.y;
int col = bx*TILE_WIDTH + tx;
int row = by*TILE_WIDTH + ty;
float pValue = 0;
for (int m = 0; m < width/TILE_WIDTH; m++) {        // m = phase index
    sM[ty][tx] = devM[row*width + (m*TILE_WIDTH + tx)];
    sN[ty][tx] = devN[col + (m*TILE_WIDTH + ty)*width];
    __syncthreads();                                 // 1: tiles fully loaded
    for (int k = 0; k < TILE_WIDTH; ++k)
        pValue += sM[ty][k] * sN[k][tx];
    __syncthreads();                                 // 2: done before overwrite
}
devP[row*width + col] = pValue;
Two barriers#1 after the loads so every thread sees the full tiles; #2 so no thread overwrites the tile before others finish reading it. width/TILE_WIDTH = number of phases.

▶ Demo: Demos/cuda/hotspot/gemm_tiled.cu

Choosing TILE_WIDTH

Bounded by max threads/block (1024 on all current GPUs, CC ≥ 2.0) and shared memory per block.

Sizing the tiles
  • TILE_WIDTH = 32 → \( 32\times32 = 1024 \) threads/block (the max)
  • \( 32 \times 32 \times 4\,\text{B} = 4 \) KB each for sM, sN → 8 KB/block — easily within 164 KB (A100)
  • Larger tile → more reuse
Payoff
  • Each value reused TILE_WIDTH times → global access cut by TILE_WIDTH× (16× at TW=16, 32× at TW=32)
  • On A100 the bandwidth bound rises from ~2% of FP32 peak to ~32% (TW=16) or ~64% (TW=32)
CUDA C++ Programming Guide; NVIDIA A100 whitepaper.

First-order Sizing

TILE_WIDTH = 16
  • \( 16 \times 16 = 256 \) threads/block
  • A \( 1024 \times 1024 \) output P → \( 64 \times 64 = 4096 \) blocks
  • Each block does 512 global loads (per phase, both tiles) for 8192 mul/add
Bottom lineTiling cuts global traffic 16×: 0.25 B/FLOP instead of 4. On A100 that lifts the first-order bound from ~0.39 to ~6.2 TFLOPS — 16× faster, but still bandwidth-bound at ~32% of peak. Modern GPUs have far more compute per byte than G80 did, so reaching peak needs more reuse (bigger tiles, register tiling) — Session 2.
