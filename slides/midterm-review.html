Why Parallel: Multicore & the Power Wall

The Switch to Multicore

Low-hanging-fruit theory Easy performance is taken first. ILP (pipelining, superscalar, out-of-order, caches) needs no programmer effort. Multicore needs TLP, and TLP needs parallel programming — so it came last, once cheap ILP ran out.
Why ILP stopped being cheap Deeper pipelines: latching overhead and critical loops grow with depth.
Wider issue: complexity grows quadratically with width.
TLP formWhat runs in parallelProCon
LoopIndependent iterationsVery high parallelism, easy balanceSome loops aren't parallel
FunctionIndependent code segmentsLarge granularity, low overheadLow degree, hard to balance
ProgramIndependent programsNo communicationHard to balance, few chances
Lecture 1, Module 1.1

The Power Wall

\( P = P_{dynamic} + P_{static} = \alpha C V^2 f + V \cdot I_{leak} \)

  • Lower \(V_{thd}\) raises \(f_{max}\) almost linearly.
  • Lower \(V_{thd}\) raises leakage exponentially: \( I_{leak} > e^{-qV_{thd}/kT} \).
  • So V could not keep dropping, and frequency stalled around 2005.

Energy metrics: EPI = W/IPS = J/inst; EDP = E × D; ED²P = E × D².

Transistors / chip× 1/S² = 2× 1/S² = 2

Three signatures, ~2001–2005 Frequency stops climbing, pipelining reverses, and power management (clock gating, DVFS, power gating) becomes essential.

Practice — Part 1

1. Gate length scales at S = 0.8. Find dynamic power under constant-field vs. constant-voltage scaling.

Constant-field: \(1.56 \cdot 0.8 \cdot 0.8^2 \cdot 1.25 \approx 1.0\) → constant. Constant-voltage: \(1.56 \cdot 0.8 \cdot 1.25 \approx 1.56\) → +56%.

2. How does the threshold voltage affect static vs. dynamic power as transistors shrink?

Lowering \(V_{thd}\) lets you lower V, so dynamic power drops (≈ linearly). Static (leakage) power rises exponentially.

3. Classify: a single core, a GPU, a multicore chip, and a server farm of PCs.

Single core: SISD. GPU: SIMD (or SIMD/MIMD). Multicore chip: MIMD. Server farm: distributed MIMD with no shared memory.

Performance Metrics & Scalability

The Four Metrics

MetricDefinition
Execution time\(T_P\), \(T_S\): wall clock until the last PE finishes
Speedup\(S = T_S / T_P\)
Efficiency\(E = S / p\)
Cost\(C = p\,T_P\)
Total overhead\(T_o = p\,T_P - T_S\)

\( E = \dfrac{T_S}{p\,T_P} = \dfrac{T_S}{C} \)

Read the fine print \(T_S\) is the time of the best sequential algorithm, not a serial run of the parallel code.
Super-linear speedup (S > p) Possible: the per-PE working set now fits in cache, or an exploratory search finds the answer early.
Cost and imbalance Idle time is still charged. A PE waiting on a straggler costs as much as a working one.
Lecture 3, Module A

Amdahl vs. Gustafson

Amdahl: strong scaling Fixed problem size; serial fraction s.

\( S(p) = \dfrac{1}{\,s + \dfrac{1-s}{p}\,} \qquad S_{max} = \dfrac{1}{s} \)

Equivalently \( T_p = T_1\left(s + \dfrac{1-s}{p}\right) \) and \(T_\infty = s\,T_1\).

s = 0.2 caps speedup at 5× no matter how many PEs.

Gustafson: weak scaling Work grows with p; parallel time fixed at 1.

\( S(p) = s + p\,(1-s) \)

s = 0.05, p = 32: S ≈ 30.5, versus Amdahl's ceiling of 20.

What you hold fixed Strong scaling fixes the total problem, so efficiency falls. Weak scaling fixes the work per PE, so efficiency can stay ≈ constant.
Lecture 3, Module B

Overhead & Isoefficiency

Three sources of overhead Interaction (synchronization, communication); idling (imbalance, serialization, contention); excess computation (work repeated across PEs).

Real speedup peaks and then declines, because overhead grows with p.

Summing n numbers on p PEs

\( T_P = \dfrac{n}{p} + 2\log p \qquad S = \dfrac{np}{n + 2p\log p} \qquad E = \dfrac{n}{n + 2p\log p} \)

Isoefficiency

\( W = \dfrac{E}{1-E}\,T(W,p) = K\cdot T(W,p) \)

W = work of the best sequential algorithm (not data size). W(p) ≤ O(p) → scalable.

Lecture 3, Module B

Communication Cost & the Roofline

Message passing: α and β A message of m bytes costs \(\alpha + m\beta\), with \(\alpha \gg \beta\).

Matmul, per PE:

\( \dfrac{n}{\alpha + n\beta} \;\longrightarrow\; \dfrac{g^2 n}{\alpha + g n \beta} \)

α = 1000, β = 0.2, n = 1000, g = 10: 0.83 → 33.3.

Shared memory: roofline

\( P = \min(\pi,\ \beta \times I) \qquad \text{ridge } I = \pi/\beta \)

I < π/β → memory-bound, ceiling βI. I > π/β → compute-bound, ceiling π.

Matmul: naive I = 0.25; blocked I = g/4.

One idea, two bottlenecks Blocking raises reuse. It improves the computation–communication ratio and moves a kernel right, across the ridge.
Lecture 3, Modules C–D

Practice — Part 2

1. A program gets speedup 20 on 32 PEs. What is its efficiency?

\(E = S/p = 20/32 = 0.625\).

2. State Amdahl's maximum speedup for s = 0.05. Why does real speedup peak and then decline?

\(1/s = 20\)×. Overhead (communication, idling, excess computation) grows with p and eventually outweighs the extra compute.

3. π = 400 GFLOP/s, β = 100 GB/s. Where is the ridge? What is the ceiling at I = 0.5 flop/byte?

Ridge = 400/100 = 4 flop/byte. 0.5 < 4, so memory-bound: P = 100 × 0.5 = 50 GFLOP/s.

Part 4
Dependences & Loop-Level Parallelism

Three Dependence Types

NotationTypeMeaning
S1 T S2true (RAW)S1 writes a location later read by S2
S1 A S2anti (WAR)S1 reads a location later written by S2
S1 O S2output (WAW)S1 and S2 write the same location

Anti and output are "name" dependences: they come from reusing a storage location, not from real data flow.

Loop-carried vs. loop-independent

for (i = 1; i < n; i++) {
  S1: a[i] = a[i-1] + 1; // S1[i] T S1[i+1]: carried
  S2: b[i] = a[i];       // S1[i] T S2[i]: independent
}

Only loop-carried dependences block parallelism across iterations. A loop level with none is fully parallel (DOALL).

Lecture 5–6, Module 3.1

Which Loop Carries It? ITG vs. LDG

Carried on j → the i loop is parallel

for (i = 1; i < n; i++)
  for (j = 1; j < n; j++)
    S3: a[i][j] = a[i][j-1] + 1;
// S3[i,j] T S3[i,j+1]
Carried on i → the j loop is parallel

for (i = 1; i < n; i++)
  for (j = 1; j < n; j++)
    S4: a[i][j] = a[i-1][j] + 1;
// S4[i,j] T S4[i+1,j]
ITG — Iteration-space Traversal Graph Nodes are iteration points; edges show the traversal (happens-before) order.
LDG — Loop-carried Dependence Graph Nodes are iteration points; edges are dependences, labelled T / A / O.
5-point stencil Every grid edge is a true and an anti dependence. Points on one anti-diagonal are independent → wavefront.

Four Forms of Loop-Level Parallelism

FormWhat runs in parallelSynchronizationDegree
DOALLIndependent iterations (no carried dependence at that level)NoneGrows with n
DOACROSSDependent iterations, overlappedpost / wait on the carried partAverage 1 + TS1/TS2
DOPIPEDependent statements, as pipeline stagespost / wait between stagesNumber of stages
FunctionIndependent code sections (e.g. after loop distribution)None between sectionsNumber of tasks
post / wait post(x) increments m(x). wait(x) blocks while m(x) ≤ 0, then decrements it.
How much parallelism? \( S_\infty = T_1/T_\infty = W/D \) = average degree. Rewriting can inflate the peak degree, never the average.
Lecture 5–6, Module 3.2

DOACROSS and DOPIPE in Code

DOACROSS: a[i] = a[i-1] + b[i]*c[i]

post(0);
for (i=1; i<=N; i++) {   // DOACROSS loop
  temp = b[i]*c[i];      // S1: independent
  wait(i-1);             // need a[i-1]
  a[i] = a[i-1] + temp;  // S2: carried dep
  post(i);               // release i+1
}

Time goes from N·(TS1+TS2) to TS1 + N·TS2.

DOPIPE: S1 carried, S2 follows S1

for (i=2; i<=N; i++) {   // stage 1
  a[i] = a[i-1] + b[i];
  post(i);
}
for (i=2; i<=N; i++) {   // stage 2
  wait(i);
  c[i] = c[i] + a[i];
}

Speedup → 2: capped by the serial a[] chain in stage 1.

Rule of thumb Reach for DOALL first. Try DOACROSS if the level carries a dependence. Layer function or DOPIPE parallelism on top. When code analysis is too pessimistic, change the algorithm (red-black, asynchronous).
Lecture 5–6, Modules 3.2–3.3

Practice — Dependences

1. What are the three dependence types? Which kind blocks iteration-level parallelism?

True (RAW), anti (WAR), output (WAW). Only loop-carried dependences block parallelism across iterations.

2. ITG vs. LDG — what does each show?

The ITG shows the traversal order; the LDG shows the dependences between iteration points.

3. Is for (i=2; i<=n; i++) a[i] = a[i-2]; DOALL? How much parallelism can you extract?

No: a true dependence of distance 2 is carried by i. Even and odd indices never touch, so split by parity: 2 independent chains. The degree stays 2 however large n is.

Granularity, Blocking & Distribution

Granularity Fine-grained: more parallelism and balance, more overhead. Coarse-grained: less overhead, better locality, less parallelism.
Blocking An n×n matrix in B×B blocks gives (n/B)×(n/B) tasks. Choose the largest B with \(B^2 \le\) cache size. Cost: communication between neighbouring blocks.
Modulo mapping \( B[i][j] \rightarrow P[\,i \bmod P_x\,][\,j \bmod P_y\,] \)
DistributionBlock sizeStrength
Blockn/pBest locality
Cyclic1Best load balance
Block-cyclicbetween 1 and n/pTunes between the two
Two more axes Static vs. dynamic assignment. Row- vs. column-wise: which dimension is split, which decides what stays local.

A parallel phase is only as fast as its slowest processor.

Cache Basics

A cache is a table A set is a row, a way is a column, a line is a cell. Direct-mapped = 1-way; fully associative = one set with all the ways.
Address = tag | index | offset

2048 sets, 64-byte blocks: 6 offset bits, 11 index bits, the rest is tag.

Inclusion, Exclusion & NINE

PolicyUpper-level block also in the lower level?Consequence
InclusiveAlwaysFill both levels; replacing a lower block back-invalidates the upper copy. Wastes capacity.
ExclusiveNeverA block lives in exactly one level. No duplication, maximum capacity.
NINENot enforcedEach level evicts on its own; may or may not be duplicated.
Why inclusion An external request only needs to check the lower level. If the block is not there, the upper level cannot have it.
Real chips AMD Shanghai chose a NINE L3: inclusive would waste ~1/3 of the capacity; exclusive would need too much L2→L3 bandwidth.

Practice — Memory Hierarchy

1. In a 4-way cache, what do "set", "way", and "line" mean?

A set is the row selected by the index; a way is one of the 4 columns; a line is one cell (one block of storage).

2. Why does inclusion simplify handling an external request?

You only check the lower level. If the block isn't there, the upper level can't have it, so the upper level's tags aren't disturbed.

3. Which "C" does more associativity reduce? Which does a bigger cache reduce?

More associativity → fewer conflict misses. Bigger cache → fewer capacity misses.

4. Why is pseudo-LRU preferred to true LRU in big caches?

True LRU costs \(O(\text{ways}^2)\) state; pseudo-LRU costs \(O(\text{ways})\) and tracks recency well enough.

Part 7
Synchronization

Primitives & Why Hardware Is Needed

PrimitivePurpose
LockMutual exclusion: one thread in the critical section
Point-to-pointpost / wait (or send / recv): orders two threads
BarrierNo thread passes until all arrive
Lock performance criteria Uncontended latency, traffic, storage, and fairness.

A barrier costs as much as its slowest thread, so load balance is critical.

A pure-software lock is broken

void lock(int *lockvar) {
  while (*lockvar == 1) {};  // wait
  *lockvar = 1;              // acquire
}

The read and the write are not atomic: two threads can both read 0, both write 1, and both enter.

Atomic read-modify-write test-and-set, fetch-and-op, exchange, and compare-and-swap. Atomic = all-or-nothing and serialized.
Lecture 8, Module 5; Chapter 9, Module 8.1

test&set → TTSL → LL/SC

test&set

lock: t&s R1, &lockvar
      bnz R1, lock
      ret

Every failed attempt is an atomic write. Fix: back-off.

test-and-test-and-set

lock: ld  R1, &lockvar
      bnz R1, lock
      t&s R1, &lockvar
      bnz R1, lock
      ret

Spins on a cached load: no traffic while the lock is held.

LL/SC

lock: LL   R1, &lockvar
      bnz  R1, lock
      addi R1, #1
      SC   R1, &lockvar
      bnz  R1, lock
      ret

SC fails if the link was cleared. A failed SC generates no bus transaction.

Still not scalable With p contending threads, each critical section costs \(O(p^2)\) traffic, and none of these locks is fair.

Ticket Lock, ABQL & Lock Comparison

Ticket lock my_ticket = fetch_and_inc(next_ticket), then wait until now_serving == my_ticket. FIFO → fair. A release still invalidates all waiters.
ABQL Each thread spins on its own slot can_serve[my_ticket]. A release sets only the next slot: O(1) traffic, O(p) storage.

Chapter 9, Module 8.2

Barriers & Transactional Memory

Centralized barrier with sense reversal

void barrier() {
  valueToWait = 1 - valueToWait; // per thread
  lock(&barLock);
  numArrived++;
  myCount = numArrived;
  unlock(&barLock);
  if (myCount < NUM_THREADS)
    while (canGo != valueToWait) {};
  else {                 // last to arrive
    numArrived = 0;
    canGo = valueToWait; // release all
  }
}

Without the sense flip, a fast thread can reset canGo for the next barrier while slow threads are still leaving this one.

Transactional memory An atomic { … } block gives atomicity (all or nothing) and isolation (serializable).
Conflict rule T1's write set must not overlap T2's read or write set. On conflict: abort, cancel, retry.
HTM support Speculative buffering, conflict detection, commit, and rollback.
Chapter 9, Module 8.2

Practice — Synchronization

1. What does TTSL improve over test&set? What does LL/SC improve over TTSL?

TTSL spins on reads, so no invalidations while the lock is held. With LL/SC, a failed acquisition (failed SC) generates no bus transaction.

2. What does the ticket lock improve over LL/SC? What does ABQL improve over the ticket lock?

Ticket: fairness (FIFO order). ABQL: a release invalidates only the next waiter, O(1) instead of O(p).

3. Why is load balancing important when barriers are used?

A parallel region takes as long as its slowest thread; imbalance leaves the others idle at the barrier.
