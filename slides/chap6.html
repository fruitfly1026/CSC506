Introduction to Shared Memory Multiprocessors
This chapter introduces the shared-memory abstraction: any processor can touch any address with an ordinary load/store. That convenience hides three hard support problems we will spend the rest of the course on — cache coherence, the memory consistency model, and synchronization. The whole chapter is one module (6.1) organized around those three pillars.

The Shared-Memory Abstraction

Definition Any address in main memory is reachable from any processor with an ordinary load / store instruction.
Advantages
  • Naturally supports shared-memory programs (easier to write — e.g. OpenMP directives)
  • Single OS image across all cores
  • Fits larger problems: \( \text{mem}_n = n \cdot \text{mem}_1 \)
  • Allows fine-grain sharing
Disadvantage — cost to provide
  • Cheap on small scale (2–32 procs) and multicore
  • Expensive on large scale (> 64 procs)

The convenience is real; the engineering bill arrives as coherence + consistency + synchronization.

Coherence by Analogy: Write Propagation

You (A) agreed to meet friend B exactly one month from now. An emergency comes up — you need to move the meeting to three months from now. The only way to reach B is by mail, and you may only write the new date.

Q: How do you ensure you'll still meet B? How important is reliable delivery?

Principle 1 — Write Propagation When a processor writes a memory address, the write must be propagated to all other processors.

The "letter" = the propagated write. If it never arrives, B keeps the stale value — exactly the coherence bug.

Coherence by Analogy: Write Serialization

You already mailed B "change to 3 months." Then you realize you actually need "change to 2 months," so you mail a second letter. If the letters arrive out of order, B ends up at the wrong date.

Q: How do you guarantee the final date is correct? How important is delivery ordering?

Principle 2 — Write Serialization When there are two writes to the same address, the order they are seen must be the same for all processors.

Everyone must agree on the last write — or different cores converge to different values.

Will This Parallel Code Work?

Parallel reduction with a lock

sum = 0;
begin parallel
  for (i = 0; i < 2; i++) {
    lock(id, myLock);
    sum = sum + a[i];
    unlock(id, myLock);
  }
end parallel
Print sum;

Suppose a[0] = 3 and a[1] = 7.

Will it print sum = 10?

Spoiler Not necessarily — with write-back caches each core can hold its own private copy of sum. The lock provides mutual exclusion, but it does not by itself make caches agree.
No, assuming a write-back cache. It would be fine if sum were uncachable. The problem persists even with a write-through cache (other caches still hold stale copies). I/O DMA can create the same coherence problem.

Illustration: How Coherence Breaks

Three cores share a bus to main memory. We watch sum as P1 and P2 each add their element.

The bug Both P1 and P2 read sum=0 from memory, then each writes back a private dirty copy (3 and 7). Neither saw the other's update — write propagation failed. Final printed value could be 3, 7, or 10 depending on timing.
Step through the fragments: P1 loads sum=0 and writes 3 into its own write-back cache (Dirty). P2 independently loads the still-stale 0 from memory and writes 7. Memory never sees the right value and the two caches disagree. This is the canonical coherence failure.

Does Cache Organization Save Us?

Do P1 and P2 see the same value of sum at the end?

No — each holds its own private copy; without a coherence protocol they diverge.

What if we use write-through caches instead of write-back?

Still broken. Writes reach memory immediately, but the other cache keeps its stale copy until it is told to update or invalidate. Propagation is still missing.

What if there are no caches, or sum is uncachable?

Then it works — every access goes straight to the single shared memory location. But giving up caching destroys performance, so we keep caches and add a protocol.

Why Serialization Matters: Two Writes

P1 and P2 both write x. If P3 and P4 receive the two writes in different orders…

ResultP3 and P4 settle on different final values of x. The system is incoherent.

All processors must agree on a single global order of writes to the same address.

Write vs. Read, and Read vs. Read

Write vs. read

P1 writes x=1; it reaches P2 and P3 at different times. P2 reads x before the write has reached P3.

EffectP2 and P3 observe different values — the ordering of a write relative to reads matters too.

Read vs. read

Doesn't matterOnly one value is involved — two reads can be reordered freely.
So the rule isThe order between a write and anything else must be consistent across processors. Hence the name write serialization.

Requirements: a write must appear atomic, and its completion must be identifiable.

Coherence: The Two Properties

Write propagation A value written in one cache must reach the other caches.
Write serialization Successive writes to the same datum are seen in the same order by all caches.
We need a protocol A mechanism that guarantees both is a cache coherence protocol. It can be built in hardware or software — but software implementations usually carry very high overhead, so real machines do it in hardware (Chapter 7 onward).

From One Datum to Many: Consistency

Coherence is per-address Cache coherence only governs propagation and ordering of accesses to a single memory location.

Is there any need to order accesses to multiple, different data items?

Yes Programs rely on ordering between distinct variables (e.g. "set data, then set the ready flag"). Guaranteeing that cross-address ordering is the job of the memory consistency model.

Consistency: The Flag Idiom

P0 — producer

S1: datum = 5;
S2: datumIsReady = 1;
P1 — consumer

S3: while (!datumIsReady) {};
S4: print datum;

Common in DOACROSS and DOPIPE point-to-point synchronization.

  • Correctness depends on the order of S1 before S2, and S3 before S4
  • What if S2 runs before S1? P1 prints garbage.
  • What if S4 runs before S3? P1 reads before it is ready.
The trapEven if P0 executes S1 before S2, P1 does not necessarily see them in that order on a real multiprocessor.

Global Ordering & the Consistency Model

Full ordering Every access a processor issues runs in program order, and all processors see them in that order.

✗ Full ordering is expensive — it forbids almost every performance optimization.

Real solution — a contract A memory consistency model documents which orderings the hardware does guarantee and which it does not.
  • Programmers must write code that conforms to the model
  • Misunderstanding it is a source of subtle bugs
  • It contributes to code non-portability across machines

Enforcing Order: Compiler + Hardware

Both layers can reorder memory operations, so both must cooperate.

The compiler may reorder

  • No data dependence between S1 and S2 → free to swap them
  • Must be explicitly told not to — e.g. declare volatile
  • This disables aggressive sequential optimizations

The hardware may reorder

  • Write buffers, the memory controller, network delay
  • Many ILP features reorder memory references
  • Goal: preserve required ordering while still exploiting ILP
Key tensionWe want ordering guarantees and performance — the consistency model defines exactly where the line is drawn.

Synchronization: A First (Broken) Lock

C — naïve spin lock

void lock(int *lockvar) {
  while (*lockvar == 1) {};  // wait until released
  *lockvar = 1;              // acquire lock
}
void unlock(int *lockvar) {
  *lockvar = 0;
}
In machine language

lock:   ld   R1, &lockvar   ; R1 = MEM[&lockvar]
        bnz  R1, lock       ; retry if R1 != 0
        sti  &lockvar, #1   ; MEM[&lockvar] = 1
        ret
unlock: sti  &lockvar, #0   ; MEM[&lockvar] = 0
        ret

Goal: guarantee mutual exclusion — at most one thread in the critical section.

Why That Lock Is Wrong

Not atomic The sequence ld → bnz → sti is three separate instructions, not one indivisible operation.

Two threads can interleave like this:

  • T1 reads lockvar = 0, decides to acquire
  • T2 reads lockvar = 0 before T1 stores
  • Both then store 1 and enter the critical section
Consequence Multiple threads enter the critical section simultaneously — mutual exclusion is violated. We need the test-and-set to be atomic.

Peterson's Algorithm (Software-Only)

Two-process mutual exclusion

int turn;
int interested[n];   // init 0

void lock(int process) {     // 0 or 1
  int other = 1 - process;
  interested[process] = TRUE;
  turn = process;
  while (turn == process &&
         interested[other] == TRUE) {};
}
void unlock(int process) {
  interested[process] = FALSE;
}

Exit the wait loop only if:

  • interested[other] == FALSE — the other process isn't competing (or just unlocked), or
  • turn != process — the other set turn to itself and is blocked in its own loop
No atomic instruction neededCorrectness comes purely from the ordering of two ordinary writes.

Peterson: The Common Case (No Race)

Proc 0

interested[0] = TRUE;
turn = 0;
while (turn==0 && interested[1]==TRUE) {};
// interested[1]==FALSE
// → Proc 0 enters critical section
Proc 1 (arrives later)

interested[1] = TRUE;
turn = 1;
while (turn==1 && interested[0]==TRUE) {};
// turn==1 && interested[0]==TRUE
// → Proc 1 spins until Proc 0 unlocks
WorksProc 0 is already inside; Proc 1 correctly waits. After unlock sets interested[0]=FALSE, Proc 1 proceeds.

Peterson: The Contended Case

Proc 0

interested[0] = TRUE;
turn = 0;



while (turn==0 && interested[1]==TRUE) {};
// turn==1 now → Proc 0 enters CS
Proc 1 (interleaved)

interested[1] = TRUE;


turn = 1;          // overwrites turn

while (turn==1 && interested[0]==TRUE) {};
// → Proc 1 waits until Proc 0 unlocks
Still correctBoth set interested, but whoever writes turn last loses the tie and waits. Exactly one enters. turn breaks the symmetry.

Peterson Depends on Memory Ordering

Correctness hinges on the global order of these two writes:


A: interested[process] = TRUE;
B: turn = process;

If the hardware/compiler lets B appear before A on the other core…

Reordered: both enter!

// Proc 0          // Proc 1
interested[0]=TRUE;
                   turn = 1;
turn = 0;
                   interested[1]=TRUE;
while(turn==0 && interested[1]) {};
// turn==0? sees interested[1]
// stale → BOTH may enter CS
SoPeterson is correct only under a strong consistency model (or with explicit fences). It is intimately tied to the memory consistency problem.

Why Software Locks Lose to Hardware

Assuming full ordering Peterson does achieve mutual exclusion — but it is very inefficient.
  • Scaling to n threads needs elaborate schemes
  • e.g. a hierarchical tournament of pairwise locks
The real fix If non-atomicity is the root problem, let hardware provide an atomic load–modify–store sequence — typically a single atomic instruction (e.g. test-and-set, fetch-and-add, compare-and-swap).

Atomic instructions make a correct lock both simple and fast — the subject of later chapters.

Module 6.1 — Review

1. What two principles define cache coherence?

Write propagation (a write reaches all caches) and write serialization (all processors see writes to one address in the same order).

2. How does memory consistency differ from coherence?

Coherence orders accesses to a single address; the consistency model defines ordering guarantees across different addresses.

3. Why does the naïve spin lock fail, and what fixes it?

Its test-then-set isn't atomic, so two threads can both acquire. A hardware atomic instruction (atomic load–modify–store) fixes it.
