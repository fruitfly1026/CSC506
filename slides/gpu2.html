Part A
Memory Coalescing

Memory Coalescing — Which Access Pattern?

A matrix is stored row-major in global memory. Each thread loops over the matrix. Which pattern does the hardware like?

(a) Each thread walks down a column In each iteration, adjacent threads read adjacent words of one row.
(b) Each thread walks along a row In each iteration, adjacent threads read words a full row apart.
Answer: (a) is coalesced ✓ We want the threads active in one load iteration to touch contiguous memory. The hardware then fuses the warp's reads into the fewest 32-byte sectors (CC ≥ 6.0).
CUDA C++ Best Practices Guide.

Why Coalescing — DRAM Bandwidth

The GPU fuses a warp's consecutive reads into the fewest 32 B sectors: 32 floats fill 4 sectors. Peak bandwidth needs large consecutive requests.

GPU (memory)Peak DRAM bandwidth
V100 (HBM2)0.9 TB/s
A100 40 GB (HBM2)1.55 TB/s
H100 SXM5 (HBM3)3 TB/s
Random access Scattered or random reads cannot be fused, so effective bandwidth drops far below peak.
NVIDIA V100, A100 & H100 whitepapers; CUDA C++ Best Practices Guide.

Coalescing Strategy

Pattern
  1. Read global memory coalesced into shared memory (whole warp, contiguous)
  2. Then access shared memory randomly at full on-chip bandwidth
  3. (ignoring bank conflicts — Part H)
Modern note Less critical on GPUs with large on-chip caches, but the coalesced global → staged shared pattern is still the workhorse for tiled kernels.
CUDA C++ Best Practices Guide.
Part B
Seeing Memory Inefficiencies

Count Distinct Warps, Not Accesses

sector — 32 B, the transaction unit (8 words) word — 4 B temperature — distinct warps touching a word or a sector
The coalescing ruleA memory instruction issues per warp. One warp's accesses to different words of a sector coalesce into one 32 B transaction. Accesses to that sector from different warps cannot coalesce; each costs its own transaction.
So count distinct warpsIn (a) and (b) every word is accessed once, so the access counts are identical. Only the distinct-warp count separates them: 1 transaction vs. 8. A sector's distinct-warp count ≈ the number of sector transactions it costs.
Figure: cuThermo (Zhao et al., arXiv:2507.18729).

Part C
Hot Spots

Hot and Random Hot Sectors

Every word of every sector is touched by all 32 warps. The sector total (32) equals its hottest word.

Words are shared by a random number of warps (0–8). Which words are hot depends on the input.

Why it costs, and the fixEach warp that reads a hot sector issues its own transaction. Data that many warps share belongs on-chip: stage it in shared memory once per block.
Figure: cuThermo (Zhao et al., arXiv:2507.18729).

Hot Spot — GEMM

GEMM — every k step goes back to global memory

for (size_t k_idx = 0; k_idx < k; ++k_idx)
    sum += A[C_row_idx * lda + k_idx]
         * B[k_idx * ldb + C_col_idx];

Every warp in a block re-reads the same sectors of B from global memory. Every word of those sectors is touched by all the warps.

FixStage tiles in shared memory, exactly the tiled kernel from Session 1. Each tile of B is read from global memory once per block, then reused on-chip by every warp.
Demohotspot/gemm_coalesced.cu → gemm_tiled.cu: 32×32×32 shared-memory tiling added. 1.551 → 1.235 ms (1.26×).
cuThermo (arXiv:2507.18729); leimao/CUDA-GEMM-Optimization; parallel-demos, RTX A4500.

Random Hot Spot — SpMV

COO SpMV — a gather through the column indices

int j = blockIdx.x * BLK + threadIdx.x;
if (j < nnz)
    atomicAdd(&y[rowidx[j]],
              val[j] * x[colidx[j]]);   // random gather on x

Which entries of x are hot depends on the input, so hot words are shared by a random number of warps. There is no regular structure to tile.

Size mattersThe gap appears only once x (16.8 MB) outgrows the L2 cache. At n = 220 the same change gives just 1.6×.
Fix the data, not the kernelReorder the matrix so nonzero columns sit in a band near the diagonal. A bandwidth-reducing permutation (e.g. reverse Cuthill–McKee) does this. The kernel is unchanged.
Demorandom_hot/spmv_naive.cu → spmv_opt.cu, 4.19 M × 4.19 M with 33.5 M nonzeros: 4.167 → 0.887 ms (4.70×).
cuThermo (arXiv:2507.18729); parallel-demos, RTX A4500.
Part D
False Sharing

False Sharing on Global Memory

The trapA warp's accesses to different words of one sector coalesce into one 32 B transaction. The same sector accessed by different warps cannot be coalesced. A sector whose 8 words are each warp-private costs 8 sector transactions instead of 1.
Figures: cuThermo (Zhao et al., arXiv:2507.18729).

False Sharing — GEMM

Naive — threadIdx.x feeds the row of C

size_t C_row_idx = blockIdx.x * blockDim.x + threadIdx.x;
size_t C_col_idx = blockIdx.y * blockDim.y + threadIdx.y;
Fixed — the two lines swapped

size_t C_col_idx = blockIdx.x * blockDim.x + threadIdx.x;
size_t C_row_idx = blockIdx.y * blockDim.y + threadIdx.y;

Inner loop for both: sum += A[C_row_idx*lda + k] * B[k*ldb + C_col_idx];

In the naive kernel, warp w has threadIdx.y = w, so its column is fixed. Eight warps each take one word of the same sector of B and C.

FixSwap the thread-to-index mapping so threadIdx.x runs along the contiguous dimension. A warp then reads 32 consecutive words: 4 sectors, one warp.
Demofalse_sharing/gemm_naive.cu → gemm_opt.cu: 12.613 → 1.550 ms (8.14×).
cuThermo (arXiv:2507.18729); leimao/CUDA-GEMM-Optimization; parallel-demos, RTX A4500.
Part E
Misalignment

Misaligned Memory Requests

  • Top: a warp's 32 floats (128 B) start on a sector boundary and fill exactly 4 sectors.
  • Bottom: the request starts 4 words late. The warp needs 5 sectors instead of 4; sectors 00 and 04 are half-used and waste L1.
Figures: cuThermo (Zhao et al., arXiv:2507.18729).

Misalignment — Row Pitch

Row-scale kernel over a 2-D array

size_t idx = (size_t)r * pitch + c;
y[idx] = x[idx] * 2.0f + 1.0f;

// host side
pitch = nx;                  // naive: 1001 floats
pitch = ((nx + 7) / 8) * 8;  // fixed: 1008 floats

With 1001-float rows, each row starts one float further off a 32 B boundary, so a warp's 128 bytes straddle 5 sectors instead of 4.

FixPad the row pitch to a multiple of 32 B so every row starts on a sector boundary. cudaMallocPitch does this for you. Cost: 0.7% more memory.
Demomisalignment/rowscale_naive.cu → rowscale_opt.cu: sectors per request 4.28 → 3.43 (−24.6%).
But the time is unchangedMisalignment adds L1↔L2 traffic, not DRAM traffic, and this kernel is DRAM-bandwidth-bound.
cuThermo (arXiv:2507.18729); parallel-demos, RTX A4500.
Part F
Strided Access

Strided Memory Access

Consecutive threads access words spaced a fixed stride apart instead of contiguous words.

  • Only word 0 of each sector is used; 7 of 8 words are never touched
  • 7/8 of every sector transaction is wasted
  • That word is touched by 8 distinct warps, so coalescing does not apply
  • The unused words also fill L1, crowding out other data
Real case: Gram-SchmidtGRAMSCHM kernel3 reads q[i*NJ+k], so successive accesses are a full row apart. Transposing the indices of q lets a warp read adjacent words.
Figure: cuThermo (Zhao et al., arXiv:2507.18729).

Strided Access — Vector Add

Naive — a scattered (but complete) index mapping

int t = blockIdx.x * blockDim.x + threadIdx.x;
int chunk = n / STRIDE;                      // STRIDE = 32
int i = (t % chunk) * STRIDE + (t / chunk);
if (i < n) c[i] = a[i] + b[i];
Fixed — identity mapping

int i = blockIdx.x * blockDim.x + threadIdx.x;
if (i < n) c[i] = a[i] + b[i];

In the naive kernel adjacent lanes land 128 bytes apart: one useful word per 32 B sector, so 7/8 of every transaction is wasted. Both versions compute the same result.

FixMap adjacent threads to adjacent words, by changing the index or the data layout.
Demostrided/vadd_naive.cu → vadd_opt.cu: one line changed. 3.721 → 0.353 ms (10.5×).
cuThermo (arXiv:2507.18729); parallel-demos, RTX A4500.
Part G
Abuse of Shared Memory

When Shared Memory Is Not Shared

Each word of this shared-memory sector is touched by exactly one warp. The whole sector is touched by one warp or a few, depending on the application.

Why it hurtsShared memory is carved out of the same on-chip storage as L1. Space spent on data no other warp reads shrinks L1 for everything else. It also adds extra load, store, and synchronization instructions.
The purpose of shared memoryShorten the latency of data that is reused, by several threads or warps of the block. Words with temperature 1 defeat that purpose.
Figure: cuThermo (Zhao et al., arXiv:2507.18729).

Abuse of Shared Memory — Three Cases

Case 1: Thread-localA word touched by only one thread: thread-private scratch, no sharing at all.
Fix: keep it in registers, which also frees L1.
Case 2: Warp-localWords each touched by only one warp: no cross-warp reuse.
Fix: exchange inside the warp with __shfl_sync instead.
Case 3: Over-allocationShared memory that nobody reuses shrinks the L1 cache and can lower occupancy.
Fix: allocate only what earns cross-warp reuse.
Rule of thumbUse shared memory only when multiple warps reuse the data. Otherwise registers or __shfl_sync are cheaper and leave L1 intact.
Demosmem_abuse/ttm_naive.cu → ttm_opt.cu: a per-thread accumulator moved from __shared__ to registers, returning 16 KB/block to L1. 0.0745 → 0.0662 ms (1.13×).
cuThermo (arXiv:2507.18729); parallel-demos, RTX A4500.
Part H
Bank Conflicts

Shared Memory = Parallel Data Cache (Banks)

bank independent shared-memory port

Shared memory is divided into 32 equally-sized banks (Bank 0 … 31). Each bank delivers 32 bits per clock; successive 32-bit words map to successive banks. The warp is 32 threads and the number of banks is also 32, so a warp can read 32 distinct banks in one transaction. (historical: G80/GT200 had only 16 banks.)

Bank conflict Two threads access the same bank but different addresses → accesses are serialized.
CUDA C++ Best Practices Guide.

Bank Access Patterns

Bank of address = word_index % 32. For bank = thread*stride % 32:

Stride 1thread i → bank i
No conflict
Random 1:1 permutationeach thread a distinct bank
No conflict
Stride 2banks 0,2,4,… reused
2-way conflict
Stride 8 Many threads collapse onto few banks → heavy conflict (8-way), accesses fully serialized.
CUDA C++ Best Practices Guide.

Fast & Slow Paths

Fast Path 1 All threads access different banks → one cycle, full throughput.
Fast Path 2 All threads access the same address → hardware broadcast, no conflict.
Slow Path Multiple threads → same bank, different addresses → accesses serialized.
CostAn N-way conflict takes N times as long as a conflict-free access.
CUDA C++ Best Practices Guide.

shared-memory access

Rule Odd stride s (coprime with 32) → maps the 32 threads onto a permutation of the 32 banks → conflict-free. Even s shares factors with 32 → conflicts.

Occupancy — Block & Thread Slots (historical example, G80: 768 thread slots)

Works
  • 8 blocks × 96 threads = 768 ✓
  • 4 blocks × 192 threads = 768 ✓
Does NOT work
  • 8 blocks × 192 threads = 1536
  • Exceeds the 768 thread-slot limit ✗

The binding limit is whichever resource runs out first; here, thread slots. The method is unchanged today; only the numbers grow (2048 thread slots and 32 resident blocks/SM on V100–H100).

CUDA C++ Programming Guide.

Occupancy — Registers & the Cliff (historical example, G80)

G80 has 8192 registers/SM. Blocks of 256 threads. A modern SM has 64K registers, but the same cliff appears at its own thresholds.

10 regs / thread
  • \( 8192 / (256 \times 10) = 3.2 \Rightarrow 3 \) blocks
  • 3 × 256 = 768 threads (full!)
11 regs / thread
  • \( 8192 / (256 \times 11) = 2.9 \Rightarrow 2 \) blocks
  • 2 × 256 = 512 threads
Performance cliff One extra register/thread drops occupancy 768 → 512. More registers → less TLP. A small increase in resource use can sharply cut parallelism, unless the extra resources hide global-memory latency.
CUDA C++ Programming Guide.

Part J
Redundant Memory Instructions

Redundant Memory Instructions

DefinitionA memory instruction is redundant if it loads or stores an address whose value has already been loaded or stored, with no intervening update to that location.

RedSan checks each thread’s accesses against three rules:

DeadStoreA store to an address is followed by another store to it from the same thread — the first value is never used.
DeadLoadA load from an address is followed by another load of it from the same thread — the value was already in hand.
LoadAfterStoreA load immediately follows a store to the same address from the same thread — it reads back what was just written.

Consecutive writes by different threads to one address are not counted: they do not necessarily mean wasted work.

Why it mattersThese instructions survive in fully optimized binaries. Removing them gave up to 6.27× speedup and 3.00× fewer memory instructions.

Y. Zhao, Y. Hao, Z. Li, S. Jiao, X. Liu, J. Li, “RedSan: Redundant Memory Instruction Sanitizer for GPU Programs,” SC ’25 — §2 (definition), §4.1 (rules), abstract (results).

Why Doesn’t the Compiler Remove Them?

Four root causes in the source code, found across PolyBench, Rodinia, DARKNET, LULESH and PASTA:

PatternWhat blocks the optimizationExample
Duplicated accesses without __restrict__The compiler cannot prove that two pointers never alias, so it keeps every load and store.DARKNET avg-pool; PolyBench 2mm, gemm
Loop invariant within branchesAn invariant access sits under an input-dependent if. The path is unknown at compile time, so even __restrict__ does not help.Sparse matrix multiply (SpGEMM)
Outdated algorithm implementationCode written for older GPUs, e.g. a volatile shared-memory reduction where warp shuffles need no memory instructions.LULESH
Inefficient algorithm designShared memory holds values that only one thread touches: extra loads and stores, and less L1 for everything else.Rodinia backprop; PASTA

Y. Zhao, Y. Hao, Z. Li, S. Jiao, X. Liu, J. Li, “RedSan: Redundant Memory Instruction Sanitizer for GPU Programs,” SC ’25 — §2.1–2.4, §3.2, §7.

Example — A Store That Should Happen Once

DARKNET forward_avgpool_layer_kernel

int out_index = (k + c*b);   // fixed for this thread
output[out_index] = 0;
for (i = 0; i < w*h; ++i) {
  int in_index = i + h*w*(k + b*c);
  output[out_index] += input[in_index];
}
output[out_index] /= w*h;
PTX of the unrolled loop (excerpt)

ld.global.f32  %f10, [%rd15];
add.f32        %f11, %f10, %f23;
st.global.f32  [%rd2], %f11;    // dead store
ld.global.f32  %f12, [%rd15+4];
add.f32        %f13, %f12, %f11;
st.global.f32  [%rd2], %f13;    // dead store
...
DiagnosisThe running sum already lives in a register. But input and output might alias, so every iteration still writes output[out_index] back — a DeadStore each time.
FixAccumulate in a local float sum and store it once, or mark the pointers __restrict__. Result: 2.55× faster, 1.96× fewer memory instructions.

Y. Zhao, Y. Hao, Z. Li, S. Jiao, X. Liu, J. Li, “RedSan: Redundant Memory Instruction Sanitizer for GPU Programs,” SC ’25 — Listings 1 and 3, §2.1, Table 1.

Pitfall — __restrict__ Is a Per-Thread Promise

One block of 32 threads, optimized build

__global__ void foo(float * __restrict__ data, int n) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (i > 0 && i < n - 1) {
    for (int j = 0; j < n; j++) {
      float temp = data[i-1];
      __threadfence();
      data[i] += temp;
      __threadfence();
} } }
What goes wrongWithin one thread, data[i-1] and data[i] never overlap, so the compiler loads data[i-1] once and reuses the register. But thread i−1 keeps updating data[i-1]. This thread keeps adding a stale value — even with __threadfence().
RuleDo not put __restrict__ on a pointer that other threads load and store concurrently. The CUDA documentation does not warn about this case.

Y. Zhao, Y. Hao, Z. Li, S. Jiao, X. Liu, J. Li, “RedSan: Redundant Memory Instruction Sanitizer for GPU Programs,” SC ’25 — §3.1, Listing 4 (observed with both NVCC and Clang).

Back to Matmul — Why pValue Matters

Our naive kernel (Session 1)

float pValue = 0;
for (int k = 0; k < width; k++)
    pValue += devM[row*width + k]
            * devN[k*width + col];
devP[row*width + col] = pValue;

Per iteration: 2 loads. One store at the end.

PolyBench 2mm, mm2_kernel1

tmp[i * NJ + j] = 0;
for (k = 0; k < _PB_NK; k++)
    tmp[i * NJ + j] += alpha
        * A[i * NK + k] * B[k * NJ + j];

Per iteration: 2 loads + 1 dead store to tmp.

MeasuredMoving the sum into a register takes the loop from 3 memory instructions per iteration to 2: 100.70M → 67.17M memory instructions (1.50×), and 4.32× fewer cycles.
ConnectionThe register accumulator in our naive and tiled kernels is exactly fix #2. The lab looks for kernels where it is missing.

Y. Zhao, Y. Hao, Z. Li, S. Jiao, X. Liu, J. Li, “RedSan: Redundant Memory Instruction Sanitizer for GPU Programs,” SC ’25 — Table 1 (2mm kernel1), §7.1.

1 · PreprocessExtract the kernels from the fully optimized binary; optionally sample only chosen kernels. No source changes, no recompilation.
2 · Collect onlineBinary instrumentation (NVBit) records every memory instruction per warp: PC, the 32 addresses, size, active mask, load/store and global/shared scope, block and thread ID.
3 · Analyze offlineA per-thread last-access table applies the three rules. Each PC gets a redundancy rate = redundant accesses / all accesses.
Redundancy rate of a PC= 1[0.5, 1)(0, 0.5)0
CategoryFullyPartiallySlightlyNon-redundant
WorkflowFix Fully Redundant PCs first. Map a PC back to a source line by recompiling with -lineinfo and profiling with Nsight Compute; unlike -G, it keeps the optimized code.

Wrap-Up — The Optimization Toolkit

Global memory
  • Coalesce global loads (fewest 32 B sectors per warp)
  • Count distinct warps per word and per sector
  • Hot spots → stage in shared memory
  • False sharing, strided → adjacent threads on adjacent words
  • Misalignment → align or pad to 32 B
Shared memory & resources
  • Thread- or warp-local data → registers or __shfl_sync
  • Avoid bank conflicts (odd strides)
  • Watch the occupancy cliff
  • Remove redundant loads and stores (keep per-thread values in registers)
  • Fix only what is on the critical path
