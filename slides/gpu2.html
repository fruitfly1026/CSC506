Device & Global Function Constraints

Recursion
  • Recursion on the device is OK (except very old G80)
  • Dynamic parallelism (a __global__ launching itself) requires compute capability ≥ 3.5
Not allowed inside device code
  • No static variables
  • No malloc (classic constraint)
Why Thousands of threads share the SM's tiny on-chip state — there is no per-thread stack big enough for arbitrary recursion or heap, so the model is deliberately restricted.

Math Functions & Intrinsics

Standard math (double / float overloads)

Host & device, IEEE-accurate:

sqrt rsqrt exp log sin cos tan sincos asin acos atan2 trunc ceil floor

A float and a double overload exist for each.
Intrinsics — device only
  • Faster, but less accurate
  • Prefixed with __
  • e.g. __expf, __sinf, __logf, __cosf
Use when speed matters and a few ulp of error is acceptable.

The Streaming Multiprocessor (SM)

SM streaming multiprocessor SP streaming processor (CUDA core)
A GPU is an array of SMs
  • Each SM contains many streaming processors (SPs)
  • One or more warp schedulers
  • Shared memory / L1 and a register file, all on-chip
Blocks are assigned to SMs; threads run as warps.
UIUC ECE498/AL & NVIDIA CUDA C Programming Guide.

The Warp — Unit of Scheduling

warp = 32 threadswarpSize built-in
What a warp is
  • 32 threads from one block, with consecutive threadIdx
  • Run on the same SM
  • The unit of thread scheduling — hardware schedules warps, not threads
Zero-overhead warp scheduling
  • Only one warp executes at a time
  • Warps whose next instruction's operands are ready are eligible
  • Eligible warps selected by priority
  • All 32 threads execute the same instruction (SIMT)

Interleaving Warps Hides Latency

When a warp stalls on a long-latency op (e.g. a global load), the scheduler switches to another ready warp — for free. The SM stays busy.

Key ideaGPUs hide latency with parallelism instead of reducing it with caches.
UIUC ECE498/AL.

Branch Divergence

All 32 threads of a warp share one program counter. If threads take different branches, the hardware runs both paths with lane masking.

divergent branch in a warp

if (threadIdx.x < 16) {
    // path A — lanes 0..15 active,
    //          lanes 16..31 masked off
    x = doA();
} else {
    // path B — lanes 16..31 active,
    //          lanes 0..15 masked off
    x = doB();
}
CostNot all ALUs do useful work while a path runs — the masked lanes idle.
Worst caseHeavy divergence can drop you to as low as 1/8 of peak throughput.
No divergence cost if all 32 lanes take the same branch.

In-class: Counting Warps

Q1A GT200 SM hosts 1024 threads. How many warps?
A: \( 1024 / 32 = 32 \) warps.
Q23 blocks × 256 threads — how many warps?
A: \( 3 \times 256 / 32 = 24 \) warps.
Q3A warp is 32 threads but an SM has only 8 SPs — what gives?
A: 8 threads enter the SPs per cycle, so it takes 4 cycles to dispatch a full warp.

In-class: Warps to Hide Latency

SetupA kernel has 1 global read (200 cycles) followed by 4 non-dependent mul/add ops. How many warps are needed to hide the read latency?
Work it out
  • Each op takes 4 dispatch cycles → 4 ops = \( 4 \times 4 = 16 \) cycles of independent work per warp
  • We must cover \( 200 \) cycles: \( 200 / 16 = 12.5 \)
  • Round up: \( \lceil 12.5 \rceil = \) 13 warps

Memory Hierarchy

UIUC ECE498/AL & NVIDIA CUDA C Programming Guide.

Registers

Per-thread, fast on-chip. The register file is split across all resident threads — so register use caps occupancy.

G80 budgetPer SM: 768 threads & 8K registers → \( 8192 / 768 = 10 \) registers/thread available.
Spill example
  • 11 regs × 256-thread blocks → \( 11 \times 256 = 2816 \) regs/block
  • \( 8192 / 2816 = 2 \) blocks → 512 threads → 16 warps
  • Fewer warps → less latency hiding
Special registersthreadIdx · blockIdx · blockDim · gridDim

Local Memory

What it is
  • Register / array spill space
  • Physically lives in global memory (off-chip)
  • Addressing resolved by the compiler
  • Stores are cached in L1 on SM 2.x+
Performance
  • Hurts via extra memory traffic + instruction count
  • But L1-contained spills are not always bad

Shared Memory

Per-block, fast on-chip, full-speed random access — the programmer-managed scratchpad.

G80 budgetPer SM: 16 KB shared, up to 8 blocks → \( 16/8 = 2 \) KB/block if fully occupied.
Occupancy exampleIf each block uses 5 KB → \( 16 / 5 = 3 \) blocks per SM (shared memory is the limiter).
This is the leverShared memory is what makes tiled matmul (Part E) fast — threads in a block cooperatively stage data on-chip.

Global & Constant Memory

Global memory
  • Long latency — 100s of cycles, off-chip
  • G80 86.4 GB/s, GT200 150 GB/s, up to 4 GB
  • Reads cached on 2.x+; writes invalidate the cache
Constant memory
  • Short latency / high bandwidth when all threads read the same location
  • Cached
  • Up to 64 KB

Synchronizing Threads

By the end you can…

  • Use __syncthreads() as a block barrier
  • Explain why it works only within a block
  • Avoid the conditional-barrier deadlock hazard

__syncthreads() — Block Barrier

A barrier within a block: a thread waits until all threads in the block reach the call before any continues.

classic barrier pattern

Mds[i] = Md[j];      // each thread loads
__syncthreads();     // wait for ALL loads
func(Mds[i], Mds[i+1]);   // now safe to read
                          // a neighbor's value
Use it whenThreads in a block produce data (into shared memory) that other threads in the same block will consume.
GuaranteeAfter the barrier, every shared-memory write made before it is visible to all threads in the block.

Barrier Walkthrough

Warps reach the barrier at different times; all continue only once the last warp arrives.

Same execution time helpsThreads doing similar work reach the barrier together → little waiting.
Only within a blockCross-block sync would break transparent scalability — blocks must run in any order, on any number of SMs.

Hazard: Conditional Barriers Deadlock

A barrier requires every thread in the block to reach it. Putting it inside a branch that only some threads take → the rest never arrive → hang.

deadlock — barrier in only one branch

if (cond) {
    __syncthreads();   // BAD: only some
}                      // threads reach it
fix — a barrier in BOTH branches

if (cond) {
    __syncthreads();   // all threads
} else {
    __syncthreads();   // reach a barrier
}
RuleEither all threads in the block execute a given __syncthreads(), or none do.
Part E
Tiled Matrix Multiply

Naive Multi-block Matmul

Each thread computes one element of P by streaming an entire row of M and column of N from global memory.

CUDA C — naive kernel

int col = blockIdx.x*blockDim.x + threadIdx.x;
int row = blockIdx.y*blockDim.y + threadIdx.y;
float pValue = 0;
for (int k = 0; k < width; k++)
    pValue += devM[row*width + k]
            * devN[k*width + col];
devP[row*width + col] = pValue;
CUDA C — launch

dim3 dimBlocks(TILE_WIDTH, TILE_WIDTH);
dim3 dimGrid(WIDTH/TILE_WIDTH,
             WIDTH/TILE_WIDTH);
MatrixMultiplyKernel
    <<<dimGrid, dimBlocks>>>(...);

The Bandwidth Bottleneck

Every pValue += does 2 global loads (4 B each) for 2 FLOPs — far too much memory traffic.

G80 numbers
  • Peak compute: 346.5 GFLOPS
  • That would need 1386 GB/s of bandwidth
  • But memory bandwidth is only 86.4 GB/s
ResultMemory caps you at \( \approx \) 21.6 GFLOPS (and ~15 in practice) — about 4% of peak.
FixWe must cut global-memory access — reuse data on-chip via shared memory.

The Tiling Idea

Break P into TILE_WIDTH × TILE_WIDTH tiles — one tile per block. Each phase:

  • Load a tile of M and a tile of N into shared memory
  • __syncthreads() — wait for the loads
  • Accumulate the partial dot product from the tiles
  • __syncthreads() — before overwriting the tiles next phase
UIUC ECE498/AL.

Tiled Kernel

CUDA C — shared-memory tiled matmul

__shared__ float sM[TILE_WIDTH][TILE_WIDTH];
__shared__ float sN[TILE_WIDTH][TILE_WIDTH];
int bx = blockIdx.x;  int by = blockIdx.y;
int tx = threadIdx.x; int ty = threadIdx.y;
int col = bx*TILE_WIDTH + tx;
int row = by*TILE_WIDTH + ty;
float pValue = 0;
for (int m = 0; m < width/TILE_WIDTH; m++) {        // m = phase index
    sM[ty][tx] = devM[row*width + (m*TILE_WIDTH + tx)];
    sN[ty][tx] = devN[col + (m*TILE_WIDTH + ty)*width];
    __syncthreads();                                 // 1: tiles fully loaded
    for (int k = 0; k < TILE_WIDTH; ++k)
        pValue += sM[ty][k] * sN[k][tx];
    __syncthreads();                                 // 2: done before overwrite
}
devP[row*width + col] = pValue;
Two barriers#1 after the loads so every thread sees the full tiles; #2 so no thread overwrites the tile before others finish reading it. width/TILE_WIDTH = number of phases.

Choosing TILE_WIDTH

Bounded by max threads/block (G80/GT200 = 512, Fermi+ = 1024) and shared memory per block.

G80 shared-memory limit
  • 16 KB/SM, ≤ 8 blocks → 2 KB/block
  • \( 16 \times 16 \times 4\,\text{B} = 1 \) KB each for sM, sN → 2 KB
  • So TILE_WIDTH = 16
  • Larger tile → fewer resident blocks
Payoff
  • Each value reused TILE_WIDTH times → global access cut by 16×
  • G80 now supports 345.6 GFLOPS — near the 346.5 peak

First-order Sizing

TILE_WIDTH = 16
  • \( 16 \times 16 = 256 \) threads/block
  • A \( 1024 \times 1024 \) output P → \( 64 \times 64 = 4096 \) blocks
  • Each block does 512 global loads (per phase, both tiles) for 8192 mul/add
Bottom lineCompute now dominates memory — the global-memory bandwidth is no longer the limiter. Tiling turned a 4%-of-peak kernel into a near-peak one.
