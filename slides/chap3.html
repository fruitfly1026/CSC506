Chapter 3 is the "how do I actually parallelize a program" chapter. The goal: given source code, without knowing the algorithm, find parallel tasks; decide which variables each thread can touch; and coordinate threads with synchronization. We work mostly in the shared-memory model and express the result in OpenMP and pthreads.

Module 3.1
Parallelism & Dependence Analysis

By the end you can…

  • Identify true, anti, and output dependences in source code
  • Distinguish loop-carried from loop-independent dependences
  • Draw an Iteration-space Traversal Graph (ITG) and a Loop-Carried Dependence Graph (LDG)

The Premise of Code Analysis

Goal Given code — without knowing the algorithm — find the parallel tasks. Our main lever is loop dependence analysis.

Notation we'll use throughout:

  • S = a statement in the source code; S[i,j,…] = that statement in loop iteration [i,j,…]
  • S1 then S2 means S1 happens before S2
S1 T S2 — trueS1 writes a location later read by S2 (read-after-write). The real producer→consumer flow.
S1 A S2 — antiS1 reads a location later written by S2 (write-after-read).
S1 O S2 — outputS1 and S2 write the same location (write-after-write).

Anti & output are "name" dependences — they exist because of reuse of a storage location, not real data flow.

Worked Example: Spotting Dependences

Source

S1: x = 2;
S2: y = x;
S3: y = x + z;
S4: z = 6;

Trace each variable: who writes it, who reads it, in what order.

DependenceTypeWhy
S1 T S2trueS1 writes x, S2 reads it
S1 T S3trueS1 writes x, S3 reads it
S3 A S4antiS3 reads z, S4 writes it
S2 O S3outputboth write y
Grouping Merge S1,S2 → S12 and S3,S4 → S34: the relation collapses to S12 T S34 and S12 O S34.

Loop-Carried vs. Loop-Independent

Loop-carried Dependence crosses iterations — remove the loop and it disappears. This is what blocks parallelism.
Loop-independent Dependence lives within one iteration — it survives even if the loop is removed.
A 1-D loop

for (i = 1; i < n; i++) {
  S1: a[i] = a[i-1] + 1;   // S1[i] T S1[i+1]  -> loop-carried
  S2: b[i] = a[i];         // S1[i] T S2[i]    -> loop-independent
}

a[i] depends on a[i-1] from the previous iteration (carried); b[i] uses a[i] from the same iteration (independent).

Which Loop Carries the Dependence?

Carried on the j loop

for (i = 1; i < n; i++)
  for (j = 1; j < n; j++)
    S3: a[i][j] = a[i][j-1] + 1;

S3[i,j] T S3[i,j+1] → carried on j. No carried dependence on the i loop → i is parallel.

Carried on the i loop

for (i = 1; i < n; i++)
  for (j = 1; j < n; j++)
    S4: a[i][j] = a[i-1][j] + 1;

S4[i,j] T S4[i+1,j] → carried on i. No carried dependence on the j loop → j is parallel.

The payoff A loop level with no loop-carried dependence is fully parallel. Finding that level is the whole game.

Iteration-Space Traversal Graph (ITG)

The ITG draws the happens-before order of the iteration space.

  • Node = a point [i,j] in the iteration space
  • Directed edge = the next point visited after the current one
Example

for (i=1; i<4; i++)
  for (j=1; j<4; j++)
    S3: a[i][j]=a[i][j-1]+1;

Row-major traversal: finish a row of j, then drop to the next i.

ITG = traversal order, not dependences.

Loop-Carried Dependence Graph (LDG)

The LDG draws the dependences (true/anti/output), not the traversal order.

  • Node = a point in the iteration space
  • Directed edge = a dependence, labeled by type

For the same loop, the only relation is S3[i,j] T S3[i,j+1] — a horizontal true-dependence chain along each row. No vertical edges → the i rows are independent.

Each row is a serial chain; rows are parallel.

A Denser Example: 5-Point Stencil

Loop nest

for (i=1; i<=n; i++)
  for (j=1; j<=n; j++)
    S1: a[i][j] = a[i][j-1] + a[i][j+1]
               + a[i-1][j] + a[i+1][j];

True: S1[i,j] T S1[i,j+1], S1[i,j] T S1[i+1,j]
Anti: S1[i,j] A S1[i+1,j], S1[i,j] A S1[i,j+1]
Output: none

NoteEach grid edge represents both a true and an anti dependence → neither full rows nor full columns are independent.
Edges go right and down — a dependence "wavefront."

1. What are the three types of dependences?

True (producer→consumer, RAW), anti (WAR), and output (WAW).

2. Which dependence types are tied to loop structure?

Loop-carried (across iterations) and loop-independent (within one iteration). Only loop-carried dependences block iteration-level parallelism.

3. ITG vs. LDG — what does each show?

The ITG shows the traversal (happens-before) order; the LDG shows the actual dependences between iteration points.
Module 3.2
Loop-Level Parallelism

By the end you can…

  • Read an LDG to find independent tasks and rewrite the loop to expose them
  • Tell apart DOALL, DOACROSS, function, and DOPIPE parallelism
  • Use post/wait synchronization to parallelize loops with carried dependences

Finding Tasks Across Iterations

A dependence must be obeyed (especially true dependences) — but gaps in the LDG are opportunities.

Stride-2 dependence

for (i=2; i<=n; i++)
  S: a[i] = a[i-2];

a[i] depends only on a[i-2] → even and odd indices never touch.

Split into two independent tasks

for (i=2; i<=n; i+=2)   // even chain
  S: a[i] = a[i-2];
for (i=3; i<=n; i+=2)   // odd chain
  S: a[i] = a[i-2];

✓ Two independent chains → run them on two threads.

DOALL When a loop level has no loop-carried dependence, every iteration is independent — a DOALL loop, the gold standard. The inner j loop of a[i][j]=a[i][j-1]+1 gives n independent tasks (one per i).

Wavefront: Parallel Anti-Diagonals

In the 5-point stencil, each edge is a true+anti dependence — but within any anti-diagonal the nodes do not depend on one another.

IdeaIterate over anti-diagonals (serially), parallelizing the points within each one.
Restructured shape

// 2n-1 anti-diagonals, computed in order
for (i = 1; i <= 2*n-1; i++) {
  // count points on this anti-diagonal,
  // find its first (row,col)
  for_all (k = 1; k <= points; k++) {
    a[row][col] = ...;   // independent!
    row--; col++;
  }
}
Shaded bands = independent anti-diagonals.

Expressing the Wavefront in OpenMP

Parallelize the inner (within-anti-diagonal) loop; row/col are computed per thread.

OpenMP — parallel inner loop

for (i = 1; i <= 2*n - 1; i++) {          // serial over anti-diagonals
  int points, row, col;
  if (i <= n) { points = i;     row = i; col = 1; }
  else        { points = 2*n-i; row = n; col = i-n+1; }

  #pragma omp parallel for default(shared) \
                           private(k) firstprivate(row, col)
  for (int k = 1; k <= points; k++) {
    a[row - (k-1)][col + (k-1)] = /* stencil update */ ;
  }
}
Why firstprivate Each thread needs its own initialized copy of row/col for the anti-diagonal; deriving the index from k keeps iterations independent.

DOACROSS: Parallelizing a Carried Dependence

Sequential — carried on a[]

for (i=1; i<=N; i++) {
  S: a[i] = a[i-1] + b[i]*c[i];
}

S[i] T S[i+1] looks fully serial — but b[i]*c[i] has no carried dependence.

Split out the independent work

for (i=1; i<=N; i++)        // DOALL
  S1: temp[i] = b[i]*c[i];
for (i=1; i<=N; i++)        // serial
  S2: a[i] = a[i-1] + temp[i];

First loop parallel; time N·(TS1+TS2) → TS1+N·TS2. But temp[] adds storage.

DOACROSS Better: keep one loop and let iterations overlap, guarding only the carried part with point-to-point synchronization.

Post / Wait Synchronization

post(x)Increments the counter m(x) named by x.
wait(x)Blocks while m(x) ≤ 0; when m(x) > 0 it unblocks and decrements.

Names can be structured: post(i+1) / wait(i) chains successive iterations.

DOACROSS with post/wait

post(0);
#pragma omp parallel for ordered
for (i=1; i<=N; i++) {
  S1: temp = b[i]*c[i];   // independent
  wait(i-1);              // need a[i-1]
  S2: a[i] = a[i-1] + temp;
  post(i);                // release a[i]
}

Time → TS1 + N·TS2, and temp is now per-thread, not per-iteration.

post/wait is the conceptual primitive; in OpenMP the natural realizations are an `ordered` clause or explicit atomic counters. The point is overlap: the independent S1 of iteration i runs while the dependent S2 chain catches up.

Function Parallelism via Loop Distribution

One loop, several statements

for (i=0; i<n; i++) {
  S1: a[i] = b[i+1]*a[i-1];
  S2: b[i] = b[i]*coef;
  S3: c[i] = 0.5*(c[i]+a[i]);
  S4: d[i] = d[i-1]*d[i];
}

Carried: S1[i] A S2[i+1] · Loop-indep: S1[i] T S3[i] · S4 is independent of S1–S3.

After loop distribution

for (i=0; i<n; i++) {     // task A
  S1: a[i] = b[i+1]*a[i-1];
  S2: b[i] = b[i]*coef;
  S3: c[i] = 0.5*(c[i]+a[i]);
}
for (i=0; i<n; i++)       // task B
  S4: d[i] = d[i-1]*d[i];

✓ Each loop is a parallel task — run A and B concurrently.

S1[i] A S2[i+1] only requires all S1's finish before any S2 of a later iteration — preserved within task A's order.

Function vs. Data Parallelism

Function parallelism
  • Modest degree — does not grow with input size
  • Hard to load-balance
  • Natural for pipelines: video encode/decode, polygon rendering
Data parallelism
  • Degree scales with data size
  • Most scalable programs are data parallel
  • Use function parallelism to fill in when data parallelism is limited
Rule of thumb Reach for data parallelism (DOALL) first; layer function/DOPIPE parallelism on top when DOALL alone doesn't fill the machine.

DOPIPE: Software Pipelining a Loop

Sequential

for (i=2; i<=N; i++) {
  S1: a[i] = a[i-1] + b[i];
  S2: c[i] = c[i] + a[i];
}

Carried: S1[i-1] T S1[i] (S1 is a serial chain).
Loop-indep: S1[i] T S2[i] (S2 follows S1 same iteration).

OpportunityS2 has no carried dependence — it can run a pipeline stage behind S1.
DOPIPE — two pipelined stages

for (i=2; i<=N; i++) {    // stage 1
  a[i] = a[i-1] + b[i];
  post(i);
}
for (i=2; i<=N; i++) {    // stage 2
  wait(i);
  c[i] = c[i] + a[i];
}

Stage 2 consumes a[i] as soon as stage 1 posts it — the two stages overlap like a pipeline.

Algorithm-Level Parallelism

By the end you can…

  • Explain why code analysis alone misses parallelism the algorithm allows
  • Apply red-black (checkerboard) ordering to expose fully parallel sweeps
  • Reason about asynchronous (chaotic) relaxation and its trade-offs

When Code Analysis Is Too Pessimistic

Code analysis assumes the given traversal order is sacred. But the ITG sometimes imposes unnecessary serialization.

Ocean / stencil At each sweep, each point is updated from its neighbors. Any order within a sweep is just an approximation — different orderings simply converge faster or slower.

So we are free to change the ordering to expose parallelism.

The Gauss-Seidel-style sweep

for (I=1; I<=N; I++)
  for (j=1; j<=N; j++) {
    S1: temp = A[I][j];
    S2: A[I][j] = 0.2*(A[I][j]+A[I][j-1]
                 + A[I-1][j]+A[I][j+1]+A[I+1][j]);
    S3: diff += abs(A[I][j]-temp);
  }

As written, the 5-point coupling serializes the sweep into a wavefront.

Red-Black Coloring

Color the grid like a checkerboard. A red point's four neighbors are all black, and vice-versa.

Key fact Within one sweep, there is no dependence between red and black points — so each color sweep is fully parallel.
Restructured algorithm

while (!converged) {
  doall (red points)   compute;   // DOALL
  barrier;                        // wait for red
  doall (black points) compute;   // DOALL
  barrier;
}
Two fully parallel half-sweeps per iteration.

Going Further: Asynchronous Execution

If the algorithm tolerates it, we can simply ignore dependences within a sweep — threads read whatever value of a neighbor is currently available.

UpsideNo synchronization inside a sweep → maximum parallelism, no barrier stalls.
DownsideThe parallel program is now nondeterministic — results are timing-dependent, and convergence behavior changes.
The spectrum
  • Strict order — wavefront, limited parallelism, deterministic
  • Red-black — fully parallel sweeps, deterministic, an exact reordering
  • Asynchronous — most parallel, nondeterministic, only valid if the numerics tolerate it

Choosing a point on this spectrum is an algorithm decision, invisible to pure code analysis.

Variable Scope & OpenMP

Determining Variable Scope

Specific to the shared-memory model: given the parallel tasks, decide how each variable is used across tasks.

Read-onlyOnly read by all tasks. Safe to share.
R/W non-conflictingRead and/or written by only one task. Also safe to share.
R/W conflictingWritten by one task and read/written by another — the dangerous case.
Example — task = each "for i" iteration

for (i=1; i<=n; i++)
  for (j=1; j<=n; j++) {
    S2: a[i][j] = b[i][j] + c[i][j];
    S3: b[i][j] = a[i][j-1] * d[i][j];
  }

Read-only: n, c, d · R/W non-conflicting: a, b · R/W conflicting: i, j (the loop indices).

Privatization

Privatization Convert a shared variable into a per-thread private copy to remove a conflict. Goal: turn R/W conflicting into R/W non-conflicting.

A conflicting variable is privatizable if:

  • In program order, each task writes it before reading it, and
  • The values for different tasks are known ahead of time (so private copies can be initialized).
ConsequenceThe conflict disappears once the variable is privatized — one copy per thread (not per task).
Special case: registers A register-allocated scalar is inherently private — each core has its own register file.

In the previous example, i and j are conflicting but privatizable → i[ID], j[ID] per thread.

Reduction

Reduction A special privatization where each thread accumulates into a private partial result, then all partials are merged into the shared result at the end.
Classic example — summing an array

double sum = 0.0;
#pragma omp parallel for reduction(+:sum)
for (i = 0; i < n; i++)
    sum += a[i];

Each thread keeps a private sum; OpenMP combines them with + at the join.

Reducibility criteria — the update order must not matter, so the operator must be:

\( u \;\text{op}\; v = v \;\text{op}\; u \quad\text{(commutative)} \)
\( (u \;\text{op}\; v)\;\text{op}\; w = u\;\text{op}\;(v\;\text{op}\;w)\;\text{(assoc.)} \)

Examples: +, *, logical AND/OR, min/max. The accumulated scalar is the reduction variable.

CautionFloating-point + is not perfectly associative — reduction can change the last bits of a result.

Putting Scope into OpenMP

CategoryOpenMP clause
Privatizableprivate
Read-onlyshared
R/W non-conflictingshared
Reduction variablereduction(op:var)
Other conflictingshared + lock/atomic

private further splits into firstprivate (init from the outside value) and lastprivate (copy the final value out).

Scoping the "for i" example

#pragma omp parallel for \
        default(none) \
        shared(n, a, b, c, d) \
        private(i, j)
for (i=1; i<=n; i++)
  for (j=1; j<=n; j++) {
    a[i][j] = b[i][j] + c[i][j];
    b[i][j] = a[i][j-1] * d[i][j];
  }

Shared: n, c, d, a, b · Private: i, j. Using default(none) forces you to scope every variable on purpose.

Module 3.5
Synchronization & pthreads

By the end you can…

  • Name the three synchronization primitives and when to use each
  • Use a lock to protect a critical section and explain granularity trade-offs
  • Explain why load balance dominates barrier performance, and what gang scheduling fixes

Three Synchronization Primitives

Point-to-point A post()/wait() pair (shared memory) — or send()/recv() in message passing. Orders two specific threads.
Lock (mutex) Mutual exclusion: only one thread in the locked region at a time.
Barrier A point no thread passes until all threads have arrived. Global event sync.
Match the tool to the need Producer→consumer ordering? Point-to-point. Protecting a shared update? Lock. Phase boundary (like red→black)? Barrier.

Locks: Protecting a Critical Section

Race — unsynchronized

// inside a parallel region
for (i=start; i<end; i++)
    sum = sum + a[i];   // lost updates!

✗ Concurrent read-modify-write on the shared sum → lost updates.

Correct — with a lock (pthreads)

pthread_mutex_t x = PTHREAD_MUTEX_INITIALIZER;
for (i=start; i<end; i++) {
    pthread_mutex_lock(&x);
    sum = sum + a[i];
    pthread_mutex_unlock(&x);
}

✓ Only one thread updates sum at a time.

GranularityLocking every iteration serializes the loop — prefer a per-thread partial sum (a reduction!) and one lock at the end.
Open questionsWhat granularity to lock? How to build a lock that is both correct and fast? (later chapters)

Barriers & Load Balance

BarrierGlobal event sync — every thread blocks until the last one arrives, then all proceed.
Cost = slowest thread A barrier's wall-clock time is set by the slowest thread, so load balance is critical.

Artificial imbalance also arises from context switching — a thread swapped out mid-region stalls everyone at the barrier. Mitigate with gang scheduling (co-schedule all of a job's threads together).

Imbalance → wasted cycles at the barrier.

1. What synchronization primitives does a shared-memory system support?

Lock (mutual exclusion), barrier (global event), and point-to-point (e.g. post/wait).

2. Why is load balancing important when barriers are used?

A parallel region's execution time is determined by the slowest thread — imbalance leaves everyone else idle at the barrier.

3. What does gang scheduling solve — and not solve?

It prevents the no-forward-progress stall when a thread is switched out, and frees CPUs for other work during a switch-out. It does not remove inherent load imbalance.
