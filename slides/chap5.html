Why Caches Exist

Main-memory latency used to be a few clock cycles. Today it is several hundred cycles.

  • Keep small but fast storage near the processor — a cache
  • Works because programs have temporal and spatial locality
  • Hit rates of 70–95% are not uncommon
The betStore the few things you use a lot close by; recently or nearby-touched data is likely to be touched again soon.

A Cache Is a Table

Placement policyWhich line holds a block fetched from the lower level? A block lands in one of the ways of its set.
Replacement policyWhen the set is full, which block in the set is evicted to make room?

These two policies are what make a cache a cache — everything else is just a table.

Three Associativities

One spectrum Direct-mapped is a 1-way set-associative cache; fully-associative is a single set with all the ways. Everything in between is N-way set-associative.

Trade-offs in Associativity

Fully associative

  • Flexible placement anywhere
  • Usually a lower miss rate
ButPower hungry — must search the entire cache to find a block.

Direct mapped

  • Rigid: one possible location
  • Usually a higher miss rate
ButPower efficient — search only one place.
Miss rateThe fraction of cache accesses that do not find the block. Set-associativity is the practical middle ground real caches choose.

Mapping a Block to a Set

\( setIdx = blkAddr \bmod numSets \)

If numSets is a power of 2, the modulo is free — just take the low index bits.

  • Index bits sit just above the block-offset bits
  • e.g. 2048 sets, 64-byte blocks: offset = low 6 bits, index = next 11 bits (\(2^{11}=2048\)), the rest is tag

Other Mapping Functions

Prime moduloUse a prime number of sets. Resistant to non-uniform set utilization caused by strided accesses (which would otherwise hammer a few sets).
XOR indexingXOR several address bit-fields together to randomize the set mapping cheaply — spreads accesses without an expensive divide.
Why bother A power-of-two modulo is cheap but can leave sets idle under regular access patterns. Prime / XOR hashing trades a little hardware for better set utilization.

Locating a Block (Step by Step)

  1. Index → map address to a set
  2. Read out the tags from the set
  3. Compare address tag to stored tags — match = hit, else miss
  4. Read out the data from the set
  5. On a hit, select the block from the way that hit
  6. Use the offset to pick the byte/word
  7. Return it to the processor

Replacement Policy

Which block to evict to make room for a new one?

LRUEvict the least recently used block. Usually performs well.
Bad when the working set is just slightly larger than the cache; expensive at high associativity.
FIFOEvict the earliest block brought in, regardless of use. Cheap, but ignores recency.
Pseudo-LRUApproximates LRU. Behaves like LRU for the more-recently-used half. Cheaper — keep a tree of bits recording the recent path.
Cost vs. quality True LRU is \(O(\text{ways}^2)\) state; pseudo-LRU is \(O(\text{ways})\). High-associativity caches almost always use an approximation.

LRU: Matrix Implementation

  • Give each way a row and a column of a bit matrix
  • On a hit in way k: set row k to 1, then clear column k to 0
  • The count of 1's in a row = that way's recency rank (more 1's = more recently used)
  • Evict the way whose row has the fewest 1's

State \(\propto\) ways² — exact, but it doesn't scale.

Pseudo-LRU: Tree of Bits

  • True LRU is \(O(\text{ways}^2)\) — too expensive at high associativity
  • Pseudo-LRU keeps one bit per internal tree node: \(O(\text{ways})\)
  • Each access flips the bits along its path to point away from itself
  • To find a victim, walk the tree following the bits to a leaf
Good enoughTracks LRU well for the most-recently-used half of a set at a fraction of the cost.

Write Policy: Write-Through vs. Write-Back

When is a new value propagated to the lower level?

Write-throughPropagate immediately on every write. Simple; keeps lower level current.
Write-backPropagate only on eviction. Multiple writes to a block → one propagation, not many. Conserves bandwidth.
Typical L1Write-through — L1↔L2 bandwidth is plentiful; L1 can be protected by parity alone.
Typical L2Write-back — bandwidth to the (often off-chip) lower level is scarce, so save it.

Write Policy: Allocate vs. No-Allocate

Is a block brought into the cache on a write miss? (A read miss always allocates.)

Write-allocateFetch the block on a write miss, then write. Typical choice.
Write no-allocateWrite straight to the lower level; don't pull the block in.
Rationale (no-allocate)If a block will be overwritten completely, why fetch it first?
PitfallThe block may be read or written again soon — and larger blocks raise the odds of multiple partial writes. Usually write-allocate wins.

Module 5.1 — Review

1. In a 4-way cache, what do "set", "way", and "line" mean?

A set is a row selected by the index; a way is one of the 4 columns; a line is a single cell (one block's worth of storage).

2. For 2048 sets and 64-byte blocks, how many offset and index bits?

6 offset bits (\(2^6=64\)) and 11 index bits (\(2^{11}=2048\)); the remaining high bits are the tag.

3. Why is pseudo-LRU preferred to true LRU in big caches?

True LRU costs \(O(\text{ways}^2)\) state; pseudo-LRU is \(O(\text{ways})\) and tracks recency well enough.

Inclusion in Multi-Level Caches

Should a block in the upper (smaller) cache also live in the lower (larger) one?

InclusionAlways — every upper-level block is also in the lower level.
NINENot enforced — may or may not be present.
ExclusionNever duplicated — a block lives in exactly one level.
Why inclusion? An external (coherence) request only needs to check the lower level: if it's not there, the upper level can't have it either. Reduces tag contention at the busy upper level. (Value inclusion = the copies must also match.)

Enforcing Inclusion — and Its Cost

Protocol

  • A fetched block is placed in the lower level too, not just the upper level
  • When a lower-level block is replaced, probe the upper level and evict its copy as well (back-invalidation)
PitfallInclusion wastes capacity — the lower level re-stores what the upper level already holds. Worse in multicore.

e.g. AMD Barcelona quad-core: 4 × 512 KB L2 + a 2 MB L3 — a strictly inclusive L3 could be almost entirely shadowed by the L2s.

Comparing Inclusion Policies

After an L1+L2 miss on X and Y (Z already in L2), then after X is evicted from L1:

Read itInclusion duplicates (X in both) and back-invalidates; exclusion never duplicates (max capacity); NINE just lets each level evict on its own.

Split Cache Organization

A unified L1 holding instructions + data must serve both each cycle:

  • Supply instructions to the pipeline every cycle
  • Serve several load/store accesses every cycle
  • ⇒ needs many ports → expensive and slow
SolutionSplit into an I-cache and a D-cache so instruction and data accesses stop contending for ports. Less useful for lower levels (low access frequency).

Virtual vs. Physical Addressing

Virtual memory lets each program assume it owns the whole address space, and lets many programs reside at once.

  • Separate the virtual address (seen by the program) from the physical address (actual location)
  • The OS manages VA → PA translation at page granularity
Index with VA?Access the cache directly (fast), but contents are invalid on context switch.
Index with PA?Valid across switches, but latency too high — must do a TLB lookup first.

So… what's a good compromise?

Virtually-Indexed, Physically-Tagged (VIPT)

Key insightThe page-offset bits are identical in the VA and PA — translation never touches them.
  • Index the cache with the (untranslated) page-offset bits — start the array read immediately
  • In parallel, the TLB produces the physical tag for the comparison
ConstraintIndex must fit within the page offset → caps capacity / associativity for a given page size.

Types of Cache Misses — the C's

CompulsoryFirst-ever reference to a block — it must be brought in once. (a.k.a. cold misses)
ConflictToo many active blocks map to the same set — insufficient associativity.
CapacityWorking set exceeds the cache size; blocks evicted then re-referenced.
CoherenceMultiprocessor only — a block was invalidated by another processor.
System-relatedSystem calls, interrupts, and context switches pollute / flush the cache.

What Each Parameter Does to Misses

ChangeCompulsoryConflictCapacity
Larger cache sizeunchangedunchangedreduced
Larger block sizereducedunclearunclear
Larger associativityunchangedreducedunchanged
Read the diagonal Bigger cache fights capacity misses; more associativity fights conflict misses; bigger blocks fetch neighbors and cut compulsory misses — but can hurt the others (more eviction, less effective capacity).

Context-Switch Misses

  • Natural misses (compulsory/conflict/capacity) fall as the cache grows
  • Context-switch misses rise with cache size — a bigger cache holds more of each process's footprint, so more is lost when another process runs
  • They keep rising until total working sets fit together

Cache Performance Metrics

Average Access Time (AAT)

\( AAT = L1_T + L1_{MR}\,(L2_T + L2_{MR}\,L2_{MT}) \)
  • \(L_xT\) = level-x access time
  • \(L_x{MR}\) = level-x miss rate
  • \(L_x{MT}\) = level-x miss penalty

You only pay the lower level when the upper level misses — hence the multiplied terms.

Cycles per Instruction

\( cpi = (1 - h_2 - h_m)\,cpi_0 + h_2\,t_2 + h_m\,t_m \)
  • \(h_2\) = fraction of insts that reach L2 · \(h_m\) = reach memory
  • \(cpi_0\) = CPI of insts that stay in L1
  • \(t_2,\,t_m\) = avg penalty for an L2 / memory access

Prefetching

Bring data into the cache before the program asks for it.

SoftwareSpecial prefetch instructions inserted by the compiler.
HardwareAn engine detects access patterns and prefetches automatically.

Basic techniques: sequential prefetching (extrapolate consecutive block accesses) and stride prefetching.

CoverageFraction of misses that were prefetched.
AccuracyFraction of prefetches that turn out useful.
TimelinessArrives early enough to hide latency, but not so early it's evicted first.

Stream Buffers & Multiprocessor Prefetch

Stream buffers [Jouppi '90]

  • On a miss, check the stream buffers for a match
  • Match → move the block into the cache
  • No match → allocate a new stream buffer and prefetch the continuation until it's full

Variants are widely deployed (Pentium, PowerPC, …).

Harder in multiprocessors

Timeliness is harder; a prefetch that's too early may:

  • Be evicted before use, or evict a more useful block (uniprocessor)
  • Be invalidated by another processor
  • Cause a downgrade on another processor's copy

Example: AMD Shanghai vs. Intel Nehalem

Two contemporaries, two L3 inclusion choices:

  • AMD Shanghai L3 is NINE: inclusive would waste ~1/3 capacity; exclusive would need too much L2→L3 bandwidth
  • L3-miss latency: inclusive ≈ 65 ns RT (go to memory) vs. NINE ≈ 77 ns (probe L1s & L2s first)
BandwidthSustained L2 BW: 31 GB/s (Intel) vs. 21.5 GB/s (AMD) — likely tied to AMD's exclusive L2.
AMD compensatesBigger L1 with more ports → L1 read BW 80 GB/s (AMD) vs. 41 GB/s (Intel).
AMD Shanghai uses a NINE (non-inclusive, non-exclusive) L3. Inclusive would incur too much wasted capacity (about 1/3); exclusive would require too much bandwidth (4 L2s feeding the L3). L3-miss latency: inclusive sends straight to the memory controller (65 ns round trip); NINE must probe all L1s and L2s first (77 ns round trip). Sustained L2 bandwidth is 31 GB/s Intel vs 21.5 GB/s AMD, likely related to AMD's exclusive L2, which AMD compensates for by making L1 large and adding more L1 ports — L1 read bandwidth 80 GB/s AMD vs 41 GB/s Intel.

Alternative View: Cache vs. Scratchpad

CachePlacement & replacement managed by hardware. Used by servers and general-purpose systems.
ScratchpadEverything managed by software. Common in embedded systems.
Why scratchpad? It gives predictability of hits and misses — essential for guaranteeing real-time behavior, where a cache's variability is unacceptable.

Optimizing for Latency vs. Throughput

Latency-oriented (CPUs)A miss stalls the processor — few independent instructions to hide it.
  • Small register file · deep cache hierarchy
  • Large last-level cache (LLC) · low memory BW
  • Latency-tolerant tricks (prefetching)
Throughput-oriented (GPUs)A miss is hidden by switching threads — many are ready.
  • Large register file (many threads) · shallow hierarchy
  • Small LLC · high memory BW
Same idea, opposite knobs CPUs avoid stalls with big caches; GPUs tolerate them with massive thread-level parallelism and bandwidth. e.g. NVIDIA H100: small per-SM caches, huge register files, HBM bandwidth.

Other Cache Topics

Pipelined accessSequential vs. parallel tag–data lookups.
Way predictionGuess the hitting way to save energy/latency.
Stack-distance profileModel reuse to predict miss behavior.
Nonblocking cacheServe hits while misses are outstanding (hit-under-miss).
Write-back queue / write combiningBuffer and merge evicted dirty blocks.

Module 5.2 — Review

1. Why does inclusion simplify handling an external coherence request?

You only check the lower level. If the block isn't there, the upper level can't have it — so the upper level's tags aren't disturbed.

2. In VIPT, why can the cache start the lookup before translation finishes?

The page-offset bits are identical in VA and PA, so the index (taken from them) is available immediately; the TLB supplies the physical tag in parallel.

3. Which "C" does more associativity reduce, and which does a bigger cache reduce?

More associativity → fewer conflict misses; bigger cache → fewer capacity misses.

From Single Core to Multicore

We've covered single-core multi-level caches — the ABCs, placement, replacement, inclusion.

How do we organize caches across many cores?

Physical questionOne large monolithic cache (uniformly slow) or many small tiles?
Logical questionEach core uses only its own cache, or are caches shared? Closer data vs. less fragmentation?

Physical vs. Logical Organization

The setupYou have N cores and M cache parts (think banks). How do you connect them?

Physical (how connected)

  • United: cache is directly accessible by cores — without going through a network
  • Distributed: each part is directly reachable by only some cores (others via a NoC)

Logical (who may fill it)

  • Private: only one core may fill a given part with its data
  • Shared: any core may fill any part
Two independent axesPhysical ≠ logical. You can have shared-on-distributed, private-on-distributed, etc. — that combination is the whole design space.

United Cache Organization

  • Crossbar connects each L1 to all L2 banks
  • Bus count grows with cores (N) and banks (M); bus size scales with (N+M)
  • Access time scales with N²
+Uniform latency to every bank.
−Does not scale to many cores.

Distributed Cache Organization

Each cache tile is connected directly to its core, and indirectly to others through a NoC of routers and links.

+Scalable — add tiles and routers.
−Non-uniform latency; high worst-case latency to far tiles.

Few Large Tiles vs. Many Small Tiles

  • Many small tiles: each tile is fast, but more hops to reach the right one
  • Few large tiles: fewer hops, but each tile is slow to access
  • The two effects trade off — there is an optimum tile size

Hybrid Organization

United + distributed L2

Cluster cores around a shared local L2, link clusters by NoC.

+Local L2 fast; remote L2 not too far; scales better than fully united.

Add a level (distributed L2 + united L3)

Private/fast L2 per cluster, big shared L3 behind it.

+Local L2 fast; L3 accessed infrequently.
−L3 slow; multi-level complexity.

Exercise: Distributed Access Times

QShared distributed caches. Estimate min, max, and avg access time. Design A = 2×2 tiles (12-cycle tile access); Design B = 3×3 tiles (8-cycle tile access). Routing/link = 5 cycles/hop; a request needs a reply.
Design A (2×2)
  • Min = 12 (local tile)
  • Max = 12 + (2-hop req + 2-hop reply) = 12 + 4×5 = 32
  • Avg ≈ (√4+1)/3 = 1 hop each way → 12 + 2×5 = 22
Design B (3×3)
  • Min = 8 (local tile)
  • Max = 8 + (4-hop req + 4-hop reply) = 8 + 8×5 = 48
  • Avg ≈ (√9+1)/3 = 4/3 hop each way → 12 + (8/3)×5 ≈ 21.3

More, smaller tiles lower the average (lower tile-access time) but raise the worst case (more hops).

Logical Cache Organization

Two combinations are intuitive and need no further discussion:

  • Private on distributed — each core owns its local tile
  • Shared on united — one logical cache, uniform access

The hard case: shared on distributed. Where does an address map? How do you look a block up?

New concept: distance localityHow far is data that lives at the same cache level? In a distributed cache, two L2 blocks can be 0 hops or many hops away.

Shared Distributed: Tile Associativity

Approach 1: treat the set of tiles like ways of a cache.

Direct-mapped tilesEasy lookup, but data is likely far away — poor distance locality.
Fully-associative tilesBetter distance locality, but you must look up all tiles.

Shared Distributed: Partitioned Shared

Approach 2: partition tiles into groups — shared within a group, private across groups.

+Limited (bounded) distance locality.
+Less fragmentation than fully private.
−Now thread scheduling matters — put threads near their group.

Exercise: Private vs. Shared AAT

QMiss rates: local tile 20%, combined tiles 7%. A request travels a full ring loop; at each router forward it immediately and start a tag lookup; the hitting cache returns the reply. Miss penalty = 200 cycles. Compute AAT for private vs. shared.
Private
  • Access time = 10
  • Miss rate = 20%
  • \(AAT = 10 + 0.20 \times 200 = \) 50 cycles
Shared
  • Access time = 4×3 + 10 = 22 (ring traversal + tile)
  • Miss rate = 7%
  • \(AAT = 22 + 0.07 \times 200 = \) 36 cycles
LessonShared pays more per access (distance) but its lower miss rate (less fragmentation) wins overall here.

The tension, in one line Shared = data far but cache used efficiently; Private = data near but cache fragmented. The next two techniques attack each weakness.

Address-to-Tile Mapping (Hashing)

The hash determines how addresses are interleaved across tiles. A good one should:

  • Spread addresses evenly over tiles
  • Not hurt set utilization within a tile
Bad hashesBlock or page interleaving on the wrong bits can leave some sets unused.
Using upper bitsBlocks are not spread over tiles — a contiguous region all lands on one tile.
Bit randomizationXOR-style mixing of address bits spreads blocks across tiles and keeps sets busy.

Exercise: Minimum Associativity

Q64 tiles in a 2D mesh. Each L2 tile = 512 KB, block = 128 B. Addresses mapped to tiles by page interleaving, page = 4 KB. What minimum set-associativity ensures all sets in each tile are used?
  • Block offset: \(\log_2 128 = \mathbf{7}\) bits
  • Page offset: \(\log_2 4\text{KB} = \mathbf{12}\) bits
  • To use all sets, the tile index must not overlap the set index: \(7 + x \le 12 \Rightarrow x \le 5\)
  • So at most \(2^5 = \mathbf{32}\) sets per tile
\( A = \dfrac{size}{block \times sets} = \dfrac{512\text{KB}}{128 \times 32} = 128 \)
AnswerEach tile must be at least 128-way associative for full set utilization under page interleaving.

Victim Replication: Better Distance Locality

Improves distance locality of shared distributed caches. Idea: use the local tile as a victim cache.

  • A remote block fetched into local L1/L2 — when evicted, place it in the local L3 tile
  • On an L1/L2 miss, check the local L3 first; hit → restore to L1/L2; miss → query the home tile (where the hash maps it)
Coherence costAn external request to L1/L2 must also be forwarded to the local L3 tile, since a replica may live there.
Net effectFrequently-used remote data ends up near the core that uses it, shrinking effective distance.

Capacity Sharing: Less Fragmentation

Reduces fragmentation in private caches. Idea: use remote caches to hold victims of the local cache.

  • On a local miss, the block may be found in a remote cache
  • A core short on space "borrows" capacity from a core with room to spare
Open questions
  • What if the remote cache holds more valuable blocks? Must find one with excess capacity.
  • Replace into the remote cache or place into it? (evict vs. coexist)

Case Study: IBM Power7 Caches

  • 1.2B transistors, large 567 mm² die
  • 8 cores × 4 threads, private L1/L2
  • L3 physically distributed: 8 tiles × 4 MB eDRAM
  • Latency 6 ns local, 30 ns remote
  • L2 inclusive, L3 NINE; a new block fills L1, L2, and L3

Power7 Fill / Eviction Paths

  • L1 eviction is silent (data also in L2)
  • L2 eviction may fill the local L3 — 1st type
  • L3 eviction may fill a remote L3 — 2nd type (capacity sharing!)
Local policyPrefer evicting 2nd-type over 1st-type; when a 1st-type block reaches LRU, convert it to 2nd-type (push to a remote tile rather than drop it).

Module 5.3 — Review

1. Distinguish physical from logical cache organization.

Physical = how cores connect to cache parts (united / distributed / hybrid). Logical = who may fill a part (private / shared). They are independent axes.

2. Shared distributed caches have the worst what, and how is it fixed?

Worst distance locality (data far away). Fixed by victim replication — keep evicted remote blocks in the local tile.

3. Private caches have the worst what, and how is it fixed?

Worst fragmentation (wasted capacity). Fixed by capacity sharing — spill victims into remote caches with free space.
