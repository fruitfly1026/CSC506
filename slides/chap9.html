Chapter 10

Memory Consistency Models — what order do other threads see your memory accesses in?
Coherence (Chapters 7–9) answered: for a single location, what value does a read return? Consistency answers a broader question: across all locations, in what order are one thread's reads and writes seen by every other thread? Two modules: (9.1) sequential consistency and processor consistency; (9.2) the more relaxed models — weak ordering, release consistency, lazy release consistency, and the fences that act as safety nets.

Cache Coherence vs. Memory Consistency

Cache coherence Orders writes to a single memory location.
Only needed for systems with caches. (Chapters 7–9.)
Memory consistency Orders reads/writes across all memory locations.
Concerns systems with or without caches.
Why a consistency model at all? Coherence per-location is not enough: a program's correctness can depend on how a write to A is ordered relative to a write to B. The consistency model is the contract that tells the programmer which inter-location orderings the hardware guarantees.

Programmer's Intuition I — Program Order

Post–wait handoff

// P0                  // P1
S1: datum = 5;         S3: while (!datumIsReady) ;
S2: datumIsReady = 1;  S4: ... = datum;   // expect 5

The programmer expects S4 to read 5. That breaks if S2 runs before S1, or S4 before S3.

Hypothesis 1 · Program order Memory accesses in a thread are executed in the order they appear in source code.
The subtle part This order must hold not just within the thread, but as seen by all other threads.

Programmer's Intuition II — Atomicity

3-way propagation (init x=y=z=xReady=xyReady=0)

// P0            // P1                     // P2
S1: x = 5;       S3: while (!xReady) ;     S6: while (!xyReady) ;
S2: xReady = 1;  S4: y = x + 4;            S7: z = x * y;
                 S5: xyReady = 1;

Programmer expects z = 45 at S7 (x=5, y=9). This implies: if the new x reached P1, it must also have reached P2.

Hypothesis 2 · Atomicity A read/write appears to happen instantaneously with respect to all processors.

How Atomicity Gets Violated

Without atomic writes, the new value of x can reach P1 but lag reaching P2:

StepWhat happensState at P2
1New x & xReady reach P1, not yet P2still old x
2P1 computes y; y & xyReady reach P2 before x doesold x, new y
3P2 already read old x → z = 0; then new x arrivesz = 0, not 45
Root cause The write to x was not atomic — it became visible to different processors at different times.

Sequential Consistency — Lamport's Definition

Summary of expectations Memory accesses from a processor are performed in program order, and each is performed atomically.
"A multiprocessor is sequentially consistent if the result of any execution is the same as if the operations of all processors were executed in some sequential order, and the operations of each individual processor appear in this sequence in the order specified by its program."
— Leslie Lamport, 1979

Empirically, programmer expectations fit SC very closely — it is the model people reason with by default.

SC vs. Non-SC Outcomes — Example A

init a=b=0

// P0        // P1
S1: a = 1;   S3: ...=b;
S2: b = 1;   S4: ...=a;

Non-deterministic — no synchronization. In SC, S1→S2 and S3→S4 are guaranteed.

Interleaving(a,b) read by P1
S1 S2 S3 S41, 1
S3 S4 S1 S20, 0
S1 S3 S2 S41, 0
any SC order0, 1 → impossible

(a,b)=(0,1) needs both S4→S1 (for a=0) and S2→S3 (for b=1) — contradictory under SC.

On a Non-SC Machine — Example A

The illegal outcome (a,b) = (0,1) becomes possible if ordering is broken:

Order S4 S1 S2 S3 S3→S4 violated — the order between two reads is broken.
Order S2 S3 S4 S1 S1→S2 violated — the order between two writes is broken.
Takeaway A forbidden SC result is a fingerprint: it can only appear when the hardware reordered accesses the programmer assumed were in order.

SC vs. Non-SC Outcomes — Example B

init a=b=0 (store-buffer / Dekker shape)

// P0        // P1
S1: a = 1;   S3: b = 1;
S2: ...=b;   S4: ...=a;

Each thread writes one flag, then reads the other. In SC, S1→S2 and S3→S4 hold.

Interleaving(b read by P0, a read by P1)
S1 S2 S3 S40, 1
S3 S4 S1 S21, 0
S1 S3 S2 S41, 1
any SC order0, 0 → impossible

(0,0) needs both S4→S1 (a read 0) and S2→S3 (b read 0) — contradictory under SC.

This is the store-buffer litmus test On real x86/ARM, both threads can buffer their store and read the other's old flag → (0,0) is observable. SC forbids it.

On a Non-SC Machine — Example B

The illegal outcome (0,0) appears when a write and a younger read to different locations are reordered:

Order S4 S1 S2 S3 S3→S4 violated — a write reordered after a younger read.
Order S2 S3 S4 S1 S1→S2 violated — again a write↔younger-read reorder.
Exactly the order PC relaxes Both Example-B violations are the Store → Load ordering. Processor consistency deliberately drops it — coming up.

Does Preserving Order Matter?

Both example codes are non-deterministic — they lack synchronization. Such races are rare and notoriously hard to debug.

Non-determinism is sometimes intentional (legitimate uses exist). If so, ordering may not matter.

But usually it matters
  • Programs go non-deterministic by accident (forgotten synchronization)
  • Predictable ordering keeps programmers sane while debugging
  • Even correctly synchronized programs need ordering for the synchronization itself to work

So: how do we build a system that guarantees SC?

Building an SC System

Program order

  • Stop the compiler from reordering memory accesses
  • Declare critical variables volatile (no register allocation, no dead-code elimination)

Atomicity

  • Expose accesses to the cache one at a time, in program order (pipeline may overlap internally)
  • Load completes when the block is read from cache
  • Store completes when invalidation is posted on the bus / acknowledged
Cost Naïvely, each access must fully complete before the next is exposed — that serializes the memory system.

Example of SC Ordering

Program order

S1: ld R1, A
S2: ld R2, B
S3: st R3, C
S4: st R4, D
S5: ld R5, D

S1 must complete before S2, S2 before S3, and so on.

  • If S1 misses and S2 hits, S2 still waits for S1
  • S5 waits for S4 even though stores are usually retired early and exposed late
  • S5 waits for S4 even though they target the same location D
The performance pain Strict SC throws away the latency-hiding that out-of-order memory systems are built for.

Improving SC Performance — Prefetching

Keep the ordering, but make each completion faster by turning misses into hits:

Load prefetch As soon as the address is known/predictable, prefetch the block in Exclusive/Shared state.
Store prefetch Prefetch the block in Modified state (exclusive prefetch) so the store hits.
Not perfect Too late → little benefit. Too early → cache pollution, and the block may be stolen before use.

Improving SC Performance — Load Speculation

Violate ordering speculatively, but undo if atomicity turns out to be broken. The undo machinery already exists for branch speculation (ILP, ECE 521).

load A; load B
  • Strict SC: B waits for A to complete
  • Speculate: B accesses cache anyway, marked speculative
  • If B's block is invalidated before B retires → atomicity violated → cancel & re-execute B
Loads only Store speculation is hard — a store, once exposed, cannot be canceled. So only load speculation is used.
Result Modern aggressive cores can present an SC interface while still reordering under the hood — at the cost of recovery logic.

Relaxed Consistency Models

Idea: allow some accesses to reorder or overlap. But violating SC can break intuition — so provide a safety net the programmer uses where needed.

Memory fence / barrier A fence instruction orders preceding load/stores before following load/stores. It is the programmer's responsibility to insert fences.
The family
  • PC — Processor Consistency
  • WO — Weak Ordering
  • RC — Release Consistency
  • LRC — Lazy Release Consistency

Implementing a Memory Fence

A fence guarantees that younger memory ops are not issued until older ops have globally performed:

  • Wait until all older writes are posted on the bus (or InvAck received)
  • Wait until all older reads have completed
  • Flush the pipeline so younger memory ops can't issue early
Who inserts them?Thread-library / synchronization-library authors.
If you DIY synchronization without fencesThe machine does not guarantee correctness. (Other, finer fence types exist — later.)

Processor Consistency (PC)

SC enforces all four orderings: LD→LD LD→ST ST→LD ST→ST

PC drops one PC removes the Store → Load constraint — exactly the order whose loss produced Example B's (0,0).

Implications for ILP

  • Committed stores sit in a write buffer, exposed to caches later
  • Loads do not wait for older stores — they hit the cache right away (no speculation needed!)
  • A load dependent on an older store can bypass (read the value straight from the buffer)
  • PC also drops write atomicity

PC: A Load Bypasses Older Stores

This load bypasses 2 stores.
PC produces SC results 

//P1            //P2
data = 2000;    while(flag==0){}
flag = 1;       print data;
PC fails SC — but such code is rare 

//P1               //P2
flag1 = 1;         flag2 = 1;
if (flag2==0) ..   if (flag1==0) ..
Both stores buffered, both loads bypass → both ifs can fire.

How Close Is PC to Intuition?

Usually very close
  • Post–wait synchronization works correctly
  • Major OSes were ported to PC with relative ease
Where it bites
  • Errors usually trace to races that also fail under SC
  • But debugging those races under PC is harder
  • Non-atomic writes still surprise programmers (recall the 3-way example)
Bottom line PC keeps most intuition while unlocking real store-to-load performance — the dropped write atomicity is the price.

Module 9.1 — Review

1. What two expectations do programmers have when writing a parallel program?

Program order — accesses appear in source-code order; and atomicity — each access happens all-at-once with respect to every processor.

2. Name two optimizations that speed up a sequentially consistent machine.

Prefetching (read and exclusive/write prefetch) and load speculation (with cancel-and-replay on invalidation).

3. Which ordering does Processor Consistency relax?

Store → Load. Loads need not wait for older stores; it also drops write atomicity.

Weak Ordering (WO)

Key observation If a programmer wants one ld/st ordered after another, they would have inserted synchronization. Most bug-free programs are synchronized.
Key idea It is safe to reorder/overlap all memory ops except at synchronization points — and blame the programmer for the rest.
WO relies on 2 assumptions
  1. Programs are properly synchronized
  2. Programmers correctly label which ld/st act as synchronization accesses

Why WO Is Safe

Synch may be a lock acquire/release.
Two rules at a synch Before a synch, all previous ops must finish. Before any ld/st, all previous synch must finish.
  • Inside a critical section only one thread runs → reordering anything within it is safe.
  • Outside a critical section we don't care about order (we'd have synchronized if we did).

Challenges for WO

How does the hardware know a given ld/st is a synchronization point?

Heuristics
  • Treat all atomic instructions as synch (fetch-and-op, test-and-set)
  • Treat all LL / SC (load-linked / store-conditional) as synch
But what about plain ld/st that are synch points? The programmer must:
  • Insert safety nets (fence instructions), or
  • Label them as synchronization accesses (e.g. convert to atomics)

WO vs. PC

WO is more aggressive
  • Relaxes read→write, read→read, write→write (not just store→load)
  • More overlap → higher performance
…but more complex
  • Must distinguish normal ld/st from synch operations
  • Sometimes PC wins — e.g. a lock release immediately followed by a read

Release Consistency (RC)

RC splits a synchronization operation into two distinct kinds:

Acquire Gains access to a shared variable.
  • Lock acquisition
  • Wait() in signal–wait synchronization
Release Relinquishes access.
  • Lock release
  • Post() / Signal() in signal–wait
Why split? Acquire and release need ordering in opposite directions — so each gets a one-directional barrier instead of WO's full barrier.

Acquire & Release Semantics

Acquire — blocks upward migration No ld/st after sync_acquire may execute until the acquire completes.

Placed after taking the lock, it ensures no critical-section access runs before the lock is fully held — preventing races inside.

Release — blocks downward migration All ld/st before sync_release must have globally performed before the release executes.

Placed before releasing the lock, it ensures the critical section's writes are visible to others first.

RC in Post–Wait Synchronization

Release side (P0) S2 is the release. So S1 (datum=5) is guaranteed to have performed before S2.
Acquire side (P1) S3 is the acquire. So S3 must have performed before S4 reads datum.

P1 is guaranteed to read the value P0 wrote.

Why RC Is Safe — Critical Section

Shared sum, lock L1

// producer
lock(L1);        // acquire
S2: sum += x;
unlock(L1);      // release
// consumer
S4: lock(L1);    // acquire
S5: ... = sum;
unlock(L1);
unlock = release S2 (the update to sum) is guaranteed to have performed before the unlock(L1).
lock = acquire The lock is acquired before S5 reads sum, so the consumer sees the updated value.

Overlapping Critical Sections: WO vs. RC

With WO Only ld/st within each block overlap; blocks cannot overlap across the synch boundary.
With RC Blocks 1, 2, 3 can overlap in execution — none may start before lock(A) performs, but they need not wait on each other.

Lazy Release Consistency (LRC)

Key observation New values aren't needed until an acquire is performed — so why propagate them early?
LRC idea Delay propagation: push all new values only when the acquire happens (pull on demand) rather than eagerly at each write.

This is where the consistency model and the coherence mechanism blend together.

When LRC wins Systems where many small write propagations are costly vs. a few large ones — e.g. software shared-memory multiprocessors.

Usage Example: PowerPC Fences

Post–wait, full fence

; P0 (post)        ; P1 (wait)
st  datum, 5       loop: ld r, ready
lwsync             cmp r, 0 ; beq loop
st  ready, 1       isync
                   ld  ... , datum
lwsync — full fence Without labeling, a full fence is needed on the post side to block both downward and upward migration.
isync — acquire fence On the wait side, an acquire fence suffices so datum is not read too soon.

Usage Example: IA-64 Labeled Synch

Post–wait with labeled accesses

; P0 (post)            ; P1 (wait)
st       datum, 5      loop: ld.acq r, ready
st.rel   ready, 1            cmp r,0 ; beq loop
                             ld  ..., datum
Labeling beats fences With per-access labels (st.rel / ld.acq), a release store on the post side is sufficient — no separate full fence instruction.

This is the RC philosophy baked into the ISA.

Usage Example: PowerPC LL/SC Lock

Lock via load-linked / store-conditional

acquire:
  lwarx  r, 0, lock      ; load-linked
  cmp    r, 0 ; bne acquire
  stwcx. one, 0, lock    ; store-conditional
  bne    acquire
  isync                  ; <-- acquire fence
  ; ... critical section ...
  lwsync                 ; <-- release fence
  st     lock, 0         ; release the lock
isync Inserted right before entering the critical section — blocks upward migration (acquire).
lwsync Inserted right before the store that releases the lock — blocks downward migration (release).

An Alternative View: Language-Level Models

Embed the consistency model in the programming-language spec; the compiler inserts fences to map it onto whatever the hardware provides.

  • Absent in early languages (C, C++, early Java)
  • Adopted in Java (Java Memory Model, Pugh et al.); later in C++11 and modern C
ProProgrammers get certainty — portable, well-defined ordering.
ConCompiler may sacrifice performance for correctness — though benefits usually outweigh costs.

Module 9.2 — Review

1. What ordering is relaxed, and what is imposed, by Weak Ordering?

Relaxed: any ld/st → ld/st ordering. Imposed: synch → ld/st and ld/st → synch.

2. How does Release Consistency improve on Weak Ordering?

It splits synch into acquire and release, and so allows overlapped execution of critical sections.

3. What migration is prevented by a regular fence, an acquire, and a release?

Regular fence → both directions. Acquire → upward migration. Release → downward migration.

Chapter 10 — Big Picture

Consistency ≠ coherenceCoherence orders one location; consistency orders all locations as seen across threads.
SC is the intuitionProgram order + atomicity. Easy to reason about, expensive to enforce — but prefetch & load speculation help.
Relax for speedPC drops ST→LD; WO orders only at synch; RC splits acquire/release; LRC delays propagation.
One sentence Relaxed models trade away guaranteed ordering for performance, then hand the ordering back to the programmer through fences and acquire/release labels.

The four orderings — LD→LD LD→ST ST→LD ST→ST — and which a model keeps, are the whole story.
