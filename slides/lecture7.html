From Program to Processors

The classic pipeline turns a sequential program into a running parallel one in four steps:

1 · DecompositionSplit the work into tasks — the units of possible concurrency.
2 · AssignmentGroup tasks into processes/threads; balance the load.
3 · OrchestrationName data, communicate, and synchronize the threads.
4 · MappingPlace threads onto physical cores for locality and speed.
This deck Chapter 3 handled decomposition + orchestration for correctness. Here the emphasis is assignment and mapping for performance: granularity, blocking, and how data is distributed across processors.
Module 1
Decomposition & Granularity

By the end you can…

  • Decompose a matrix-vector product into n independent tasks
  • Identify the data each task touches (one row of A + the whole vector)
  • Explain granularity and the fine- vs. coarse-grained trade-off

Worked Example: Matrix × Vector

Compute y = A·x for an n×n matrix A and length-n vector x:

\( y[i] = \sum_{j=0}^{n-1} A[i][j]\cdot x[j] \)
Key observation Each output element y[i] is computed independently of every other y[k]. So the product decomposes into n tasks — one per output element.

Task i touches: row i of A and the entire vector x; it writes only y[i].

Task i = row i of A · all of x → y[i].

Granularity: How Many Tasks?

The number of tasks a problem is decomposed into sets its granularity.

Fine-grained Many small tasks (e.g. one per y[i]). More parallelism & easier load balancing — but more scheduling / communication overhead per unit of work.
Coarse-grained Few large tasks (e.g. one per block of rows). Low overhead and good locality — but less parallelism and a higher risk of imbalance.
The trade-off Granularity trades overhead against parallelism & load balance. Pick tasks large enough to amortize overhead, yet small and numerous enough to keep every core busy.

Module 1 — Review

1. Into how many independent tasks does y = A·x decompose, and why?

Into n tasks — one per output element y[i], since each y[i] is computed independently of the others.

2. What data does one such task read and write?

It reads row i of A and all of vector x, and writes only y[i].

3. Fine- vs. coarse-grained — what is the trade-off?

Fine = many small tasks (more parallelism/balance, more overhead); coarse = few large tasks (less overhead/better locality, less parallelism). Granularity balances the two.
Module 2
Block Partitioning & Cache

By the end you can…

  • Tile an n×n matrix into (n/B)×(n/B) blocks of size B×B
  • Give three reasons block partitioning helps — and the cost it adds
  • Choose a block size B so a block fits in cache

Task Parallelism via Block Partitioning

Instead of rows or single elements, subdivide the matrix into 2-D blocks.

Blocking rule Given an n×n matrix and block size B×B, you obtain a grid of (n/B)×(n/B) blocks. Each block becomes a task.

Why is block partitioning useful?

  1. Cache efficiency — a block is reused while it sits in cache
  2. Efficient load distribution — many equal-size tasks to spread
  3. Scalability — task count grows as the matrix grows
CaveatBlocking also introduces communication between processors that own neighboring blocks.
Each B×B block is one task.

Sizing Blocks to the Cache

Rule of thumb Choose B so that a whole block fits in the data cache and can be reused before it is evicted:
\( B^2 \;\le\; \text{cache size} \)

Example: with a 32 KB data cache, keep the block footprint B² ≤ 32 KB (ideal). Too large and the block spills out of cache mid-use; too small and you lose reuse and add overhead.

CacheConstraintEffect
32 KB L1B² ≤ 32 KBblock stays resident
Too bigB² > cacheeviction → cache misses
Too smallB² ≪ cachepoor reuse, more overhead
Goal Pick the largest B whose block still fits in cache — maximize reuse without spilling.

In practice you also account for the vector/operands sharing the cache, associativity, and line size — but B² ≤ cache is the first-order guide.

Module 2 — Review

1. An n×n matrix is tiled with block size B×B. How many blocks result?

(n/B)×(n/B) blocks.

2. Give three reasons block partitioning helps, and one cost it adds.

Cache efficiency, efficient load distribution, scalability. The cost: it introduces communication between processors holding neighboring blocks.

3. How should you pick B relative to cache size?

So a block fits in cache: B² ≤ cache size (e.g. ≤ 32 KB) — the largest such B, to maximize reuse without eviction.
Module 3
Mapping Blocks to Processors

By the end you can…

  • Apply modulo mapping B[i][j] → P[i%Px][j%Py]
  • Lay blocks onto a Px×Py processor grid
  • Read which processor owns a given block

Modulo Mapping onto a Processor Grid

Given a processor grid of size Px×Py, assign each block to a processor by taking indices modulo the grid dimensions:

\( B[i][j] \;\rightarrow\; P[\,i \bmod P_x\,][\,j \bmod P_y\,] \)

Two processors in a column (Px=2, Py=1): B[i][j] → P[i%2][j%1] — even block-rows go to P00, odd to P10.

On a 2×2 grid the ownership tiles: the same 2×2 pattern of processor IDs repeats across the whole block grid.

Why modulo It spreads neighboring blocks across different processors → interleaves work for balance, at the cost of communication between neighbors.
B[i][j] → P[i%2][j%2]; the 2×2 ownership pattern repeats.

Module 3 — Review

1. Write the modulo mapping of block B[i][j] onto a Px×Py processor grid.

B[i][j] → P[i%Px][j%Py].

2. On a 2×2 grid, which processor owns block B[3][2]?

P[3%2][2%2] = P[1][0] = P10.
Module 4
Distribution Taxonomy & Load Balance

By the end you can…

  • Define block-cyclic distribution and its two special cases
  • Recognize cyclic (block size 1) and block (block size n/p)
  • Reason about the load-balance vs. locality trade-off each implies

Block, Cyclic & Block-Cyclic

Block-cyclic distribution is the general scheme: cut the dimension into blocks of a chosen size, then hand blocks out to the p processors round-robin. The two familiar schemes are its extremes:

Cyclic Special case with block size = 1. Consecutive elements go to consecutive processors (P0,P1,…,P0,P1,…). Best load balance, worst locality.
Block Special case with block size = n/p. Each processor gets one contiguous chunk. Best locality, worst balance if work is uneven.

Block-cyclic (block size between 1 and n/p) dials between the two.

Blue = P0, orange = P1. Block-cyclic (size 2) sits between.

Choosing a Distribution: Balance vs. Locality

BlockContiguous chunks → great spatial locality and low communication, but poor balance when work per element is uneven (e.g. triangular / growing work).
CyclicRound-robin single elements → excellent balance for uneven work, but scattered data hurts locality and raises communication.
Block-cyclicTunable block size → keep enough locality to reuse a block in cache while still interleaving work across processors.
Load balancing A parallel phase runs only as fast as its slowest processor. When per-task work is uniform, block is fine; when it varies, cyclic or block-cyclic spreads the heavy tasks so no single processor is overloaded.

Two More Mapping Axes: Static/Dynamic & Row/Column

Beyond block vs. cyclic, task mapping has two more choices. [Solihin Ch. 3]

Static vs. dynamic Static: the task→processor assignment is fixed before/at launch — lowest overhead, best when work per task is uniform and known (block and cyclic are static schemes). Dynamic: tasks are handed out at runtime from a shared work pool (or by work-stealing) — adapts to irregular or unpredictable work, at the cost of scheduling/synchronization overhead.
Dimension mapping: row- vs. column-wise Which matrix dimension is split across processors — row-wise (each processor owns whole rows) or column-wise (whole columns). The choice decides which accesses stay local vs. become communication: in \(y = A\cdot x\), a row-wise split keeps each \(y[i]\) update local (a processor owns row \(i\) and reads all of \(x\)).
The full taxonomy Task mapping = static/dynamic × block/cyclic/block-cyclic × row/column dimension, all judged by load balance and data locality.

The Same Choices in OpenMP: schedule

On #pragma omp parallel for, the schedule clause is the distribution taxonomy above — the same decisions, in directive form. [OpenMP specification, schedule clause]

Mapping choiceOpenMP clause
Block, static (block size n/p)schedule(static)
Cyclic, static (block size 1)schedule(static, 1)
Block-cyclic, static (block size k)schedule(static, k)
Dynamic, chunk kschedule(dynamic, k)
Dynamic, shrinking chunksschedule(guided, k)

No chunk size → one approximately equal chunk per thread, i.e. block; a chunk size makes the hand-out round-robin, i.e. block-cyclic.


#pragma omp parallel for schedule(static)      // block
#pragma omp parallel for schedule(static,1)    // cyclic
#pragma omp parallel for schedule(dynamic,4)   // dynamic
for (i=0; i<n; i++)  work(i);
Not covered by scheduleThe row/column axis. schedule only distributes iterations of the loop you parallelized — which loop carries the parallel for decides row- vs. column-wise.
Same trade-off static → static,k → static,1 walks the locality → balance dial of the previous slides; dynamic/guided buy balance for irregular work at the cost of runtime scheduling.

Module 4 — Review

1. What are the two special cases of block-cyclic distribution?

Cyclic — block size 1; and block — block size n/p (n = dimension, p = number of processes).

2. Which distribution gives the best load balance, and which the best locality?

Cyclic gives the best balance; block gives the best locality. Block-cyclic tunes between them.

3. Why does load balance matter for performance?

A parallel phase finishes only when its slowest processor does — imbalance leaves other processors idle.
