Parallel Deep Learning
Module 1
Introduction to Neural Networks

Why Now? Three Ingredients

AlgorithmsMost core techniques were invented in the 1980s–90s — backprop, conv nets, recurrent nets.
Big dataWeb-scale labeled datasets arrive in the 2000s.
HardwareGPUs / accelerators become widely available through the 2010s.
For usOld algorithms + huge data + parallel hardware = a systems problem. The interesting question is how to map this compute onto thousands of devices.

Deep Neural Networks

DNNA collection of simple, trainable mathematical units (neurons) composed into layers that together solve a complicated task.

Each layer applies a linear map then a nonlinearity:

\( h^{(\ell)} = \sigma\!\left( W^{(\ell)} h^{(\ell-1)} + b^{(\ell)} \right) \)

The weights \(W^{(\ell)}\) are the parameters we learn. Modern models have billions of them — which is exactly why they no longer fit on one device.

Training: Gradient Descent

Training minimizes a loss \(L(\theta)\) over parameters \(\theta\). Each step nudges \(\theta\) downhill along the gradient:

\( \theta \leftarrow \theta - \eta \, \nabla_\theta L(\theta) \)

\(\eta\) is the learning rate. The gradient is computed by backpropagation — a backward pass through the layers applying the chain rule.

Two passesForward computes the loss; backward computes \(\nabla_\theta L\). Both are dense tensor algebra — perfect for accelerators.
Each step descends the loss landscape.

Stochastic Gradient Descent (SGD)

Full-batch GD is too costlyComputing \(\nabla L\) over the whole dataset every step is impossibly slow at scale.

SGD estimates the gradient from a small random mini-batch \(B\) of samples each step:

\( \theta \leftarrow \theta - \eta \, \nabla_\theta L_B(\theta) \)
Why it matters for parallelismThe mini-batch is what we split across GPUs in data parallelism — each device processes a slice of \(B\), then the gradients are averaged.

Larger batches expose more parallelism but can hurt convergence — the batch size is itself a systems / accuracy trade-off.

CNNs & Convolution

CNNA sequence of convolutional layers interspersed with pooling, normalization, and activations — dominant in vision.

A small filter slides over the input; at each position it computes a weighted sum (a dot product). Weights are shared across positions, so far fewer parameters than a dense layer.

Convolution is the compute hot-spot — usually lowered to dense matrix multiply (im2col + GEMM) on the GPU.

Transformers: Self-Attention

Each token is projected into query, key, value vectors. Attention weights every value by how well its key matches the query:

\( \text{Attn}(Q,K,V) = \text{softmax}\!\left(\tfrac{QK^{\top}}{\sqrt{d_k}}\right) V \)
Multi-headRun h attention computations in parallel on different projections, then concatenate. Heads are an obvious axis to partition across devices.

Graph Neural Networks (GNNs)

GNNNeural networks on relational data — nodes and edges. Each layer aggregates messages from a node's neighbors, then transforms them.

Computation alternates between a sparse aggregate (gather over neighbors) and a dense update (a small MLP per node).

Hard on GPUsThe aggregation is irregular & sparse — poor locality and load imbalance, unlike the dense GEMMs in CNNs/Transformers.

The Rising Compute Demand

Model size and training FLOPs have grown far faster than the memory and throughput of a single accelerator.

Two wallsMemory: parameters + activations + optimizer state exceed one GPU.
Time: one device would take months.
ConsequenceLarge-scale training is now fundamentally parallel — the rest of this lecture is how.
Module 2
Data Parallelism

Three Ways to Decompose

Data parallelismSplit the batch across devices. Each holds a full model replica → independent tasks per device.
Model parallelismSplit the model (neurons / tensors) across devices → independent or dependent tasks.
Pipeline (layer)Split by layers into stages → a chain of dependent tasks.
Big pictureThese are orthogonal axes — real large-scale training combines all three (we get there in Module 5).

Data Parallelism

IdeaReplicate the full model on every device. Each device gets a different shard of the mini-batch, runs forward + backward locally, then average gradients.
Per-step, per device p

shard = batch[p]                # disjoint slice
loss  = forward(model, shard)
g_p   = backward(loss)          # local gradients
g     = all_reduce(g_p, SUM) / P  # average across P devices
model = optimizer.step(model, g)  # identical update

After the all-reduce every replica applies the same averaged gradient, so all replicas stay in sync.

The Memory Issue with Data Parallelism

The catchEvery GPU stores a replica of the entire model — parameters, gradients, and optimizer state.

Data parallelism scales throughput (more samples/sec), but not capacity. If the model doesn't fit on one GPU, replication doesn't help.

ConsequenceCannot train models larger than a single device's memory by data parallelism alone.

This is exactly the gap that model, tensor, and pipeline parallelism fill — they split the model so no one device must hold all of it.

ZeRO & FSDP: Shard the Replica

ZeRO = Zero Redundancy Optimizer (DeepSpeed) FSDP = Fully Sharded Data Parallel (PyTorch) Ψ = #parameters N = #GPUs

Mixed-precision Adam keeps 16 bytes per parameter, so 16Ψ bytes on every replica:
FP16 weight + gradient (4 B), FP32 master weight + momentum + variance (12 B).

Model & Pipeline Parallelism

Model Parallelism: Two Ways to Split

Model parallelism splits the model itself across devices, so no GPU holds the full model. In data parallelism every GPU runs the full model on different data.

KindHow it splitsEach GPU holdsCommunication

Naming"Model parallelism" covers both. Older work often uses it for the layer or subgraph split alone, so today the two are usually named separately: 3D parallelism = data, tensor, pipeline.
Shoeybi et al., "Megatron-LM," 2019; Huang et al., "GPipe," NeurIPS 2019.

Model Parallelism

IdeaSplit the model into subgraphs and assign each to a different device. Each device holds only part of the parameters.

A simple form divides the neurons within each layer, or assigns whole layers/branches to different devices. Capacity now scales with the number of devices.

CostDevices must exchange activations at every cut in the graph — communication is on the critical path.

Device Placement is Hard

Given a computation graph and a set of heterogeneous devices, which op goes where? The space is combinatorial, and the objective (step time) depends on compute, memory limits, and communication.

A research angleUse ML to optimize placement for ML — e.g. reinforcement learning that learns to assign graph nodes to devices to minimize runtime (Mirhoseini et al.).
Combine the axesIn practice we mix data and model parallelism: replicate some parts across groups while splitting others within a group.

Hand-tuned placement dominates production systems; learned placement is promising but expensive to search.

Pipeline (Layer) Parallelism

IdeaPartition the layers into sequential stages, one per device. Stage i's output feeds stage i+1 — a chain of dependent tasks.

Naively, only one stage is active at a time and the others sit idle. GPipe fixes this by splitting each mini-batch into micro-batches that flow through the pipeline back-to-back.

"GPipe: Efficient Training of Giant Neural Networks using Pipeline Parallelism."

Device Utilization: the Bubble

The bubbleAt pipeline fill and drain, some stages have nothing to do. That idle time is the pipeline bubble — pure overhead.

With m micro-batches and p stages, the bubble fraction is roughly \(\tfrac{p-1}{m+p-1}\). More micro-batches → smaller relative bubble, but more in-flight activations.

1F1B & Interleaved Schedules

Memory problemGPipe runs all forwards, then all backwards — so it must keep activations for every in-flight micro-batch. Memory grows with micro-batch count.
1F1B"One-forward-one-backward": once the pipe is full, each stage alternates a forward and a backward. Backward frees activations early, so peak memory stays bounded.
Interleaved 1F1BGive each device multiple non-contiguous stages (model chunks). This shrinks the bubble further at the cost of more communication.

Same total work, finer-grained schedule → higher utilization. Used in large-model training frameworks (e.g. Megatron / DeepSpeed).

Module 4
Tensor Parallelism

Tensor Model Parallelism

IdeaPartition the parameters / gradients within a single layer across devices — split the weight matrix itself, not whole layers.

A matmul \(Y = XW\) splits \(W\) by columns: each device computes a slice \(Y_i = X W_i\), then the slices are concatenated (an all-gather). Splitting \(W\) by rows instead gives partial sums that need an all-reduce. The whole team cooperates on one layer.

Trade-offFine-grained → frequent collective communication; best kept within a fast interconnect (a single node / NVLink).

Module 6
Model Compression

Why Compress?

GoalProduce a simplified model — fewer / smaller parameters, lower inference latency — without significantly diminished accuracy.

Size and speed usually improve together: a smaller model moves less data and does less arithmetic.

Three methodsSparsification (pruning), Quantization, Low-rank approximation.

Especially important for inference at the edge, where memory, latency, and energy are all constrained.

Pruning (Sparsification)

PremiseNetworks tend to be over-parameterized — many weights contribute little. Remove them to save space, time, and energy.

Today's sparsity methods reach a 10–100× (up to ~two-orders-of-magnitude) reduction in model size with little accuracy loss.

Hoefler et al., "Sparsity in Deep Learning," JMLR 22, 2021.
Accuracy curveLight pruning can even improve accuracy (it acts as a regularizer); a wide middle range stays stable; past a point accuracy drops — and where that point is depends on the network.

What, When & How to Sparsify

WhatModel sparsity (neuron / filter / head — fixed pattern across passes) vs. ephemeral sparsity (activations, gradients — per example).
WhenTrain-then-sparsify (then fine-tune), sparsify-during-training, or fully-sparse training from the start.
HowStatic (prune once, fixed) vs. dynamic (prune & regrow during training).
Structured vs. unstructuredUnstructured removes individual weights → highest compression but irregular. Structured removes whole neurons / filters / heads → less compression but hardware-friendly dense kernels.

Sparse Storage Formats

Once a matrix is sparse, storing every zero is wasteful. Sparse formats store only the m nonzeros plus index metadata.

COOTriples (row, col, value) per nonzero — simple, easy to build, good for construction.
CSRCompressed Sparse Row: values + col_idx + row_ptr. Less index overhead, fast row traversal for SpMV.

Simpler schemes (bitmap, delta) trade index size against random-access cost.

Quantization

PTQ = post-training quantization QAT = quantization-aware training
IdeaStore and compute weights (and activations) in fewer bits: FP32 → FP16/BF16 → INT8 → 4-bit, via a scale and zero point, \(x \approx s\,(q - z)\).
Why it paysFewer bytes per weight means less memory traffic, which bounds inference; matrix engines also run faster at low precision.
Risk and remediesAccuracy loss, mostly from outliers that stretch the scale. Remedies: per-channel or per-group scales; keep outliers in higher precision; QAT trains with rounding in the loop.

Weight-only quantization is the common choice for LLM inference: weights dominate memory traffic, activations stay in 16-bit.

Jacob et al., CVPR 2018 (integer-arithmetic inference); Dettmers et al., LLM.int8(), NeurIPS 2022; Frantar et al., GPTQ, ICLR 2023.

Low-Rank Approximation

IdeaReplace a big weight matrix \(W\) by a product of two thin matrices, \(W \approx U V\), with rank \(r \ll n\). Storage and FLOPs drop from \(n^2\) to \(2nr\).
\( n \times n \;\rightarrow\; n\,r + r\,n \)
How to get itTruncated SVD of a trained weight, or train the layer in factored form. Works when singular values decay fast.
LoRA: low-rank for fine-tuningFreeze \(W\); train a low-rank update \(\Delta W = BA\) with \(r\) of 8 to 64. Far fewer trainable parameters, and \(BA\) merges into \(W\) after training: no inference cost.

Same idea as the CP and Tucker decompositions in Part II (Module 11): a low-rank factorization is compression.

Denton et al., NeurIPS 2014 (low-rank expansions of conv nets); Hu et al., "LoRA: Low-Rank Adaptation of Large Language Models," ICLR 2022.

Parallel Deep Learning — Big Picture

DataSplit the batch; all-reduce gradients. Scales throughput, replicates the model.
PipelineSplit layers into stages; mind the bubble. 1F1B bounds memory.
TensorSplit weights within a layer. Scales layer size; keep it intra-node.
3D parallelism and beyondCombine all three: \(N = d \times t \times p\), each mapped to the right interconnect level (DeepSpeed). Context and expert axes extend it to 4D/5D.
CompressionPruning + quantization + low-rank shrink the model — size, latency, energy together.
One sentence When a model outgrows one device, partition along data, tensor, and layer axes — matching each to the interconnect — then compress the model to make every device do less.

LLM Systems: Attention Kernels & Serving

The Whole Model: a Decoder-Only LLM

N = number of layers MLP = multi-layer perceptron (feed-forward network)
Vaswani et al., "Attention Is All You Need," NeurIPS 2017; Radford et al., GPT-2, 2019.

Recap: Self-Attention in Transformers

Each token is projected into query, key, value vectors. Attention weights every value by how well its key matches the query:

\( \text{Attn}(Q,K,V) = \text{softmax}\!\left(\tfrac{QK^{\top}}{\sqrt{d_k}}\right) V \)
Multi-headRun h attention computations in parallel on different projections, then concatenate. Heads are an obvious axis to partition across devices.

Transformer Anatomy & the Two Phases of Inference

n = sequence length d = model width KV cache = stored keys and values of past tokens
One Transformer layerMulti-head attention, then an MLP. Attention: \(O(n^2 d)\) time, \(O(n^2)\) memory per head. The MLP holds about two thirds of the parameters (for \(d_{ff}=4d\)).
PrefillThe prompt's \(n\) tokens run in parallel: big GEMMs, compute-bound. Produces the first token and the KV cache.
DecodeThen one token per step: each step reads all weights and the whole KV cache for ~2 flops per weight. A GEMV in disguise, memory-bound; intensity ≈ sequences batched.
The serving problem: keep the GPU busy in decode without exhausting KV memory.
Vaswani et al., NeurIPS 2017; Pope et al., "Efficiently Scaling Transformer Inference," MLSys 2023.

FlashAttention: Tiling the Attention Kernel

HBM = GPU main memory (high-bandwidth memory) SRAM = on-chip cache, small and fast
Standard attentionWrite \(S = QK^{\top}\) (\(n \times n\)) to HBM, read it for softmax, write \(P\), read it for \(PV\). \(O(n^2)\) traffic: memory-bound, and the \(n \times n\) matrix limits sequence length.
FlashAttentionLoad tiles of Q, K, V into SRAM; keep a running softmax (row max and sum, rescaled as blocks arrive) and accumulate the output tile. The \(n \times n\) matrix is never written; backward recomputes it from saved statistics.
ResultExact attention, memory linear in \(n\), up to 3× faster than the standard kernel (original paper); FlashAttention-2 adds about 2× by cutting non-matmul work and parallelizing across thread blocks and warps.
Dao et al., "FlashAttention," NeurIPS 2022; Dao, "FlashAttention-2," ICLR 2024.

KV Cache & PagedAttention (vLLM)

The KV cache is bigEvery token adds its K and V for every layer: about 800 KB per token for a 13B FP16 model, 1.6 GB for a 2K-token sequence. The cache, not the weights, decides how many requests fit.
The wasteEarlier systems reserved one contiguous buffer per request at its maximum length; fragmentation and over-reservation wasted 60–80% of KV memory.
PagedAttentionStore the cache in fixed-size blocks (e.g. 16 tokens); a per-request block table maps logical to physical blocks, like virtual-memory paging. Blocks are allocated on demand and shared across sequences (parallel samples, beams, common prefixes) with copy-on-write.

Result: near-zero waste, 2–4× serving throughput at the same latency vs. FasterTransformer and Orca (paper's figures).

Kwon et al., "Efficient Memory Management for Large Language Model Serving with PagedAttention," SOSP 2023.

Scheduling Requests: Batching, Chunking, Disaggregation

TTFT = time to first token (prefill latency) TPOT = time per output token (decode latency)
Continuous batching (Orca)Static batching waits for the whole batch to finish; short requests leave GPUs idle. Orca schedules at the iteration level: after every decode step, finished sequences leave and new ones join. Batch the GEMMs, run attention per request.
Chunked prefill (Sarathi-Serve)A long prompt's prefill stalls every decode in the batch. Split the prefill into chunks and run each chunk together with the pending decode steps: decodes never stall, and the chunk fills the GPU the decodes left idle.
Disaggregation (DistServe)Prefill is compute-bound, decode is memory-bound; on shared GPUs they interfere. Run them on separate GPU pools, each with its own parallelism, and ship the KV cache across. TTFT and TPOT are tuned independently.
The common threadServing is a scheduling problem: the goal is a full GPU at every decode step under latency targets, which is the utilization story of this course with requests instead of threads.
Yu et al., "Orca," OSDI 2022; Agrawal et al., "Sarathi-Serve," OSDI 2024; Zhong et al., "DistServe," OSDI 2024.

Faster Decoding: Speculation, Prefix Sharing, MoE

Speculative decodingA small draft model proposes \(k\) tokens; the large model verifies all \(k\) in one parallel forward pass and keeps the longest accepted prefix. With rejection sampling the output distribution is unchanged. 2–3× faster decoding (paper's figure): spends spare compute to cut memory-bound steps.
Prefix sharing (SGLang)System prompts, few-shot examples and chat history repeat across requests. RadixAttention keeps KV blocks of shared prefixes in a radix tree and reuses them, skipping their prefill. Up to 6.4× higher throughput on such workloads (paper's figure).
MoE inferenceEach token touches only a few experts, so FLOPs per token stay small while parameters grow. Experts are spread over GPUs with expert parallelism; the cost is a token all-to-all per MoE layer and load imbalance when a few experts are popular.
PatternEach trick cuts the memory-bound work per generated token: verify several tokens per weight pass, skip prefill for shared prefixes, touch only a few experts.
Leviathan et al., "Fast Inference from Transformers via Speculative Decoding," ICML 2023; Zheng et al., "SGLang," NeurIPS 2024; Lepikhin et al., "GShard," ICLR 2021.

From GEMM to Multi-Linear Algebra

Why BLAS? Lift the Operation, Gain the Reuse

BLAS = Basic Linear Algebra Subprograms AI = arithmetic intensity, flops per number moved

Applications were once loops over vector operations. Each streams its operands once and does one flop per element: no reuse, so it runs at memory speed.

The BLAS ideaExpress the work as matrix-level operations (BLAS-3). An \(n\times n\) GEMM touches \(3n^2\) numbers but does \(2n^3\) flops, so each number is reused n times: what caches and vector units need. LAPACK's blocked algorithms exist for this.
The principlePerformance comes from raising the level of the primitive so the library can find reuse the loop could not. The rest of this lecture applies the same move one order up.
LevelOpFlopsDataAI
BLAS-1\(y \leftarrow \alpha x + y\)\(2n\)\(3n\)\(\approx 1\)
BLAS-2\(y \leftarrow Ax\)\(2n^2\)\(n^2\)\(\approx 2\)
BLAS-3\(C \leftarrow AB\)\(2n^3\)\(3n^2\)\(\approx n\)

Only BLAS-3 has intensity that grows with problem size, so only BLAS-3 can reach the compute roof (recall the roofline lecture).

Dongarra, Du Croz, Hammarling & Duff, "A Set of Level 3 Basic Linear Algebra Subprograms," ACM TOMS 16(1), 1990; Anderson et al., LAPACK Users' Guide.
This is the motivation for the whole lecture: BLAS exists because raising the primitive from vectors to matrices creates reuse that loops over vectors cannot expose. Tensor algebra repeats this move, and sparse tensors are where the move stops working.

The Ladder: GEMM → Batched → Contraction

GEMMThe BLAS-3 workhorse: \( C_{ij} = \sum_k A_{ik} B_{kj} \). The single most tuned kernel in computing — you climbed this ladder in the midterm.
Batched GEMMMany small, independent products at once: \( C^{(b)} = A^{(b)} B^{(b)} \). Fills the machine when one GEMM is too small (deep learning, block solvers).
Tensor contractionSum over shared indices of higher-order arrays, e.g. \( C_{abc} = \sum_{k} A_{akc}\,B_{kb} \). GEMM is just the order-2 special case.
Same move, one order upLoops over matrix ops (a GEMM per slice, a TTM per mode) reuse data only inside each call. One whole-contraction primitive lets the library tile across all modes, as BLAS-3 did for vectors.
Same algebra, rising dimensionality.
The key mental model for the whole topic: a tensor contraction is a sum over one or more shared ("contracted") index groups, leaving the "free" indices of each operand on the result. Set the order to 2 and you recover GEMM. Everything the community does for tensors is an attempt to reuse the decades of GEMM engineering at higher order.

Notation — Einstein Summation

\(\mathcal{A},\mathcal{B},\mathcal{X}\)  order-N tensor order = #indices (modes) free index  appears in output contracted index  summed away
Einsum, informallyName every index; repeated names on the input side that are absent from the output are summed.
\( C_{abc} = \sum_{k,l} A_{akl}\,B_{lbkc} \)

Contraction generalizes matrix multiply, matrix–vector product, inner/outer products, and mode-n products all at once.

Two flagship kernels (sparse world) TTM / SpTTM — tensor × matrix along one mode:
\( \mathcal{Y}_{ijr} = \sum_{k}\mathcal{X}_{ijk}\,U_{kr} \)
MTTKRP — matricized tensor × Khatri–Rao product (the CP hot loop):
\( \tilde{A} = X_{(1)}\,(C \odot B) \)
Students should leave this slide able to read an einsum expression and identify which indices survive to the output (free) and which are summed (contracted). TTM and MTTKRP are the two kernels we will return to on the sparse side — TTM is the engine of Tucker, MTTKRP is the engine of CP.

How Do You Make a Contraction Fast? TTGT vs. GETT

TTGT — Transpose-Transpose-GEMM-TransposePermute & flatten each tensor into a matrix, call tuned GEMM, then transpose the result back. Simple & portable — reuses all of BLAS.
Cost of TTGTThe explicit transposes move data with no flops and need scratch memory — pure overhead, worst for "fat" contractions with little arithmetic.
GETT — GEMM-like Tensor-Tensor mult.Fold the reshaping into the packing/blocking of a GEMM-style macro-kernel. No explicit transpose, no scratch — the permutation happens for free while data is copied into tiles anyway.
Also: LoG"Loops-over-GEMM" — wrap GEMM calls in loops over the remaining indices. A useful middle ground.
The recurring themeThe cache/tiling lessons from Topic 6 come back exactly: whoever packs data into cache-sized tiles with the fewest wasted moves wins. TTGT is the naïve copy; GETT is the fused, tiled version.
Springer & Bientinesi, "Design of a High-Performance GEMM-like Tensor-Tensor Multiplication," ACM TOMS 44(3), 2018.
Draw the analogy to tiled matmul from the cache lecture: TTGT is like materializing a transposed copy of B before multiplying, GETT is like transposing-on-the-fly inside the packing routine. TBLIS and GETT are the two clean "no-transpose" designs; cuTENSOR uses similar ideas on the GPU.
Module 9
Dense Tensor Contraction Frameworks

TBLIS — Contraction Without Transposition

Built on BLIS (the GotoBLAS-style GEMM framework you saw behind tuned matmul). TBLIS realizes the GETT idea in full.

Key ideaFuse the logical tensor transposition into BLIS's own partitioning & packing stages via a "block-scatter-matrix" view of the tensor. No permutation pass, no workspace.
ResultArbitrary contractions run at performance approaching the equivalent GEMM — the transpose overhead simply disappears.
block-scatter-matrix idea

// A tensor's modes are split into
//   M-group (free, rows)
//   N-group (free, cols)
//   K-group (contracted)
// A "scatter" vector maps each logical
// (i,j) to the real memory offset, so
// BLIS packs tiles directly from the
// tensor — transpose happens for free.
D. A. Matthews, "High-Performance Tensor Contraction without Transposition," SIAM J. Sci. Comput. 40(1):C1–C24, 2018.
TBLIS is the cleanest existence proof that you never need to physically transpose. The scatter/block-scatter vectors are the trick: they let the BLIS packing kernels read from an arbitrarily-strided tensor as if it were a matrix. Devin Matthews comes from quantum chemistry, where these contractions dominate coupled-cluster methods.

Cyclops Tensor Framework (CTF) — Distributed

Scales tensor contractions to distributed memory (thousands of nodes) — the MPI world of Topic 3, generalized to order-N.

Cyclic distributionSpreads tensor elements cyclically across the process grid → even load and packed storage even for symmetric tensors.
Why symmetry mattersQuantum-chemistry tensors have permutational symmetry; cyclic layout keeps the compressed form balanced across ranks.
Contractions as communicationCTF reduces each contraction to a distributed matrix multiply and picks a mapping that minimizes communication — the same cost model as SUMMA/Cannon, one dimension up.
Flagship useCoupled-cluster electronic-structure codes (e.g. CCSD/CCSDT) — some of the largest tensor contractions run in science.
Solomonik, Matthews, Hammond, Demmel, "Cyclops Tensor Framework…," IPDPS 2013; journal version in J. Parallel Distrib. Comput. 74(12), 2014.
Tie CTF back to the distributed-memory lectures: it is literally SUMMA-style 2.5D/redistribution logic applied to contractions, plus symmetry-aware packed storage. Edgar Solomonik's communication-avoiding background shows up in the mapping choices. Good place to remind students that "tensor contraction = matmul after the right reshape/redistribute."

cuTENSOR — Tensor Primitives on the GPU

NVIDIA's GPU library exposing an Einstein-summation API. The "cuBLAS of tensors," with mixed-precision compute (FP16, BF16, TF32).

Four operation classes • Contraction (generalized GEMM, transpose-free)
• Block-sparse contraction
• Reduction (sum/max over modes)
• Element-wise with operator fusion (permute + scale + add in one pass)
Where it's usedBackend for cuTensorNet in the cuQuantum SDK (quantum-circuit simulation).
Same tiling story on-GPUSelects a contraction plan per operation — the GPU shared-memory tiling of Topic 8, automated.
NVIDIA cuTENSOR docs (developer.nvidia.com/cutensor); Bayraktar et al., "cuQuantum SDK," arXiv:2308.01999, 2023 (cuTensorNet uses cuTENSOR as its contraction backend).
cuTENSOR is the vendor answer: you give it the index strings and strides, it selects a plan (which may internally permute) and runs it on the GPU. The important connection for a quantum audience is cuTensorNet/cuQuantum, where contracting a tensor network IS the simulation. Note it also does transposition/permutation as first-class ops.

Bientinesi's Line — GETT & the Linnea Compiler

GETT (kernel level)Identify the three index groups of a contraction and drive a tuned GEMM-style macro-kernel — no explicit transpose. Shipped with TTGT & LoG in the open TCCG code generator, so you can compare all three.
Springer & Bientinesi, ACM TOMS 44(3), 2018.
Linnea (expression level)A compiler for linear-algebra expressions: given a high-level formula, it exploits matrix properties & algebraic identities to emit an efficient sequence of BLAS/LAPACK calls — beating a naïve one-call-per-operation translation.
Barthels, Psarras, Bientinesi, "Linnea…," ACM TOMS 47(3), 2021.
Why include this groupThey span the two altitudes that matter: the kernel (GETT, like your GEMM tuning) and the whole-expression optimizer (Linnea, like a query planner for matrix math). Their survey "The Landscape of Software for Tensor Computations" (Psarras, Karlsson, Li, Bientinesi, 2021) is a good map of the whole field.
Bientinesi's HPAC group is worth showing because it connects the two ends of the stack. GETT is the low-level answer to "how do I contract fast"; Linnea is the high-level answer to "given a big matrix expression, what order and which kernels?" — essentially a cost-based compiler. The 2021 survey is a good pointer for the curious.

Dense Landscape — One Table

The common threadEvery one of them is "reach GEMM performance at order N" — by avoiding transposes, balancing across nodes, or running mixed-precision GPU kernels. The dense world is, at heart, solved by reduction to GEMM.
…and that's exactly what breaks nextReduction-to-GEMM assumes dense, regular data. Real tensors — reviews, health records, graphs — are hyper-sparse. There is no dense matrix to call GEMM on.
Framework survey: Psarras, Karlsson, Li & Bientinesi, "The Landscape of Software for Tensor Computations," arXiv:2103.13756, 2021 (per-framework sources on their own slides).
Use this as the pivot slide. The dense story has a happy ending: everything reduces to GEMM. The sparse story does not — the moment >99.99% of entries are zero, materializing a dense matricization is impossible, and all the format and locality problems come roaring back. That is the research half of the lecture.
Module 10
Sparse Tensors — Formats & Kernels

Why Sparse Tensors?

A tensor is a multi-way array; real data is naturally multi-way:

Examples• (user × item × time) reviews
• (patient × diagnosis × procedure) health records
• (source × dest × port) network traffic
Extreme sparsityOften < 0.01% nonzero. A dense representation is astronomically too big — you must store only nonzeros, like SpMV in the homeworks but one dimension up.
Why it's hard (vs. SpMV) • No dense GEMM to fall back on: nothing dense to lift.
• Not just memory-bound: access follows the input's nonzero structure, known only at runtime: irregular, poor locality, load imbalance.
• Indexing overhead grows with order.
Format and kernel are bound togetherA format fixes which indices are cheap to walk, hence the kernel's loop order, parallelism and reuse. It is fast only for the kernel, mode and input it was designed for.
Motivating data & workloads: Li et al., PASTA benchmark suite, 2019.
Anchor to the homework SpMV: students already know that sparse matrices need special formats and that the best format is input-dependent. Sparse tensors are the same story with more indices, more overhead, and a format-choice space that explodes. Motivate with the FROSTT-style real datasets (reviews, health, network).

Format 1 — COO (Coordinate)

\(nnz\)  number of nonzeros mode = tensor dimension "mode-agnostic"  no mode preferred

Store each nonzero as (i, j, k, value). The tensor analog of the simplest sparse-matrix format.

ProsDead simple, mode-agnostic (no index is privileged), easy to build.
ConsStores an integer index per mode per nonzero → for order-4 that's 4 indices for 1 value. Poor locality; lots of redundant index bytes.
COO for an order-3 tensor

i:   [0 0 1 2 2]
j:   [0 2 1 0 3]
k:   [1 0 2 1 0]
val: [a b c d e]
// 3 index arrays + 1 value array,
// all of length nnz

Index storage dominates: 3–4× the value bytes for high-order tensors.

Sparse-tensor COO storage: Bader & Kolda, "Efficient MATLAB Computations with Sparse and Factored Tensors," SIAM J. Sci. Comput. 30(1):205–231, 2007.
COO is the baseline everyone compares against. Its virtue — mode-agnosticism — matters because tensor kernels operate along different modes, and mode-specific formats (like CSF) pay a cost to switch modes. Its vice is index bloat, which HiCOO attacks directly.

Format 2 — CSF (Compressed Sparse Fiber)

Generalizes CSR to tensors: nonzeros form a tree, one level per mode, sharing common index prefixes.

IdeaA "fiber" is a 1-D section: fix all but one index. CSF compresses repeated outer indices — like CSR row pointers, nested N deep.
Foundational workThe CSF format & the parallel SPLATT library are the reference point the whole field builds on.
CSF tree: one level per mode.
Smith & Karypis, CSF format (IA³ 2015); Smith, Ravindran, Sidiropoulos, Karypis, "SPLATT: Efficient and Parallel Sparse Tensor-Matrix Multiplication," IPDPS 2015.
Attribute CSF and SPLATT clearly to Smith and Karypis — this is the foundational format the community, including my own group, builds on and compares against. The tree view makes the CSR analogy concrete: outer indices are shared like CSR row pointers, but nested to tensor order. Downside: it's mode-specific — you may store several trees to contract along different modes.

Format 3 — HiCOO (Hierarchical COO)

block = small sub-tensor holding nearby nonzeros byte-index = offset within a block goal: keep COO's mode-agnostic simplicity, shrink the bytes

Compress COO indices in units of sparse blocks: store each block's origin once, then a tiny byte-sized offset per nonzero within the block.

Best of bothKeeps COO's mode-agnostic simplicity and slashes index bytes; blocking also improves data locality.
Payoff (MTTKRP)Up to 23× over COO and up to 15.6× over CSF, with less or comparable storage.
Blocked indices → fewer bytes, more locality.
Li, Sun, Vuduc, "HiCOO: Hierarchical Storage of Sparse Tensors," SC 2018.
HiCOO (pronounced "haiku") is my SC18 work. The one-line pitch: COO wastes bytes on full-width indices; if you block the tensor, most of each index is the block origin (shared) and only a small within-block offset varies, which fits in a byte. You get COO's mode-agnostic flexibility, far smaller footprint, and better locality — hence the big MTTKRP speedups over both COO and CSF.

Format 4 — ALTO (Adaptive Linearized Tensor Order)

linearize = map (i,j,k,…) → one integer mode-agnostic  same layout serves every mode adaptive bit-encoding  bits per mode ∝ its extent

Encode each nonzero's whole coordinate as a single linearized integer that interleaves the mode bits, so spatially-near nonzeros stay near in memory — along every mode at once.

One copy, all modesRuns MTTKRP for every mode from a single tensor copy — no per-mode reordering, no per-mode duplicate structures.
WinsAn adaptive bit-encoding trades cheap index arithmetic for smaller metadata & better bandwidth use; cuts load imbalance and synchronization.
FormatModeStrategy
COOagnosticraw coordinates
CSFspecificper-mode tree
HiCOOagnosticblocking
ALTOagnosticlinearization

CSF is mode-specific (may store one tree per mode); HiCOO stays agnostic via blocking; ALTO stays agnostic via linearization of the coordinate space.

Helal, Laukemann, Checconi, Tithi, Ranadive, Petrini, Choi, "ALTO: Adaptive Linearized Storage of Sparse Tensors," ICS 2021.
ALTO is the contrast piece to HiCOO. Both are mode-agnostic — they don't privilege a mode the way CSF's tree does — but they get there differently: HiCOO blocks the coordinate space and stores byte offsets within blocks; ALTO linearizes the full coordinate into one integer with an adaptive number of bits per mode, so a space-filling-curve- like ordering keeps neighbors close along all modes simultaneously. The payoff is one tensor copy that serves MTTKRP for every mode with low imbalance and synchronization — no per-mode copies or reordering. Note the author list ends with Jee Choi (a frequent collaborator). P. Sadayappan works with the group on other sparse-tensor papers but is not an ALTO author.

The Hot Kernels — MTTKRP & SpTTM

MTTKRPMatricized-tensor times Khatri–Rao product — the dominant cost of CP decomposition.
\( \tilde{A} = X_{(1)}\,(C \odot B) \)
Touches every nonzero once per mode; memory-bound and irregular.
SpTTM / TTMSparse tensor times dense matrix along a mode — the engine of Tucker.
\( \mathcal{Y}_{ijr} = \sum_k \mathcal{X}_{ijk}\,U_{kr} \)
Why they're hard in parallel• Output-side write conflicts (atomics / privatization)
• Irregular reuse of the dense factor rows
• Severe load imbalance across fibers/slices
• A different mode = a different access pattern
Same tricks returnTiling, privatization/reduction (false-sharing lesson!), reordering for locality, format specialization.
MTTKRP as CP bottleneck: Li et al., IPDPS 2017 & SC 2018. SpTTM: Li et al., IA³ 2016; Ma et al., J. Parallel Distrib. Comput. 129, 2019.
These two kernels are why formats matter — they are the innermost loops of the two dominant decompositions. MTTKRP for CP, TTM for Tucker. Every parallelization headache from earlier lectures reappears: write conflicts (use privatization/reduction, exactly the false-sharing fix), load imbalance, and locality. That is what makes them a rich systems research target.

Making Kernels Faster — Reordering & Layout

Reordering for localityRelabel indices so nearby nonzeros cluster — turning irregular access into blocked, cache-friendly access. Two schemes: BFS-MCS (maximum-cardinality-search heuristic) and Lexi-Order (doubly-lexical ordering lifted to tensors).
PayoffUp to 4.1× sequential and 11.9× parallel speedup on HiCOO-MTTKRP — for free, as preprocessing.
GPU data layout for SpTTMFine thread granularity, coalesced access, rank blocking, shared memory, and an in-place scheme that avoids reorganizing the tensor ↔ matrix.
ResultGPU-SpTTM up to ~67× over a CPU baseline on P100.
Li et al., "Efficient and Effective Sparse Tensor Reordering," ICS 2019. Ma, Li et al., "Optimizing Sparse Tensor Times Matrix on GPUs," JPDC 129, 2019.
Reordering is the tensor version of the cache-locality transformations from Topic 6 — you cannot change the hardware, but relabeling indices changes the access pattern and recovers most of the lost locality, and it composes with HiCOO's blocking. The GPU SpTTM work is the coalescing/shared-memory/in-place story from the GPU lectures, applied to a sparse kernel.
Module 11
Why It All Matters — Tensor Decompositions

CP and Tucker — the "SVD for Tensors"

CP / CANDECOMP-PARAFACApproximate a tensor as a sum of R rank-1 terms:
\( \mathcal{X} \approx \sum_{r=1}^{R} a_r \circ b_r \circ c_r \)
Solved by CP-ALS — whose per-iteration cost is a sequence of MTTKRPs.
TuckerA small dense core tensor times a factor matrix per mode:
\( \mathcal{X} \approx \mathcal{G}\times_1 A\times_2 B\times_3 C \)
Solved via HOOI — inner loop is TTM.
The whole pointDecompositions do data mining, compression, and latent-factor discovery. Their runtime is dominated by MTTKRP (CP) and TTM (Tucker) — so all the format/kernel work pays off directly here.
Redundancy across MTTKRPsAdaTM memoizes shared partial results across the MTTKRP sequence in a CP-ALS sweep — a model-driven space/time tradeoff, up to 8× over SPLATT.
CP, Tucker, CP-ALS & HOOI: Kolda & Bader, "Tensor Decompositions and Applications," SIAM Review 51(3):455–500, 2009.
AdaTM: Li, Choi, Perros, Sun, Vuduc, "Model-Driven Sparse CP Decomposition for Higher-Order Tensors," IPDPS 2017.
Close the loop: the reason anyone cares about MTTKRP and TTM is that they are the inner loops of CP and Tucker, the workhorse tensor decompositions for analytics. AdaTM is a nice algorithmic twist — within one CP-ALS iteration you compute an MTTKRP per mode, and they share sub-computations; memoizing them (with a model to decide how much to cache) cuts asymptotic work. It is built as a patch on SPLATT, reusing CSF.

Input-Adaptive & Auto-Tuned Approaches

InTensLi — dense TTMGenerates fast, in-place dense tensor-times-matrix for arbitrary order/mode, avoiding the explicit tensor→matrix conversion — an input-adaptive framework that tunes the loop & parallel parameters.
Li, Battaglino, Perros, Sun, Vuduc, SC 2015.
SMAT — the SpMV ancestorAuto-tunes the sparse-matrix format (CSR/ELL/…) per input via an offline-trained model — the format-selection idea that tensors inherit.
Li, Tan, Chen, Sun, "SMAT," PLDI 2013.
The unifying ideaThere is no single best format or schedule. The winning system measures the input (and machine) and adapts — format, blocking, thread granularity, memoization.
Connects back to the midtermSame philosophy as auto-tuned GEMM/BLAS: a tuned search over implementations beats one hand-fixed kernel.
Two threads meet here. InTensLi is the dense-TTM, in-place, input-adaptive engine (SC15). SMAT (PLDI13) is the older SpMV auto-tuner that established "learn the best sparse format for this input" — the intellectual ancestor of format selection for tensors. The common message: adaptivity beats a single fixed kernel, exactly as with tuned BLAS.

Systems & Benchmarks — the ParTI! Ecosystem

ParTI! / HiParTIA parallel sparse-tensor infrastructure (CPU+GPU): COO/HiCOO storage, MTTKRP, SpTTM, and CP/Tucker building blocks. The library home of much of this work.
PASTAThe first benchmark suite for sparse-tensor kernels — representative workloads so you can compare systems & architectures fairly.
SpartaHigh-performance element-wise sparse tensor contraction on heterogeneous (DRAM + NVM) memory — extends the story to general contraction, not just TTM/MTTKRP.
Why a benchmark mattersSparse-tensor performance is input-dependent; without a common suite (PASTA), speedup claims aren't comparable. Reproducible workloads are how the field makes real progress — a systems-engineering lesson beyond tensors.
PASTA: Li, Ma, Wu, Li, Barker, CCF Trans. HPC / arXiv:1902.03317, 2019. Sparta: Liu, Ren, Gioiosa, Li, Li, PPoPP 2021. ParTI!/HiParTI: github.com/hpcgarage/ParTI.
Wrap the systems tour: ParTI!/HiParTI is the library where HiCOO, the kernels, and reordering live; PASTA is the benchmark suite that makes cross-system comparison meaningful; Sparta pushes into general element-wise contraction on heterogeneous memory. The meta-point — you need a shared benchmark before performance claims mean anything — is a good systems lesson in its own right.

Takeaways

Big Picture — What to Remember

Lift the primitiveBLAS-1 → BLAS-3 created reuse; contractions repeat the lift one order up.
Dense = reduce to GEMMTBLIS/GETT avoid transposes; CTF distributes; cuTENSOR runs it on GPUs.
Sparse breaks thatNo dense matrix to call, and not merely memory-bound: irregular, input-driven access.
Format and kernel, togetherCOO → CSF → HiCOO: access is input- and runtime-dependent, so the format fixes the kernel's performance.
Kernels drive appsMTTKRP → CP, TTM → Tucker. Speed the kernel, speed the science.
Old lessons returnTiling, coalescing, privatization, NUMA, auto-tuning — all reappear one order up.
One sentence Multi-linear algebra is where every performance idea in this course — locality, tiling, GPU coalescing, distributed layout, avoiding false sharing, and auto-tuning — comes back at once, because a tensor is just a matrix with more places to lose reuse.
The synthesis slide. If students remember one thing: contractions generalize GEMM; the dense world wins by reducing to GEMM; the sparse world can't, so formats and locality dominate; and every optimization technique from the course reappears. This is deliberately a capstone that reaches back to caches, GPUs, and distributed memory.
