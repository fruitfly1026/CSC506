Bus-Based Coherent Multiprocessors — Cache Coherence
Chapter 8 is the heart of shared-memory multiprocessing: how do we keep multiple private caches consistent when they cache the same memory line? We build up from the bus itself, to snooping, to the family of invalidation protocols (write-through, MSI, MESI, MOESI), and finally the Dragon update protocol and performance/design issues.

Module 7.1
Intro to Bus-Based Multiprocessor

By the end you can…

  • Explain the trade-offs of shared cache, SMP, and distributed memory

Shared-Memory Multiprocessor Organizations

Shared cacheOne copy of data → no coherence problem, but contention, interference, and pressure on bandwidth/size. Restricted to a few cores.
SMP — symmetric multiprocessorFocus of this chapter. Private caches, shared memory, simplest interconnect = the bus (a ring is also possible).
Distributed memoryMost scalable; deferred to Chapter 11.

These organizations are not exclusive — real systems combine them.

The Bus: the Simplest Interconnect

A set of parallel wires shared among multiple devices, with lines for command, address, and data (which may be multiplexed onto the same wires).

  • Bus master — a device that can inject data
  • Slave — responds to a master
  • Arbiter — decides which device gets the bus
AdvantagesSimple, low cost (often already present); versatile — new devices plug in easily; cost does not scale with system size.
DisadvantagesA shared communication bottleneck; not scalable — bus speed is limited by length and device count.
Memory bus vs. I/O busA memory bus knows all its devices at design time → short, fast, synchronous (one shared clock, known skew). An I/O bus must be standardized for unknown devices → longer, slower, often asynchronous.

Bus Transactions & Timing

A uniprocessor bus transaction has three phases:

  1. Arbitration — win the bus
  2. Command / address — broadcast
  3. Data transfer
  • Read: command + address, then wait for data
  • Write: command + address + data

All devices observe the address; one device is responsible for responding.

SynchronousAll devices share one clock; timing is pre-determined. The bus must be short or run slow (clock-skew limit).
AsynchronousIndependent clocks; timing established by a handshaking protocol. More flexible, slower.
Builds on the uniprocessorBus-based MPs reuse two uniprocessor fundamentals: bus transactions and the per-line cache state machine. A uniprocessor line already has states — Valid/Invalid for write-through, plus Modified for write-back. Coherence extends both.

Bus Design Choices

ChoiceOptions & trade-off
Address/data linesSeparate (expensive) vs. multiplexed (cheaper, longer latency)
Data line widthWider → more pins (matters for off-chip buses)
Transfer sizeSingle word (simple) vs. multiple words (less overhead)
PrioritizationCritical-word-first: send the requested word first
Bus mastersOne → no arbitration; multiple → need arbitration + priority
Sync vs. asyncSync = simple/fast/short; typically sync for memory bus, async for I/O bus
Why it matters for MPsA multiprocessor has many bus masters (all the CPUs), so arbitration and master/slave logic are unavoidable.

Timing: Atomic vs. Split-Transaction Bus

Split-transactionDecouple request from reply. Transactions must be tagged; a pending-transactions buffer tracks them; requires arbitration.
AdvHigher bandwidth; tolerates higher memory latency.
DisadvMore complex → higher per-transaction latency.

Split transactions get more attractive as memory-access latency grows.

Bus Arbitration

Deciding which master gets the bus — needed whenever there are multiple masters (multiple CPUs, split-transaction).

Daisy chainA grant line runs from highest- to lowest-priority device.
CentralizedEach device has a request line; an arbiter grants the bus (e.g. PCI).
Distributed self-selectionEach device inspects the bus and decides whether to proceed.
Distributed w/ collision detectionOptimistically transmit; back off and retry on a collision (e.g. Ethernet).

Providing Cache Coherence

Processor-sideAdd a snooper to each node to watch all bus transactions. Cache controllers react by changing line states.
Memory-sideThe memory controller (MC) also snoops, deciding whether to read the line from memory and return it.
Two correctness requirements 1. Write propagation — a snooped write must reach other copies, either by update (write the new value into the copy) or invalidate (kill the copy so the next read re-fetches).

2. Write serialization — the bus provides a single global order of writes; every snooper reacts in that bus order.

Where Snoopers Sit — Coherence Controller

A snooper at every cache and at the memory controller.

A coherence controller is added to each node:

  • The snooper watches all bus transactions
  • If a transaction is relevant, it takes an action
  • A finite state machine (FSM) computes the line's new state
  • An outstanding-transaction table tracks pending (not-yet-completed) transactions
In shortCoherence = snoopers + an extended per-line FSM on top of the ordinary cache.

Module 7.1 — Review

1. What is a bus, and what properties make it attractive for a small-scale multiprocessor?

A set of long shared wires with arbitration. It is simple, cheap, and extendable — you can plug in more processors as needed. But clock skew limits its scalability.

2. What components are needed to build a bus-based multiprocessor?

Snoopers (at each processor and at memory), plus modifications to the cache controller, tag array, and its FSM — additional states and state transitions for coherence.

Write-Through Coherence & the MSI Protocol

The Coherence Problem

With private caches over shared memory, the same line can sit in several caches. A write by one core makes the others stale.

The problemCoherence is violated when a read can return a value older than the most recent write to that location.

A coherence protocol enforces write propagation + write serialization using the snoopers from 7.1.

Coherence for Write-Through Caches

The simplest protocol. Assumptions: write no-allocate, write invalidate.

KindEvents
ProcessorPrRd, PrWr
Snooped busBusRd, BusWr
Cache stateValid, Invalid

Because writes go through to memory and the bus, a write invalidates all other caches.

Write-through, write-invalidate: only Valid / Invalid.
Modified line exists as V in only one cache; a clean line may be V in several. Invalid = invalidated, or simply not present.

Problem with Write-Through

High bus bandwidthEvery write causes a write propagation onto the bus — even repeated writes to the same line by the same core.

On a shared bus this saturates quickly as cores are added.

The fix → write-backUse write-back caches: write hits stop at the cache, eliminating most bus write transactions. We only go to the bus when sharing actually requires it.

That idea is the foundation of the MSI protocol — next.

Basic MSI Write-Back Invalidation Protocol

Three states

  • Invalid (I) — not present / killed
  • Shared (S) — ≥1 copy, memory is up-to-date
  • Modified (M) — the only copy, dirty

Processor events

PrRd (read), PrWr (write)

Bus transactions

  • BusRd — request a copy, no intent to modify
  • BusRdX — request a copy with intent to modify (replaces BusWr)
  • Flush — write the line out to memory / bus
Two key verbsInvalidation: Any → I.   Intervention: M → S (a peer's read forces the owner to share + flush).

MSI — Processor-Initiated Transitions

Solid = state; label = event / bus action.
  • I → S on PrRd → issue BusRd
  • I → M on PrWr → issue BusRdX
  • S → M on PrWr → issue BusRdX (or the cheaper BusUpgr)
  • S → S on PrRd: hit, no bus
  • M → M: read/write hits, no bus
Cost of MSIA read-then-write to a private line costs two bus transactions (BusRd then BusRdX/BusUpgr) — the weakness MESI fixes.

MSI — Bus-Initiated (Snooped) Transitions

Snooped transactions; M supplies data via Flush.
  • M → S on snooped BusRd → Flush (intervention: a peer wants to read; downgrade and supply data)
  • M → I on snooped BusRdX → Flush (peer wants to write; give up the line)
  • S → I on snooped BusRdX (invalidate)
  • S → S on snooped BusRd: stay shared
Memory's roleIf a Flush happens, the MC can cancel its read — the dirty owner supplies the data (and memory is updated too).

MSI Walkthrough — P3 Reads X

P1 holds X dirty in M (X=2); memory still has X=1. P3 issues PrRd:

  1. P3 puts BusRd on the bus
  2. P1 snoops it: intervention — Flush X=2, transition M → S
  3. The MC sees the Flush and cancels its memory read; memory is updated to X=2
  4. P3 receives X=2 and enters S
Cache-to-cacheThe dirty owner — not memory — supplies the freshest data.

MSI — Subtle Points

What does the memory controller do?

On snooped BusRd or BusRdX → read and supply data (unless a cache Flushes first). On snooped Flush → update main memory.

On a BusRdX, if the block is M, why Flush it — we're about to overwrite it anyway?

A cache line holds several words (x1, x2, x3, x4). A write may target a different word than the one being overwritten, so the whole dirty line must be fetched first. Also, BusRdX signals intent to write, but a read of the block may still follow.

Writing to a block already Shared — what's more efficient than BusRdX?

BusUpgr: the cache already has valid data, so it only needs to invalidate peers — no data transfer required.

Module 7.2 — Review

1. Contrast the two protocols in this module: write-through and MSI.

Write-through coherence is for write-through caches; MSI is for write-back caches (write hits stay in the cache, cutting bus traffic).

2. When is a written value propagated?

Step 1: a write invalidates other cached copies. Step 2: a later read by a peer misses and reloads the new value — from memory (write-through) or from the peer cache that wrote it (MSI).

MESI and MOESI Protocols

By the end you can…

MESI — Adding the Exclusive State

MSI's flawA read-then-write sequence costs 2 bus transactions — even when no one else shares the line (e.g. a sequential program). BusRd (I→S) then BusRdX/BusUpgr (S→M). Penalizing sequential code is unacceptable.

Add a fourth state. The four MESI states:

  • M odified — dirty, sole copy
  • E xclusive — only this cache has a clean copy (matches memory)
  • S hared — two or more caches may have copies
  • I nvalid
I → E or I → S?Decide with a wired-OR bus signal C = "copy exists," asserted by any cache that has the line in response to a BusRd.

MESI — Processor-Initiated Transitions

  • I → E on PrRd when C not asserted (no other copy)
  • I → S on PrRd when C asserted (someone shares)
  • E → M on PrWr: silent, no bus transaction — the payoff
  • S → M on PrWr → BusUpgr
  • I → M on PrWr → BusRdX
The winRead-then-write to a private line: BusRd (I→E), then E→M for free. One transaction, not two.

MESI — Bus-Initiated (Snooped) Transitions

  • M → S / E → S on snooped BusRd (a peer reads; downgrade)
  • M → I / E → I / S → I on snooped BusRdX or BusUpgr (invalidate)
  • M must Flush (it's the only valid copy); E/S may use the optional FlushOpt
Flush vs. FlushOptFlush is mandatory (correctness). FlushOpt is optional — only for performance, betting that a peer cache is faster than memory. That premise is not always true.

Implementation Choice: Who Supplies Data?

On a miss to a line that is not in M, should memory or a peer cache supply the data?

  • Original Illinois MESI: a cache supplies it (FlushOpt), assuming cache < memory latency
  • Not necessarily true; adds complexity
ComplicationsHow does memory know not to supply (must wait for caches)? Which cache supplies when several are valid (a selection algorithm)?
When it pays offDistributed memory: a nearby cache can be cheaper than distant memory — e.g. SMP nodes in Stanford DASH.

MOESI — Allowing Dirty Sharing

MESI's flawNo dirty sharing: a shared block must be clean. So whenever a dirty block is read by a peer, MESI writes it back to memory — generating lots of memory traffic.
MOESI's fixAllow a dirty block to be shared. One cache is designated the Owner (O) and is responsible for eventually writing it back. Others can evict silently.

Used in AMD processors since the K7 (Athlon).

Owner's jobWhen a read/write to the block is snooped, other (Shared) caches do nothing — the Owner supplies the block and carries the write-back responsibility. Two named actions: Flush = supply the data cache-to-cache to the requester; FlushWB = write the dirty block back to memory (on eviction, or to give up ownership).

MOESI — Five States

O = dirty + shared; the owner supplies data and owes the write-back.
  • E / I → M like MESI
  • M → O on snooped BusRd: stay dirty but become the shared owner (memory not updated)
  • Peer enters S holding a dirty value — legal in MOESI
  • O supplies data on snooped reads and remains responsible for write-back
Eviction ruleAn S copy of a dirty block can be dropped silently. The O copy must be written back on eviction — unlike MSI/MESI where write-back happens only from M.

MOESI Walkthrough — Dirty Sharing

P1 had X in M (X=2). P3 reads X:

  1. P1 Flushes X=2 to P3 but stays dirty, becoming the Owner (M→O)
  2. P3 enters S with the dirty value
  3. Memory is NOT updated — that's the dirty-sharing win
On evictionIf P1 (Owner) evicts → must write X=2 back. If P3 (Shared) evicts → silent drop.

Module 7.3 — Review

1. How does MESI improve on MSI?

A block that is read then written incurs only one bus transaction (not two), thanks to the Exclusive state — E → M is silent.

2. What assumption underlies cache-to-cache transfer in MESI?

That a peer cache can supply the block faster than outer memory. Not always true — hence FlushOpt is optional.

3. How does MOESI improve on MESI?

Dirty sharing: a dirty block may be shared as long as one cache keeps it in the Owner state, reducing Flushes to main memory.

Dragon Update Protocol & Coherence Performance

By the end you can…

  • Contrast write-update (Dragon) with write-invalidate protocols
  • Read the Dragon state diagram (E, Sc, Sm, M) and the BusUpd transaction
  • Define coherence misses — true vs. false sharing — and multi-level coherence

Dragon — a Write-Update Protocol

Four states (and no Invalid — if present it's valid; absent = "not present"):

  • E (exclusive-clean): I and memory have it
  • Sc (shared-clean): I + others, maybe memory; I'm not owner
  • Sm (shared-modified): I + others, not memory; I'm the owner
  • M (modified): only I, dirty

At most one cache holds Sm; Sc and Sm coexist across caches.

New eventsPrRdMiss, PrWrMiss — actions when the block is not present.
New bus transactionBusUpd — broadcasts the single word written on the bus and updates other caches (instead of invalidating them).
On replacementSc can be dropped silently; Sm must Flush (it's the owner).

Dragon — Processor-Initiated Transitions

No Invalid state. Writes broadcast a word via BusUpd.
  • PrRdMiss → BusRd: enter E if no copy (!C), else Sc
  • PrWrMiss → BusRd; BusUpd → Sm if shared, else M
  • E → M on PrWr: silent
  • Sc → Sm / Sm → Sm on PrWr → BusUpd(C) when others share
  • When BusUpd(!C) (no one shares) → go to M
Key differenceA write updates peers in place — peers never get invalidated, so subsequent peer reads still hit.

Dragon — Bus-Initiated (Snooped) Transitions

BusUpd updates copies in place; owner (Sm/M) supplies via Flush.
  • E → Sc / M → Sm on snooped BusRd (a peer read arrives; M Flushes and becomes owner)
  • BusUpd / Update: any sharer applies the written word in place — no invalidation
  • A peer's write (BusUpd) makes the current Sm → Sc (ownership moves)
  • Sm supplies data on snooped reads (cache-to-cache)
Contrastvs. MSI/MESI a peer write here is a BusUpd (no invalidate) — what would have been a coherence miss becomes a hit.

Dragon — Implementation Choices

Eliminate Sm?If BusUpd also updated memory (e.g. DEC Firefly) you wouldn't need Sm. Dragon assumes DRAM is too slow to update on every word.
Broadcast Sc eviction?Would let the last copy return to E (skip future updates). But the eviction transaction isn't on the critical path while a later update may be.
Don't update locally too earlyA write hit must not update the local copy before the controller reaches the bus — doing so can break write serialization.

Coherence/consistency concerns mirror the write-through case.

Cache Coherence Performance — Coherence Misses

Coherence missA miss on a block that was invalidated by a coherence event. Affects only invalidation-based protocols (Dragon's update protocol has none).

Update-based protocols trade these away but increase conflict and capacity misses instead (they keep more lines alive).

True sharingMultiple threads genuinely share the same data item (byte/word). Inherent to the algorithm.
False sharingThreads touch different items that happen to live in the same cache block. An artifact of block granularity — fixable by padding/layout.

Impact of Cache Parameters

ParameterTrue-sharing missesFalse-sharing misses
Larger cache sizeincreasedincreased
Larger block sizedecreasedincreased
Larger associativityunclearunclear
Reading the tableA bigger cache keeps more shared lines resident, so more sharing misses survive (fewer are masked by eviction). A bigger block helps true sharing (more useful data per fetch) but hurts false sharing (more unrelated items collide in one block).

Prefetching & Coherence Misses

Prefetching to a dirty block forces a downgrade at the owner, with several risks:

  • The prefetched block may evict a more useful block (inherent prefetch risk)
  • The prefetched block may be invalidated before it's used
  • A subsequent write by the owner is delayed — it must re-invalidate copies first
Timeliness matters moreIn a multiprocessor, mistimed prefetching can hurt both the prefetching cache and the supplying cache — so prefetch timeliness matters far more than in a uniprocessor.

Multi-Level Cache Coherence

Downstream propagation

  • If L2 caches are coherent, writes at L1 must reach L2 — via write-through L1 or explicit write-notification with write-back L1
  • L2 may need to lump E/M together — it can't be sure of the L1 sub-state

Upstream propagation

  • An invalidation/intervention at L2 must propagate up to L1 (if L1 may hold the block)
  • The inclusion property helps: if the block isn't in L2, no need to back-invalidate L1
Snoop filteringSnoop filters (textbook §7.4.3) cut needless upstream snoops — a per-block presence summary lets a cache ignore irrelevant bus traffic.

Module 7.4 — Review

1. How does Dragon differ from MSI / MESI / MOESI?

Dragon uses write update: a written value is immediately propagated to peer caches (BusUpd), rather than invalidating them.

2. What is a coherence miss, and what are its two types?

A miss caused by a block being invalidated when a peer wrote it (only in invalidation protocols). Two types: true sharing (real read/write sharing) and false sharing (different bytes/words co-located in one block).

3. How is a write value propagated in multi-level caches?

First downstream (write-through or write-notification to L2), then upstream (invalidate any caches that may hold the block).
