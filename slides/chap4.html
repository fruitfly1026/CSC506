Chapter 5

Parallel Programming for Linked Data Structures
Chapter 5 is the pointer-chasing counterpart to the loop-based parallelism of the earlier chapters. Linked data structures (lists, trees, graphs, hash tables) defeat ordinary loop parallelization because following pointers creates a loop-carried dependence. We study three angles: (4.1) why LDS resist parallelism and what serializability means for correct concurrent operations, and (4.2) the lock-based strategies — among-readers, global lock, and fine-grain locking — together with the three hazards fine-grain locking introduces.

Module 4.1
Linked Data Structures & the Parallelism Problem

By the end you can…

  • Explain why pointer chasing creates a loop-carried dependence
  • Apply traversal-vs-compute and structure-specific parallelization

Linked Data Structures (LDS)

Definition Data structures that rely on pointers to link the nodes that make up the structure.

Examples everywhere in systems code:

  • Linked lists — singly/doubly linked, skip lists, stacks, queues, circular queues
  • Trees — binary search trees, red-black trees, B-trees
  • Graphs · hash tables · and many more

Why Use (or Avoid) an LDS?

Advantages
  • Dynamic size — add/remove nodes as needed
  • No need to pre-allocate a maximum size
  • A node can be relocated/removed without disturbing other nodes' storage
Disadvantages
  • Sequential traversal dictated by the chain of pointers
  • Poor spatial locality — nodes need not be contiguous
  • Requires explicit memory allocation / deallocation
The catch for parallelism The very thing that makes an LDS flexible — following pointers — is what makes it hard to parallelize.

Example: Linked-List Declaration

Node and list types

typedef struct tagIntListNode {
  int key;    /* unique for each node */
  int data;
  struct tagIntListNode *next;
} IntListNode;
typedef IntListNode *pIntListNode;

typedef struct {
  pIntListNode head;
} IntList;
typedef IntList *pIntList;
pIntList tracks the head (address of the first node).

Traversal Creates a Loop-Carried Dependence

Sequential traversal

p = pList->head;
while (p != NULL) {
  compute(p);       // the work
  p = p->next;      // the traversal
}
  • The address of the next node is unknown until we dereference p->next
  • Each iteration depends on the previous one → a loop-carried dependence
Consequence We cannot hand the loop to #pragma omp parallel for — iterations are not independent.

Compare to Chapter-1 loop parallelism: there, a[i] was computed from an index we already knew. Here the index is the result of the previous iteration.

Challenges in LDS Parallelization

Loop-carried dependence rules out loop-level parallelization. We must look at other venues:

Venue 1Traversal vs. computation
Keep traversal sequential; run the per-node compute() work in parallel.
Venue 2Structure-specific
Exploit a node's multiple pointers (e.g. left/right subtrees of a tree).
Venue 3Algorithm-level
View the LDS as primitives (insert/delete/search) and parallelize the primitives. → Module 4.2
Shift of mindset We stop asking "are loop iterations independent?" and start asking "which operations can safely overlap?"

Venue 1 — Parallelize Compute, Not Traversal

Idea One thread walks the list. At each node it spawns a task to do compute(p).
  • Traversal stays sequential…
  • …but the compute(p) work runs in parallel across tasks

Venue 1 — OpenMP Implementation

single producer + tasks

#pragma omp parallel
{
  #pragma omp single
  {
    p = head;
    while (p != NULL) {
      #pragma omp task firstprivate(p)
      {
        compute(p);   // runs on some thread
      }
      p = p->next;    // traversal continues
    }
  }
}
  • omp single — one thread does the traversal
  • omp task — each node's work becomes a unit of work for the team
  • firstprivate(p) — each task captures its own node pointer
Why firstprivate? p changes on the next loop iteration; the task must keep the value it had when spawned.

Venue 1 — When Is It Worth It?

Speedup when…
  • Task size ≫ thread spawn & management overhead
  • Task size ≫ per-node traversal time
Otherwise not worth it If task size ≈ traversal time, the traversal thread is itself a bottleneck — max speedup ≈ 2×.
Rule of thumb Bigger per-node work amortizes the sequential traversal. Tiny compute() bodies don't pay for the task machinery.

Venue 2 — Structure-Specific: Binary Tree

Sequential recursive search

int search_tree(pNode p, int key) {
  int out_left, out_right;
  if (p == NULL)  return 0;
  if (p->key == key) return 1;
  out_left  = search_tree(p->left,  key);
  out_right = search_tree(p->right, key);
  return (out_left | out_right);
}

A tree node has two child pointers. The left and right subtree searches are independent — nothing in one depends on the other.

Opportunity Search the left and right subtrees in parallel, then combine.

Venue 2 — Parallel Tree Search

tasks per subtree

int search_tree(pNode p, int key) {
  int out_left, out_right;
  if (p == NULL)  return 0;
  if (p->key == key) return 1;

  #pragma omp task shared(out_left)
  out_left  = search_tree(p->left,  key);

  #pragma omp task shared(out_right)
  out_right = search_tree(p->right, key);

  #pragma omp taskwait
  return (out_left | out_right);
}
/* called once inside omp single */
  • One omp task for the left subtree
  • One omp task for the right subtree
  • omp taskwait — wait for both before combining
Recursion fans out Each recursive level can spawn more tasks, so parallelism grows down the tree.

Venue 2 — Analysis

Applicability Only works where a node has multiple outgoing pointers (out-degree > 1) — trees, graphs. A plain linked list (out-degree 1) gets nothing here.
Speedup is unpredictable Depends on whether the generated tasks are large enough to overcome task fetch/spawn overhead, and on tree balance.
Venues 1 & 2 in one line Both find parallelism in the shape of the computation. For general read/write workloads on a shared list we need the algorithm-level approach — Module 4.2.

Venue 3 — LDS as Data Structure + Primitives

View the structure as a set of operations (primitives):

  • List: insert, delete, search, merge two lists…
  • Tree: insert/delete, DFS, BFS, rebalance…

Then parallelize the execution of primitives with respect to one another.

Pairs to reason about
  • Insertion vs. Insertion
  • Insertion vs. Deletion
  • Insertion vs. Search
  • Deletion vs. Search · Deletion vs. Deletion · …
New correctness question When two primitives overlap, what outcomes are acceptable? That is the question of serializability.

The Two Primitives Up Close

Sorted insert

void Insert(pIntList pList, int key) {
  pIntListNode prev = NULL, p, newNode;
  newNode = IntListNode_Create(key);
  /* find where to insert */
  p = pList->head;
  while (p != NULL && p->key < newNode->key) {
    prev = p;
    p = p->next;
  }
  newNode->next = p;            /* link forward  */
  if (prev != NULL) prev->next = newNode;
  else pList->head = newNode;   /* new head      */
}
Delete by key

void Delete(pIntList pList, int key) {
  pIntListNode prev = NULL, p;
  p = pList->head;
  while (p != NULL && p->key != key) {
    prev = p;
    p = p->next;
  }
  if (p == NULL) return;        /* not found */
  if (prev == NULL) pList->head = p->next;
  else prev->next = p->next;    /* unlink    */
  free(p);
}

Each is a traversal (find the spot) followed by a modification (relink pointers). That split drives Module 4.2.

Correctness Criterion: Serializability

Serializability A parallel execution of a group of operations is serializable if there exists some sequential execution of those operations that produces an identical result.

Run an insert and a delete in parallel. The outcome must equal either:

  • insert then delete, or
  • delete then insert.

Nothing else counts as correct.

Why this matters Serializability lets us reason about concurrency as if operations ran one-at-a-time — even though they actually overlap.

Running example: a simple sorted list where each node holds a unique integer key.

Serializability: Two Insertions

Serializable outcomes insert 4 then 5, or insert 5 then 4 — either way both 4 and 5 end up in the list.
Incorrect race Both threads read node 3's next, both set 3->next to their own node → node 4 is lost.

More Primitive Pairs

PairSerializable outcomeIncorrect race
Insert vs. Deleteinsert 4 / delete 5 in either order → 4 in, 5 outnode 4 never inserted (lost)
Insert vs. Searchinsert 5 / search 6 either order → 5 in, 6 found6 maybe found, maybe not — and the list is broken
Delete vs. Searchdelete 5 / search 5 either order → 5 deleted; found-or-not both OK(naturally serializable: 5 may be found or not)
Note the asymmetry Delete-vs-Search is harmless because either answer matches a valid serial order. The dangerous cases are the ones where a race can corrupt the structure.

Main Observations

Conflict condition Two operations on a common node where at least one writes can produce a non-serializable outcome.
  • Under some circumstances a serializable outcome may still occur despite such a conflict (e.g. delete-vs-search).
  • Conflicts can also occur between an LDS operation and memory management — allocation / deallocation (free).
Looks familiar? "Common location + at least one write" is exactly a data race. The fix is the same family of tools: locks — Module 4.2.

Module 4.1 — Review

1. Why can't we use #pragma omp parallel for to walk a linked list?

Following p = p->next is a loop-carried dependence — the next address is unknown until the current node is dereferenced, so iterations aren't independent.

2. When does the structure-specific (tree) approach apply?

Only when a node has out-degree > 1 (multiple child pointers), so independent subtrees can be searched in parallel.

3. State the serializability criterion.

A parallel execution is correct if it produces a result identical to some sequential ordering of the same operations.

Parallelization & Locking Strategies

By the end you can…

  • Compare among-readers, global-lock, and fine-grain locking

  • Diagnose and fix the three fine-grain hazards: deadlock, dangling traversal, deallocation

Three Parallelization Strategies

Among readers Read-only ops go in parallel; writers serialize. Very simple — but only helps if there are many readers.
Global lock Parallel traversal, then a critical section for the modification. Relatively simple; must re-validate after acquiring the lock.
Fine-grain lock One lock per node; lock only the nodes you touch. Highest concurrency — but deadlock, GC, and traversal hazards appear.
The spectrum Left to right: more concurrency, more complexity. Pick the cheapest strategy that delivers the concurrency you actually need.

Strategy 1 — Parallelization Among Readers

Idea: operations that don't modify the list run in parallel; operations that modify it run sequentially.

  • A read-only operation acquires a read lock
  • A write operation acquires a write lock

Enforced with a lock compatibility table: a request is granted only if compatible with the lock already held.

Held ↓ / Requested →ReadWrite
Read lockYesNo
Write lockNoNo
Only Read + Read is compatible — many readers, one writer at a time.

Strategy 1 — Example

Reader: search

int IntList_Search(pIntList l, int x) {
  acq_read_lock(l);
  /* ... traverse, read only ... */
  rel_read_lock(l);
}
Writer: insert

void IntList_Insert(pIntList l, node *p) {
  acq_write_lock(l);
  /* ... modify the list ... */
  rel_write_lock(l);
}
When it shines Read-mostly structures (lookups ≫ updates). Only one read/write lock guards the whole LDS — trivial to get right.

Lock-Granularity Trade-Offs

Coarse (1 lock for the whole LDS)
  • + Easy to program
  • + No deadlock / livelock possible
  • − Low concurrency
Fine (1 lock per node / field)
  • + High concurrency
  • − Harder to program; lock overhead
  • Often necessary for irregular (non-matrix) structures
A lock can guard… the whole structure, a single node, or even a single field within a node. Finer = more concurrency, more bookkeeping.

Strategy 2 — Global Lock Approach

Every operation has two logical steps:

  • Traversal — find the insert spot / target / searched node
  • Modification — relink pointers

Idea: do the traversal in parallel, but the modification inside a critical section.

Pitfall Between traversal and entering the critical section, the list may have changed. The traversal's assumptions must be re-validated.

Strategy 2 — Validate After Locking

insert with re-validation

void IntList_Insert(pIntList l, node *p) {
  /* perform traversal in parallel */
  ...
  acq_write_lock(l);
  /* check validity:
     are the nodes still there?
     is the link still valid?      */
  if (!still_valid) {
    /* repeat the traversal */
  }
  /* if valid: modify the list */
  ...
  rel_write_lock(l);
}
  • Traversal runs without the lock → parallelism
  • Acquire lock, then re-check the nodes/links you depend on
  • If they changed, re-traverse; else commit the modification
Trade-off More concurrent than one global write lock, but you pay for validation and possible re-traversal.

Strategy 3 — Fine-Grain Locking

Associate a lock with each node. An operation locks only the nodes it needs.

Read and write operations run in parallel except where they conflict on specific nodes.

Key principles — what to lock
  • Nodes that will be modified
  • Nodes that are read and must remain unchanged for correctness
Three new hazards Fine-grain locking buys concurrency but introduces deadlock, dangling traversal, and memory-deallocation bugs. We tackle each.

Example 1 — Two Simultaneous Deletions

Without synchronization, deletion of X can fail.

Which nodes must each thread lock?

  • P1 modifies U and V → lock U, V; depends on X surviving → lock X
  • P2 modifies V and X → lock V, X; depends on Y surviving → lock Y

Example 1 — Conflict Table

NodeLocked by P1Locked by P2

VYesYes
XYesYes
YYes
Conflict at V and X Both threads need V and X. Only one acquires them first and completes; the other waits, then proceeds.

Correct serialization — but acquiring two shared locks in two orders is exactly how deadlock sneaks in. Next slide.

Hazard 1 — Deadlock

If lock-acquisition order is uncoordinated, the two deletions can deadlock:

Lock(X) — waits for P2…Lock(V) — waits for P1…

DeadlockedDeadlocked
Cause A cycle in the "waits-for" graph: P1 holds V wants X; P2 holds X wants V.

Example 2 — Deletion vs. Insertion

Without sync, the inserted X may disappear.
  • P1 modifies U, V → lock U, V; depends on Y → lock Y
  • P2 modifies V → lock V; depends on Y → lock Y

Conflict at V → P1 and P2 serialize.

Hazard 2 — Dangling Traversal

P1 deletes node X while P2 traverses the list searching for Y:

P1 (delete X)P2 (search Y)
Lock(V), Lock(X), Lock(Y)Visiting node V
V->next = YNext node ← V->next
X->next = NULLVisiting node X
Next node ← X->next (now NULL!)
Reports "Y not found" — wrongly
Why P2 had already stepped onto X before P1 unlinked it. X's next no longer leads to Y, so the search falls off the list.

Hazard 3 — Memory Deallocation

Same race, but now P1 actually free()s X:

P1 (delete X)P2 (search Y)
Lock(V), Lock(X), Lock(Y)Visiting node V
V->next = YNext node ← V->next
free(X)Visiting node X
Next node ← X->next
Segmentation fault — X is freed memory
Why P2 dereferences a pointer into memory that P1 has already returned to the allocator. Even correct linking can't save a traversal that lands on a freed node.

Dealing with Deadlock

Deadlock comes from cycles in lock acquisition. Break cycles by imposing a global order on nodes and always locking low → high.

Rule If every thread acquires locks in the same total order, no cycle can form.
What order?
  • Non-cyclic LDS (list, tree): follow the structure — e.g. lock leftmost / parent first
  • Cyclic LDS (graphs): order by address — lock lowest address first

Dealing with Dangling Traversal & Deallocation

Dangling traversal

  • Option 1 (trick): when deleting, don't modify the deleted node's pointers
  • Option 2 (locking): require traversal to lock each node as it visits

Memory deallocation

  • Option 1 (trick): don't free on delete — set node->deleted = 1 and let garbage collection reclaim later
  • Option 2 (locking): traversal locks each visited node
Option 1 vs. Option 2 Option 2 (traversal locking) is more elegant and uniform, but it slows down traversal. The best choice depends on code complexity.

Recovering Concurrency — Read vs. Write Locks

A single lock type forces every dependence to serialize. Distinguish intent:

  • Write lock — to modify a node
  • Read lock — to read a node that must stay unchanged

Two readers of the same node no longer block each other.

Read/write helps elsewhere (two readers), but where one side writes a shared node, serialization is unavoidable — and correct.

Example 2 Revisited — Read/Write Locks

P1 deletes V; P2 inserts X between V and Y. With typed locks:

  • P1: write-lock U, V; read-lock Y (must survive, only read)
  • P2: write-lock V; read-lock Y (must survive, only read)
NodeP1P2

Conflict only at V Both write V → they serialize there. But both only read Y, and Read + Read is compatible → no conflict on Y.

Read/write locks pay off here: the shared "must-survive" node Y doesn't force serialization when nobody writes it. The next example shows where read/write still falls short.

Example 3 — An Unnecessary Conflict

P1 deletes V; P2 inserts X between Y and Z. With read/write locks:

  • P1: write U, V; read-lock Y (must survive)
  • P2: write Y; read-lock Z
NodeP1P2
U,VWrite
YReadWrite
ZRead
Conflict at Y — but is it needed? P1 only needs Y to not be deleted; it does not read Y's contents. P2 only changes Y's next. They could safely run together — yet read/write locks force them to serialize.

Read/write is too coarse: "read" conflates "I read the value" with "I just need it to exist."

Defining New Lock Types

Delete lock Required to deallocate a node.
NoDelete lock For an op whose correctness needs the node not deleted, but does not read its contents.

Note: Write and NoDelete are compatible — a writer can change a node while another op merely pins it alive.

Example 3 Resolved — NoDelete Lock

Same scenario, now P1 uses a NoDelete lock on Y instead of a read lock:

  • P1: write U, V; NoDelete Y
  • P2: write Y; NoDelete Z

Outcome Write on Y and NoDelete on Y are compatible → P1 and P2 run simultaneously. The false conflict is gone.
Lesson More lock types = more expressible intent = more concurrency — at the cost of more programming complexity.

Hand-Over-Hand Traversal Locking

read-locked search (lock coupling)

prev = NULL;
read_lock(pList->head);
p = pList->head;
while (p != NULL) {
  if (p->key == key) {
    printf("Found node\n");
    unlock(p);
    break;
  } else {
    prev = p;
    p = p->next;
    if (p != NULL) read_lock(p);  /* grab next */
    if (prev != NULL) unlock(prev); /* release prev */
  }
}

Also called lock coupling: never release a node's lock until you hold the next node's.

  • Traversal acquires a read lock on each visited node
  • Deletion needs a write lock on a node → it must wait for traversers to pass
Fixes both hazards A node can't be unlinked or freed while a traverser holds its lock — no dangling traversal, no use-after-free.

Conclusions — Parallelization Opportunities

ApproachApplicability / payoff
Loop-levelNon-existent — pointer chasing is a loop-carried dependence
Traversal vs. computePays off when task size ≫ traversal & thread-management overhead
Structure-specificOnly for nodes with out-degree > 1; speedup depends on task size / balance
Algorithm-levelGenerally applicable; strategies: among-readers, global lock, fine-grain
Big picture For shared mutable structures, the algorithm-level (primitive-based) approach is the workhorse — and locking is how we make it correct.

Conclusions — The Three Strategies

Among readers Simplest. One read/write lock for the whole LDS. High speedup if mostly read, little written.
Global lock Parallel traversal + critical-section modification. Must re-validate assumptions after locking; re-traversal possible.
Fine-grain lock One lock per node; must identify exactly which nodes to lock. Handle deadlock, dangling traversal, deallocation.
More concurrency ⇄ more complexity Richer lock types (read/write, NoDelete) unlock more parallelism. OpenMP supports fine-grain locks but does not distinguish read vs. write locks — you build that yourself.

Module 4.2 — Review

1. Name the three fine-grain locking hazards and one fix for each.

Deadlock → global lock ordering (low→high). Dangling traversal → traversal locking (don't follow a node you don't hold). Deallocation → defer free / mark-and-GC, or traversal locking.

2. Why isn't a plain read lock enough in the "insert between Y and Z" case?

P1 only needs Y to survive, not its value; a read lock still conflicts with P2's write on Y. A NoDelete lock (compatible with Write) removes the false conflict.

3. When is the among-readers strategy the right choice?

When the structure is read-mostly — lookups vastly outnumber updates — so one read/write lock gives high concurrency with trivial code.

4.1 ProblemPointer chasing kills loop parallelism. Correctness for concurrent ops = serializability.
