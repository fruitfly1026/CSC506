Synchronization

"A parallel computer is a collection of processing elements that cooperate and communicate to solve large problems fast."

Cooperation needs synchronization to order operations for correctness.

LockEnsures mutual exclusion — only one thread in a critical section at a time.
Event syncPoint-to-point — one thread signals, another waits (producer/consumer).
Group syncGlobal barriers — all threads wait until everyone arrives.
This chapter focuses mostly on locks and barriers. Event synchronization (flags / point-to-point) is the building block underneath barriers.

Typical Modern Implementation: A Stack

Each level constructs synchronization on the level above it — hardware at the bottom, libraries at the top.

HWLevels 1–2 give the atomicity that software cannot achieve alone.
SWLevels 3–4 are library code built on the atomic primitives.
Key ideaLevel i can build the synchronization of level i+1.

Lock Performance Criteria

A lock is judged on more than just correctness — these four axes drive every design choice in this chapter.

Uncontended latencyTime to acquire a lock when no one else is competing.
TrafficCoherence traffic on (a) a failed attempt while held, (b) an attempt while free, (c) lock release.
StorageSpace needed, as a function of the number of threads / processors.
FairnessWhether a thread is guaranteed to eventually acquire the lock relative to others.
TensionLow uncontended latency and low contended traffic often pull in opposite directions.

First Attempt: A Pure-Software Lock

C — naive lock / unlock

void lock(int *lockvar) {
  while (*lockvar == 1) {};  // wait until released
  *lockvar = 1;              // acquire lock
}
void unlock(int *lockvar) {
  *lockvar = 0;
}
In machine language

lock:   ld  R1, &lockvar  ; R1 = MEM[&lockvar]
        bnz R1, lock      ; loop if R1 != 0
        sti &lockvar, #1  ; MEM[&lockvar] = 1
        ret
unlock: sti &lockvar, #0  ; MEM[&lockvar] = 0
        ret
The bugThe ld…sti sequence is not atomic. Two threads can both read 0, then both write 1, and both enter the critical section.

What "Atomic" Must Mean

We need the read-test-write to execute atomically. Atomicity implies two things:

All-or-nothingThe entire sequence appears to execute in its entirety — never partially observed.
SerializedMultiple such sequences are serialized — they take effect one after another, never interleaved.
Implication Software alone cannot guarantee this on a shared-memory machine — we need a hardware atomic read-modify-write (RMW) instruction.

Atomic Read-Modify-Write Instructions

InstructionSemantics (executed atomically)
test-and-set Rx, MRead M; if it matches a constant (e.g. 0), write Rx into M. Old value returned in Rx.
fetch-and-op MRead M, apply op (inc, dec, add, sub…), store the new value back to M.
exchange Rx, MAtomically swap the value in M with the value in register Rx.
compare-and-swap Rx, Ry, MCompare M with Rx; if equal, write Ry into M and copy Rx into Ry.
TodayReal ISAs expose these as x86 XCHG/LOCK CMPXCHG, ARM/RISC-V LL/SC, and C/C++ std::atomic primitives.

How Is Atomicity Guaranteed?

Use the cache-coherence protocol to ensure one atomic instruction executes at a time. Three strategies:

1 · Reserve the busHold the bus until done — no other atomic op can reach the bus. Simple; doesn't scale.
2 · Reserve the blockObtain exclusive permission (e.g. M in MESI); reject/delay invalidations until done.
3 · Illusion of atomicityDon't enforce it — detect a violation and retry. This is LL/SC.
PreviewStrategy 3 is the modern winner: cheap on the common path, and it degrades gracefully under contention.

Simple test&set Lock

test&set lock / unlock

lock:   t&s R1, &lockvar  ; R1 = MEM[&lockvar];
                          ; if (R1==0) MEM[&lockvar]=1
        bnz R1, lock      ; loop if R1 != 0
        ret
unlock: st  &lockvar, #0  ; MEM[&lockvar] = 0
        ret
lockvar1 = lock already acquired
0 = lock is free

The atomic t&s reads the old value into R1 and, if it was 0, sets it to 1 — all in one indivisible step. A thread succeeds iff it reads back 0.

This is the textbook spin lock: every waiter hammers t&s in a tight loop. Correct, but as we will see, the traffic is terrible.

test&set Execution: Two Threads

Thread 0 — succeeds first

t&s R1, &lockvar   ; successful
bnz R1, lock
  ... critical section ...
st  &lockvar, #0   ; release
Thread 1 — spins, then wins

t&s R1, &lockvar   ; failed
bnz R1, lock
t&s R1, &lockvar   ; failed
bnz R1, lock
t&s R1, &lockvar   ; successful (after T0 release)
  ... critical section ...
NoteThread 1 issues a full atomic write on every failed attempt — each one is a coherence transaction. That is the source of the traffic problem.

test&set: Interaction with Coherence

Three processors contend (MESI). Every t&s — success or failure — issues a BusRdX.

Drawbacks & the Back-off Fix

Very high trafficMany coherence transactions even when the lock is not free. They compete with the lock holder's traffic — lengthening the critical section.
Back-offAfter a failed acquisition, pause before retrying.
  • Too little → contention stays high
  • Too much → missed opportunity
  • Exponential back-off: grow the wait interval after each failure
Better ideaStop writing on every attempt — spin on a read instead. That is the test-and-test-and-set lock.

Better: test-and-test-and-set (TTSL)

TTSL — read-spin, then t&s

lock:   ld  R1, &lockvar   ; ordinary load (spin)
        bnz R1, lock       ; loop while held
        t&s R1, &lockvar   ; try to grab it
        bnz R1, lock       ; lost the race? spin again
        ret
unlock: st  &lockvar, #0
        ret

Busy-wait with reads:

  • Spin on a cached load — no bus traffic while held
  • The cached copy is invalidated when the holder releases
  • On release, threads try t&s; only one wins, the rest fall back to read-spinning
The "test" (read loop) filters out the expensive "test-and-set" so the atomic write only happens when there is a real chance of success.

TTSL: Interaction with Coherence

Loads keep the block in Shared; spinning generates no bus traffic. Only release + the winning t&s move the bus.

RequestP1P2P3Bus
ld1E––BusRd
t&s1M–––
ld2, ld3 (spin)SSSBusRd / –
unlock1MIIBusUpgr
ld2SSIBusRd
t&s2IMIBusUpgr

WinFailed waiters sit in Shared and make zero bus transactions until the lock is actually released.

TTSL vs. test&set

Successful acquisition

  • TTSL: 2 bus transactions — BusRd to fetch + BusUpgr to invalidate copies
  • t&s: 1 — a single BusRdX

Failed acquisition

  • TTSL: 1 BusRd, then spin locally (no traffic)
  • t&s: unbounded — every attempt is a BusRdX
VerdictTTSL costs one extra transaction on success but eliminates the failure storm. Since time in the critical section usually exceeds time to grab a free lock, test&set performance can be really bad.

Can We Do Better Than Locking the Bus/Block?

Bus lockingLimited applicability; not scalable with fine-grain locks.
Cache-block lockingExpensive — must rely on buffering or NACK to delay other requests.
The illusion approachInstead of providing atomicity, detect violations of it:
  • Detect that atomicity was broken
  • Cancel the store — its new value must never become visible
  • Replay the load/branch/etc. and try again
Two new instructionsThis is exactly what Load-Linked / Store-Conditional provides.

LL/SC: Two New Instructions

Load-Linked (LL)Reads a word from memory and records its address in a special LL/link register.

Anything that may break atomicity clears the link register:

  • A context switch occurs
  • An invalidation arrives for the linked address
Store-Conditional (SC)Tests whether the link register still matches the store address.
  • Match → perform the store, return success
  • No match → cancel the store, return failure

A failed SC means someone else touched the location — retry the whole sequence.

LL/SC Lock

LL/SC lock / unlock

lock:   LL  R1, &lockvar   ; R1=MEM[&lockvar]; LINK=&lockvar
        bnz R1, lock       ; held? spin
        addi R1, #1        ; R1 = 1
        SC  R1, &lockvar   ; MEM[&lockvar]=R1 if link valid
        bnz R1, lock       ; SC failed? retry
        ret
unlock: st  &lockvar, #0
        ret

The addi makes R1 = 1, the value SC tries to store. SC then overwrites R1 with its outcome — 0 on success, nonzero on failure — so a successful store falls through to ret with the lock held, while a failed one (the link register was cleared by another writer) sends bnz back to spin.

Spin = loadsThe waiting loop uses LL (a load) — no bus traffic while the lock is held, like TTSL.

Key advantageA failed SC generates no bus transaction — unlike a failed t&s, which always issues a write.

The Remaining Problems

A lock highly contended by p threads still scales badly, even with LL/SC.

  • O(p) attempts to acquire and release
  • A single release invalidates O(p) caches
  • → O(p) subsequent cache misses
TrafficEach critical section causes \( O(p^2) \) bus traffic.
FairnessNo guarantee a contending thread will ever acquire the lock — a thread can be starved indefinitely.

Exercise: Build CAS from LL/SC

Construct atomic CAS R1, R2, L: if MEM[L] == R1, swap R2 and L; otherwise do nothing.

One solution

CAS:  LL  R3, &L        ; R3 = MEM[L]; LINK = &L
      bne R3, R1, done  ; MEM[L] != R1 -> no swap
      SC  R2, &L        ; try MEM[L] = R2
      bnz  R2, CAS      ; SC failed -> retry
      mov R2, R3        ; return old MEM[L] in R2
done: ret
ExampleInitially R1=5, R2=10, L=5.
After CAS: R1=5, R2=5, L=10.

The compare and the swap happen as one unit: a failed SC means someone changed L mid-sequence, so we retry.

Module 8.1 — Review

1. What is the purpose of an atomic RMW instruction?

It is the hardware primitive that lets software build all higher-level synchronization (locks, barriers, semaphores).

2. What factors matter when implementing a lock?

Uncontended latency, traffic scalability (on release and on failed attempts), fairness, and storage overhead.

3. What does TTSL improve over test&set?

It spins on reads, so no invalidations are generated while the lock is held.

4. What does LL/SC improve over TTSL?

A failed lock acquisition (failed SC) generates no bus transaction.

Ticket Lock

C — ticket lock

void ticketLock_init(int *next_ticket, int *now_serving) {
  *now_serving = *next_ticket = 0;
}
void ticketLock_acquire(int *next_ticket, int *now_serving) {
  my_ticket = fetch_and_inc(next_ticket);
  while (*now_serving != my_ticket) {};
}
void ticketLock_release(int *next_ticket, int *now_serving) {
  (*now_serving)++;
}
Fairness ✓Like a deli counter: take a ticket, wait for your number. Acquisition follows queue order.
But…Still \(O(p^2)\) traffic — every release updates now_serving, invalidating all p waiters' cached copies.

Array-Based Queueing Lock (ABQL)

C — ABQL

void ABQL_init(int *next_ticket, int *can_serve) {
  *next_ticket = 0;
  for (i = 1; i < MAXSIZE; i++) can_serve[i] = 0;
  can_serve[0] = 1;
}
void ABQL_acquire(int *next_ticket, int *can_serve) {
  *my_ticket = fetch_and_inc(next_ticket);
  while (can_serve[*my_ticket] != 1) {};
}
void ABQL_release(int *next_ticket, int *can_serve) {
  can_serve[*my_ticket + 1] = 1;   // wake the next waiter
  can_serve[*my_ticket]     = 0;   // reset for reuse
}
Fairness ✓Queue order, like ticket lock.
Traffic ✓Each thread spins on its own array slot. A release sets just the next slot, so it invalidates only one cache — O(1)!

Discussion: Which Lock to Use?

  • Design must balance latency vs. scalability
  • ABQL is not automatically best — its higher latency and storage often lose
  • LL/SC locks frequently perform very well in practice
Reality checkScalable programs rarely use highly-contended locks — e.g. fine-grain linked-list parallelization spreads contention out.
Fairness caveatSounds great, but a fair queue lock can stall everyone if the next-in-line is context-switched out or delayed.
TakeawayThe "best" lock depends on contention level, thread count, and scheduling — there is no universal winner.

Barriers

A barrier makes every thread wait until all threads arrive, then releases them together.

  • Typically implemented in software using locks, flags, and counters
  • Adequate for small systems
  • Not scalable for large systems
Threads finish at different times; the barrier resynchronizes them.

A Simple (But Wrong) Centralized Barrier

C — buggy barrier

int numArrived = 0;
lock_type barLock = 0;
int canGo = 0;

void barrier() {
  lock(&barLock);
    if (numArrived == 0) canGo = 0;  // first resets flag
    numArrived++;
    myCount = numArrived;
  unlock(&barLock);

  if (myCount < NUM_THREADS)
    while (canGo == 0) {};   // wait for last thread
  else {                     // last to arrive
    numArrived = 0;          // reset for next barrier
    canGo = 1;               // release everyone
  }
}
The raceReusing the same canGo flag across consecutive barriers breaks: a fast thread can race ahead into the next barrier and reset state while slow threads are still leaving the previous one.

Centralized Barrier with Sense Reversal

C — correct barrier

int numArrived = 0;
lock_type barLock = 0;
int canGo = 0;

void barrier() {
  valueToWait = 1 - valueToWait;  // toggle (per-thread)
  lock(&barLock);
    numArrived++;
    myCount = numArrived;
  unlock(&barLock);

  if (myCount < NUM_THREADS)
    while (canGo != valueToWait) {};  // wait
  else {                              // last to arrive
    numArrived = 0;
    canGo = valueToWait;              // release everyone
  }
}
The fixEach barrier flips the sense (0↔1). A thread waits for canGo == valueToWait, so the meaning of the flag alternates every barrier.

No thread can be fooled by a stale flag value from a previous barrier — the sense it is waiting for is fresh.

Scaling Barriers Further

The centralized barrier serializes on one counter + one flag — fine for small systems, a bottleneck at scale.

Combining-tree barrierArrange threads in a tree; each node combines arrivals from its children, so the counter contention is distributed. (§9.2.2)
Hardware barrier networkA dedicated wired-AND / barrier network signals "all arrived" in near-constant time. (§9.2.3)
IdeaDistribute the arrival counting (tree) or move it into dedicated hardware to escape the centralized bottleneck.

Transactional Memory

A transaction

atomic {
  // arbitrary reads AND writes
  account[i] -= amount;
  account[j] += amount;
}

Like code bookended by LL/SC — but it may contain arbitrary instructions, including stores.

AtomicityThe block appears to execute completely or not at all.
IsolationThe result is unaffected by other threads — i.e. serializable.

Two questions remain: what are the isolation requirements, and what hardware support is needed?

Isolation = Serializability

T1 writes x, z and reads y. T2 writes y, z and reads x. A correct result must equal some serial order.

The hazardInterleaving lets each transaction see the other's partial writes — the outcome matches no serial order.

Requirements for Isolation

Conflict ruleThe write set of T1 must not overlap with the read set or write set of T2 (and vice versa).

Write-write and read-write overlaps are conflicts; read-read is fine.

If a conflict is detected:

  1. Abort the transaction
  2. Cancel its effect (possible because of atomicity)
  3. Retry the transaction
Optimistic concurrencyTM lets transactions run speculatively in parallel and only pays a cost when they actually conflict — unlike a lock, which serializes always.

Needed Hardware Support (HTM)

Track speculative stateBuffer non-committed writes (store buffer, L1, L2). Record the read & write sets via cache tags.
CommitMechanism to publish a committing transaction's write set atomically.
Conflict detectCompare a committer's write set against my read/write state — any overlap = conflict.
RollbackA mechanism to discard speculative state when a transaction aborts.
Four pillarsSpeculative buffering · conflict detection · commit · rollback — every HTM design provides all four.

Example HW Support: Cache-Based HTM

Augment each cache line with read (R) and write (W) speculation bits. They mark the line as part of the current transaction's read/write set.

  • R/W bits record the read & write sets in the cache
  • Speculative writes stay in the cache, not yet visible
  • A snooped external access to a marked line = conflict → abort + flash-clear the bits (rollback)
  • Commit = clear the speculation bits, making the writes globally visible

Module 8.2 — Review

1. What problem does the ticket lock improve over LL/SC?

Fairness: a thread that wants the lock is guaranteed to eventually get it (FIFO queue order).

2. What problem does ABQL improve over the ticket lock?

Traffic: a release invalidates only one sharer (the next in line) instead of all sharers — O(1) instead of O(p).

3. What hardware support is needed for HTM?

Speculative-state buffering, conflict detection, a commit mechanism, and a rollback mechanism.
