Latency-Oriented vs. Throughput-Oriented

CPU — Latency oriented
  • Few powerful cores
  • Large caches, deep OoO pipelines
  • Branch prediction, speculation
  • Goal: make ONE thread finish fast
Minimize latency of a single task.
GPU — Throughput oriented
  • Thousands of simple cores
  • Small caches, little control logic
  • Many threads in flight at once
  • Goal: maximize TOTAL work / second
Maximize aggregate throughput.
Same budget, opposite strategy With the same transistor budget, the CPU spends on control; the GPU spends on arithmetic.

Where the Transistors Go

A cartoon of chip area. CPUs spend area on control & cache; GPUs spend it on ALUs (gold).

Read the areaGold = arithmetic units (ALUs). The GPU is almost all arithmetic.

Hiding Latency Instead of Reducing It

A CPU uses caches to make memory faster. A GPU accepts slow memory — but keeps the hardware busy by switching to other ready threads (warps) while some wait.

The trickWhile one warp stalls on memory, the scheduler runs another. Enough warps → the SM never idles.

Where GPUs Sit: SIMD → SIMT

Earlier we placed GPUs under SIMD. More precisely, GPUs use SIMT — a programming-friendly variant.

SIMD (classic)

  • One instruction drives a fixed-width vector
  • Compiler / programmer manages vector lanes
  • Example: SSE / AVX on CPUs

SIMT (GPU)

  • Write many independent scalar threads
  • HW groups 32 threads into a warp, runs lockstep
  • Lane management is implicit
Key ideaYou think in threads; the hardware executes in warps.

GPU Hardware Organization

A GPU is an array of Streaming Multiprocessors (SMs). Each SM holds many simple cores.

One SMDozens of simple cores, its own schedulers, register file, and shared memory.
Two levels of parallelismMany SMs across the chip · many cores within each SM.

Inside a Streaming Multiprocessor

An SM spends its area on arithmetic, not control. Zoom into one SM:

CUDA Cores (ALUs)Do the FP/INT arithmetic — many per SM.
Warp SchedulersPick a ready warp each cycle; switch on stalls.
Register FileHuge — holds state for many resident warps.
Shared Memory / L1On-chip, programmer-managed scratchpad.
vs. a CPU coreThe SM trades branch predictors & deep caches for raw ALU count.

1. Why can a GPU use small caches yet still achieve high throughput?

It hides memory latency with parallelism: while some warps wait on memory, the scheduler runs others, so the ALUs stay busy without needing big caches.

2. What does it mean to "hide" memory latency rather than reduce it?

The memory is still slow (latency is not reduced); the GPU overlaps that wait with useful compute from other ready warps, so the stall is invisible to throughput.

3. How does SIMT differ from classic SIMD from the programmer's view?

In SIMD you manage fixed-width vector lanes explicitly. In SIMT you write independent scalar threads, and the hardware implicitly groups 32 into a warp and runs them in lockstep.

4. Name three components inside an SM.   5. Why does the GPU's design only pay off for massively parallel problems?

SM components: CUDA cores (ALUs), warp schedulers, register file, shared memory/L1. The design needs many independent threads to keep ~17,000 cores busy and to hide latency — serial/branchy work leaves them idle.

Host and Device

A CUDA program runs on two processors. The CPU (host) orchestrates; the GPU (device) computes.

Host (CPU)
  • Runs the main() program
  • Allocates memory on the device
  • Copies data to / from the device
  • Launches kernels
Device (GPU)
  • Runs kernels in parallel
  • Thousands of threads at once
  • Has its own memory (HBM)
  • Returns results to the host
Host  — data →   Device  ← results —
Precious linkThe PCIe / NVLink connection between host and device is slow — minimize copies across it.

Your First Kernel: Vector Add

A kernel is a function that runs on the GPU. Each thread handles one element.

CUDA C — device kernel

__global__ void vecAdd(float* A, float* B,
                       float* C, int n)
{
    int i = blockIdx.x * blockDim.x
          + threadIdx.x;
    if (i < n)
        C[i] = A[i] + B[i];
}
  • __global__ = runs on the GPU, called from the CPU
  • Every thread runs this same code
  • i identifies which element this thread handles
  • The if (i < n) guards against extra threads
SPMDOne program, many data: thousands of threads execute vecAdd, each on its own i.

Launching the Kernel

The host launches the kernel with an execution configuration: <<< blocks, threadsPerBlock >>>.

CUDA C — host side

int threadsPerBlock = 256;
int blocks = (n + threadsPerBlock - 1) / threadsPerBlock;   // ceil(n / 256)

vecAdd<<<blocks, threadsPerBlock>>>(d_A, d_B, d_C, n);       // launch on GPU

cudaDeviceSynchronize();   // wait for the GPU to finish
Why the ceiling?We launch enough threads to cover all n elements — usually a few more, which is exactly why we need the if (i < n) guard inside the kernel.

The Thread Hierarchy

CUDA threads are organized in three nested levels: grid → block → thread.

  • Grid = all threads of one kernel launch
  • Block = group sharing fast shared memory
  • Thread = one execution of the kernel code
  • Blocks run independently, in any order

Computing a Global Index

Each thread computes a unique global index from its block and thread coordinates.

the canonical 1-D index

  • Block 1 → indices 256..511

1. What are the responsibilities of the host vs. the device?

Host (CPU): runs main, allocates device memory, copies data H2D/D2H, launches kernels. Device (GPU): runs kernels in parallel over thousands of threads on its own HBM memory.

2. What does the __global__ qualifier mean?

It marks a kernel: a function that runs on the GPU but is called (launched) from the CPU host.

3. Write the global-index expression and say why it's correct.   4. Why do we need if (i < n)?

i = blockIdx.x*blockDim.x + threadIdx.x: blockIdx skips whole blocks of blockDim threads, threadIdx offsets within the block, giving a unique 0-based index. We launch ceil(n/256) blocks → a few extra threads, so the guard prevents out-of-bounds writes.

5. How do thread / block / grid map onto core / SM / whole-GPU?

Thread → CUDA core; block → one SM (32-thread warps run in lockstep); grid → the whole GPU, spread across all SMs.

The Warp: 32 Threads in Lockstep

The hardware groups threads into warps of 32. All 32 execute the SAME instruction each cycle, on different data — this is the heart of SIMT.

One fetch, 32 lanesA single fetch/decode drives 32 lanes. This is why GPUs get so much arithmetic per control unit.

Branch Divergence

If threads in a warp take different branches, the warp executes both paths serially, masking the inactive threads. Performance drops.

divergent branch in a warp

if (threadIdx.x % 2 == 0)
    doA();
else
    doB();

The warp executes in two passes:

LessonHalf the lanes sit idle in each pass → up to 2× slowdown for a 2-way branch. Keep threads within a warp on the same path when you can.

Occupancy: Many Warps Hide Latency

Each SM keeps many warps resident. When one stalls on memory, the scheduler instantly switches to a ready warp. More resident warps = better latency hiding = higher occupancy.

Occupancy= resident warps ÷ max warps. Higher occupancy → more latency to hide behind.

The GPU Memory Hierarchy

Like a CPU, the GPU has a speed/capacity hierarchy — but one level is YOUR job to manage.

Inverted pyramidFast & small at top, slow & large at bottom. Shared memory is the key tool you control.

Shared Memory: A Managed Scratchpad

Unlike a CPU cache (automatic), shared memory is explicitly managed in your code. Threads in a block use it to cooperate and reuse data.

CPU Cache
  • Hardware-managed, automatic
  • Transparent to the program
  • You influence it indirectly
GPU Shared Memory
  • Programmer-declared & filled
  • Explicit load / sync / use
  • Block-private, very fast
Biggest leverUsing shared memory well is often the single biggest GPU optimization.

Memory Coalescing

When the 32 threads of a warp access consecutive addresses, the hardware merges them into one transaction. Scattered accesses explode into many.

Same data, different costLayout & indexing decide which you get. This is the single most common GPU performance pitfall.

1. How many threads are in a warp, and how do they execute?

32 threads. They execute the same instruction each cycle in lockstep (SIMT), on different data.

2. What is branch divergence and when does it occur?

When threads in the same warp take different control-flow paths. The warp serializes the paths (running each, masking the others), so a 2-way branch can cost up to 2×.

3. How does high occupancy help hide memory latency?

More resident warps give the scheduler more ready work to issue while others stall on memory, so the SM's ALUs stay busy and the long memory latency is overlapped.

4. List the memory levels fastest→slowest.   5. What is coalescing?

Registers → shared memory/L1 → L2 → global (HBM). Coalescing = when a warp's 32 threads hit consecutive addresses, the hardware merges them into one transaction; scattered accesses become many, so access pattern (data layout + indexing) matters enormously.

A GPU Performance Checklist

Most GPU tuning comes down to a handful of recurring ideas:

Coalesce global memorymake warp accesses contiguous
Use shared memorystage reused data on-chip
Keep occupancy highenough warps to hide latency
Avoid divergencekeep a warp on one path
Minimize host↔device copiesthe PCIe link is slow
In one linePerformance ≈ coalescing + shared memory + occupancy − divergence − copies.

Shared-Memory Bank Conflicts

Shared memory is split into banks. If threads in a warp hit different banks → full speed. If several hit the SAME bank → accesses serialize.

FixPadding arrays or changing the access stride can remove conflicts.

The Reduction Pattern

Summing N values in parallel: pair up and combine in log₂(N) steps instead of N steps.

8 → 4 → 2 → 1 in 3 steps (log₂ 8)Log-depth reductions are everywhere: sums, max, dot products — including inside SpMV.

When Access Becomes Irregular

Everything so far assumed regular, contiguous access. Many real problems — graphs, sparse matrices, tensors — are irregular. This is where GPUs struggle, and where research lives.

The tradeStoring/visiting only the nonzeros (gold) saves work — but scatters memory access.

Why Sparsity Is Hard on GPUs

Sparse formats (e.g. CSR) store only nonzeros with index arrays. The cost: indirect, scattered access.

Uncoalesced accessnonzero columns are scattered → many memory transactions
Load imbalancerows have different #nonzeros → some warps do far more work
Divergencevariable-length row loops → threads in a warp finish at different times
Low arithmetic intensitylittle compute per byte loaded → memory-bound
FrontierThese are open problems — the subject of active research (and your instructor's work).

1. How does shared-memory tiling reduce global memory traffic?

A block loads a tile from slow global memory into fast shared memory once, then all threads reuse it many times — fewer global accesses per FLOP, so higher arithmetic intensity.

2. What causes a shared-memory bank conflict?   3. Why does a parallel reduction take log₂(N) steps?

A conflict happens when several threads in a warp access the same bank; those accesses serialize. A reduction pairs up partial results and halves the count each step, so N → 1 takes log₂(N) levels.

4. Give two reasons sparse SpMV is hard on a GPU.

Any two of: uncoalesced/scattered access to nonzero columns; load imbalance from rows with different nonzero counts; branch divergence from variable-length row loops; low arithmetic intensity (memory-bound).

5. Which optimizations from this unit will you apply in Program 2?

Choose a thread/block mapping that coalesces CSR-array access, use shared memory and reductions where rows are processed cooperatively, keep occupancy high, minimize divergence/imbalance, and minimize H2D/D2H copies — then measure against the sequential baseline.

GPU Unit — Key Takeaways

  • GPUs are throughput machines: many simple cores, latency hidden by parallelism
  • SIMT: you write threads; hardware runs warps of 32 in lockstep
  • The thread hierarchy (grid/block/thread) maps onto GPU/SM/core
  • Memory hierarchy: registers → shared (managed!) → L2 → global
  • Performance = coalescing + shared memory + occupancy − divergence
  • Irregular/sparse problems break these assumptions — the hard, interesting frontier
One sentence A GPU turns a slow-memory, many-core machine into a fast one by always having more parallel work ready to run — and your job is to feed it regular, coalesced, reusable data.
