OpenMP Among the Multithreading Options

For shared-memory parallelism in C/C++ there is a whole family of options. OpenMP is the one we use — it is a portable, compiler-based specification, not a library you have to hand-roll.

OpenMPCompiler directives (#pragma omp) over serial code. Portable, "light" syntax, C & Fortran. Our focus.
Cilk / Cilk PlusLanguage extension with spawn/sync; work-stealing runtime for divide-and-conquer tasking.
Intel TBBA C++ template library — parallel algorithms and containers, no compiler support needed.
PBBSProblem-Based Benchmark Suite — a set of parallel benchmarks/primitives, useful for comparison.
…and pthreadsThe low-level primitive everything else is built on — maximum control, maximum boilerplate.

OpenMP's trade: you give up some control, and in return you annotate ordinary serial code instead of rewriting it.

OpenMP Will — and Will Not

OpenMP = Open specification for Multi-Processing: a standard API for shared-memory multithreaded programs (see openmp.org). Behavior depends on the implementation, and it requires compiler support.

OpenMP WILL
  • Let you split a program into serial and parallel regions
  • Hide stack / thread management — no manual create/join
  • Provide synchronization constructs (barrier, critical, atomic…)
  • Stay portable across compilers and platforms
OpenMP will NOT
  • Parallelize automatically — you mark the parallelism
  • Guarantee speedup — a bad decomposition can be slower
  • Free you from data races — correctness is still on you
Mental model OpenMP is power steering, not a self-driving car. It removes the boilerplate of threading; deciding what is parallel and scoping variables correctly is still your job (that was Chapter 3).

The Fork-Join Execution Model

An OpenMP program starts as a single process — the master thread — and runs serially until it hits a parallel region.

  • FORK — at #pragma omp parallel the master spawns a team of threads; the enclosed statements run in parallel.
  • JOIN — at the end of the region the team synchronizes at an implicit barrier and terminates, leaving only the master.

A program is just a sequence of these fork-join episodes — serial stretch, parallel region, serial stretch, and so on.

Serial → FORK a team → JOIN at an implicit barrier.

Module 1 — Review

1. In one sentence, what is OpenMP?

A portable, compiler-based specification of directives (#pragma omp) for shared-memory multithreading — you annotate mostly serial code rather than manage threads yourself.

2. Trace the fork-join model through one parallel region.

The master runs serially; at #pragma omp parallel it FORKs a team that runs the region in parallel; at the end they JOIN at an implicit barrier, leaving only the master.

3. Name one thing OpenMP will not do.

It won't parallelize automatically, won't guarantee speedup, and won't prevent data races — correctness stays your responsibility.

Setting the Thread Count — Three Ways

The same knob, at three levels of scope. Later settings override earlier ones for the region they apply to.

1 · Environment variable

# whole run, set in the shell
export OMP_NUM_THREADS=8
./myprog

Broadest & simplest — no recompile.

2 · Library call

#include <omp.h>
// from serial code, before a region
omp_set_num_threads(4);

Programmatic — overrides the env var.

3 · Clause on the region

#pragma omp parallel num_threads(2)
{
    // exactly 2 threads here
}

Most local — this region only.

Precedence num_threads() clause > omp_set_num_threads() > OMP_NUM_THREADS > implementation default (often "all hardware threads").

Compile & Run: Hello, Threads

Minimal program — hello.c

#include <stdio.h>
#include <omp.h>          // OpenMP API

int main(void) {
    #pragma omp parallel
    {
        int id  = omp_get_thread_num();
        int tot = omp_get_num_threads();
        printf("Hello from thread %d of %d\n",
               id, tot);
    }
    return 0;
}

Every thread runs the block once; omp_get_thread_num() gives its id in [0, tot).

Compile — the -fopenmp flag is required

# GNU (gcc / g++)
gcc  -fopenmp hello.c   -o hello    # C
g++  -fopenmp hello.cpp -o hello    # C++
Forget the flag? Without -fopenmp the compiler ignores every #pragma omp — the code still builds and runs, but serially on one thread. A "no speedup" bug is very often a missing flag.
Run

export OMP_NUM_THREADS=4
./hello

The schedule Clause: Handing Out Iterations

On #pragma omp parallel for, schedule decides how loop iterations are distributed across the team — a load-balancing knob.

schedule(static) Iterations split into equal contiguous chunks, assigned up front. Lowest overhead. Best when every iteration costs about the same.
schedule(dynamic, chunk) Threads grab a chunk of iterations at a time, coming back for more when done. Handles uneven iteration costs; more runtime overhead.
schedule(guided) Like dynamic, but chunk size starts large and shrinks. A compromise: good balance, fewer trips to the scheduler than dynamic.
Syntax

#pragma omp parallel for schedule(static)
for (i = 0; i < n; i++)      work(i);

#pragma omp parallel for schedule(dynamic, 4)   // 4 iterations per grab
for (i = 0; i < n; i++)      variable_cost(i);

#pragma omp parallel for schedule(guided)
for (i = 0; i < n; i++)      work(i);

Rule of thumb: uniform work → static; lumpy work → dynamic or guided. Measure before committing.

Independent Blocks: #pragma omp sections

Where omp for splits one loop across threads, omp sections hands distinct code blocks to different threads. Each section runs exactly once.

Two independent tasks in parallel

#pragma omp parallel sections
{
    #pragma omp section
    { compute_left(); }    // one thread

    #pragma omp section
    { compute_right(); }   // another thread
}
// implicit barrier here: both done
When to use Function parallelism — a handful of different jobs that can run at once (e.g. read a file while computing on the previous one).
Degree is fixed Parallelism is capped by the number of sections you write — two sections use at most two threads, no matter how many are available. It does not scale with data size.
Contrast Use for for data parallelism (scales with n); use sections for a fixed set of distinct tasks.

Module 2 — Review

1. Give the three ways to set the thread count, most-local first.

num_threads() clause on a region → omp_set_num_threads() library call → OMP_NUM_THREADS environment variable. Each overrides the broader ones below it.

2. You added pragmas but see no speedup and one thread. First thing to check?

The -fopenmp flag. Without it the compiler silently ignores every #pragma omp and builds a serial program.

3. Loop iterations have wildly different costs — which schedule?

schedule(dynamic, chunk) or schedule(guided), so idle threads pull more work. static would leave some threads stalling at the barrier.

How Many Cores? Cores vs. Hardware Threads

On Linux, /proc/cpuinfo is the ground truth. Two fields matter:

  • processor — the id of a hardware thread (logical CPU). Take the max value + 1 for the total number of hardware threads.
  • cpu cores — the number of physical cores per socket.
Why they differ With SMT / hyper-threading, one physical core exposes two hardware threads. 8 cores can show 16 processor entries — so more threads than cores does not mean more true parallelism.
Inspecting the machine

# browse the raw file
vi /proc/cpuinfo

# total hardware threads (count of ids)
grep -c '^processor' /proc/cpuinfo

# physical cores per socket
grep 'cpu cores' /proc/cpuinfo | head -1

Setting OMP_NUM_THREADS above the hardware-thread count only oversubscribes — threads timeshare cores and usually slow down.

Running on ARC with Slurm

ARC is the department research cluster. You do not run heavy jobs on the login node — you ask Slurm, the batch scheduler, for compute nodes. Slurm supports MPI, OpenMP, and CUDA jobs.

srun — interactive Runs a command now on allocated resources. Good for quick tests.
sbatch — batch Submits a job script to the queue; it runs when resources free up. Good for real runs.

Docs: arcb.csc.ncsu.edu/~mueller/cluster/arc/

Interactive test

# 1 task, 8 cores for its threads
srun -n 1 -c 8 ./hello
Batch job — job.sh

#!/bin/bash
#SBATCH -N 1           # 1 node
#SBATCH -n 1           # 1 task
#SBATCH -c 8           # 8 cores / task

export OMP_NUM_THREADS=8
./hello


sbatch job.sh          # submit to the queue

Match OMP_NUM_THREADS to the -c cores you requested.

Module 3 — Review

1. In /proc/cpuinfo, what do processor and cpu cores mean?

processor is a hardware-thread id (max + 1 = total HW threads); cpu cores is the number of physical cores. They differ when SMT is on.

2. Why not launch your parallel job directly on the ARC login node?

It is shared by everyone. You request compute nodes through Slurm — srun for interactive tests, sbatch for queued batch runs.

3. Your sbatch script requests -c 8. What should OMP_NUM_THREADS be?

8 — match the thread count to the cores you reserved, so you neither waste cores nor oversubscribe them.
