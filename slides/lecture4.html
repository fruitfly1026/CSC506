Parallel Programming Models

By the end you can…

What Is a Programming Model?

Programming model An abstraction provided by the hardware to the programmer. It decides how easy or hard it is to express an algorithm as computation tasks the hardware understands.
Uniprocessor model
  • Based on program + data
  • Bundled into the Instruction Set Architecture (ISA)
  • Highly successful at hiding the hardware from programmers
Multiprocessor model
  • Much debate — still searching for the "right" one
  • Two dominate: shared memory & message passing
Why it matters The ISA hid one processor from you almost perfectly. No abstraction hides many processors that well — that gap is what the rest of this chapter is about.

Shared Memory vs. Message Passing

Every location is visible to all processors.
Each location is visible to one processor; data moves by explicit messages.
The one-line difference Shared memory communicates implicitly through loads/stores; message passing communicates explicitly through send/recv.

Thread vs. Process: The Uniprocessor Analogy

Process — share nothing (fork)

if (fork() == 0)
    printf("child, id %d", getpid());
else
    printf("parent, id %d", getpid());
Heavyweight High creation cost; processes share nothing → explicit communication via sockets, files, messages.
Thread — share everything (clone)

void sayhello() {
  printf("child thread, tid %d", gettid());
}
printf("parent thread, tid %d", gettid());

// what's shared is set by the flags;
// CLONE_VM = share the address space
clone(&sayhello, stack_top,
      CLONE_VM | CLONE_FILES | CLONE_FS, NULL);
Lightweight Threads share the address space via CLONE_VM → implicit communication through memory. The flags pick exactly what's shared.

"Share everything" = the address space (code, data, heap). Each thread still has its own stack, registers & PC.

This is the crux: shared memory ≈ threads (share address space, communicate implicitly); message passing ≈ processes (share nothing, communicate explicitly). Everything else in 2.1 follows from it.

Address Spaces: What Each Shares

One process
Threads in one process
Shared Threads share code, data, heap, kernel — only stacks are private.
Private Separate processes share nothing logically. A copy-on-write optimization lets them share pages until one writes ("initial sharing").

Shared Memory: Communication & Synchronization

Two threads share a, b, sum + flags

int a, b, sum;
int ready = 0, done = 0;   // two flags

int dosum(void *arg) {
  while (!ready) {}         // wait for work
  sum = a + b;
  done = 1;                 // mark complete
  return 0;
}
void main() {
  clone(&dosum, ...);       // spawn child
  a = 5; b = 3;
  ready = 1;                // work is available
  while (!done) {}          // wait for child
  printf("sum is %d", sum);
}
Communication a, b, sum, ready, done are never explicitly sent — they live in shared memory.
Synchronization Only the flags ready / done are coordinated; the spin-loops try to order the two threads.
Lesson Shared memory separates data sharing (free, through memory) from synchronization (which you must write explicitly).

Shared Memory: Is the Spin-Loop Correct?

The handshake on the previous slide — the ready / done spin-loops — looks right. It isn't, for two independent reasons:

① Compiler — infinite spin while(!ready){} reads a plain global; the optimizer may cache it in a register and never re-read it → spins forever.
Fix: volatile / atomic. Bites on every platform.
② Hardware — stale a, b On weak memory (ARM, Power) the child can see ready=1 before a=5, b=3 → sum reads stale values.
Fix: a fence / acquire-release. (x86-TSO happens to hide it — a "works on my machine" trap.)
Real lessonIt is correct only under sequential consistency — the poster child for why we need memory-consistency models, atomics & fences, the subject of a later lecture on memory consistency.

Message Passing: The Same Task

Parent sends operands; child returns the result

int a, b, sum;            // parent's variables

void dosum() {            // child: separate address space
  int x, y;               // child's OWN copies
  recvMsg(mainID, &x, &y);
  sendMsg(mainID, x + y); // return the result
}
void main() {
  if (fork() == 0)        // child
    dosum();
  else {                  // parent
    a = 5; b = 3;
    sendMsg(childID, a, b);
    recvMsg(childID, &sum);     // receive result
    waitpid(childID, NULL, 0);  // reap the child
    printf("sum is %d\n", sum);
  }
}
Explicit communication Data crosses only via sendMsg / recvMsg — nothing is shared. The child's x, y are its own copies, not the parent's a, b.
Synchronization — (almost) for free* Send/receive synchronize on their own: the receiver blocks until the message arrives. No separate ready / done flags.
Trade-off Message passing bundles communication and synchronization — simpler reasoning, but you pay to move every byte.

* Not entirely free: whether the sender blocks depends on the send mode (buffered vs. synchronous vs. ready) — the send modes that message-passing libraries like MPI expose.

Inter-Process Communication

The sendMsg / recvMsg above are pseudocode for real OS inter-process communication (IPC) — pick any primitive:

Pipes / FIFOs A pipe() with fork() is the classic case: one end write()s (= send), the other read()s (= recv). read() blocks until data arrives — exactly the "receiver blocks" we relied on. Named pipes (FIFOs) do the same between unrelated processes.
Sockets Unix-domain or network sockets call send() / recv() directly — the names line up. Same host or across machines — which is what scales out to a cluster.
Where MPI fits MPI is the standard library layered on these primitives — adding ranks, datatypes & collectives. The model is OS-level, not necessarily MPI.

Module 2.1 — Review

1. What is a programming model, and which two dominate multiprocessors?

An abstraction the hardware provides to the programmer. The two dominant ones are shared memory and message passing.

2. How does each model communicate and synchronize?

Shared memory: implicit communication through loads/stores, with explicit synchronization. Message passing: explicit communication via send/recv, which automatically synchronizes.

3. Why is the thread/process analogy useful here?

Threads share the address space (≈ shared memory); processes share nothing (≈ message passing). The uniprocessor concepts map directly onto the two models.

The Two Models in Code

By the end you can…

  • Parallelize the same serial loop under both models
  • Identify the primitives shared memory needs: scope, locks, barriers
  • Explain why shared memory is easier to develop but harder to tune

The Serial Baseline

Both worked examples parallelize this sequential code — an elementwise add, then a conditional sum:

Sequential

for (i = 0; i < 8; i++)
    a[i] = b[i] + c[i];

sum = 0;
for (i = 0; i < 8; i++)
    if (a[i] > 0)
        sum = sum + a[i];

print sum;
Plan Split the 8 iterations across 2 workers (4 each). The add loop is embarrassingly parallel; the sum is a reduction — that's where the models differ.

Worked Example: Shared Memory


begin parallel               // spawn child
private int start_iter, end_iter, i;
shared int local_iter = 4;
shared double sum = 0.0, a[], b[], c[];
shared lock_type mylock;

start_iter = getid() * local_iter;
end_iter   = start_iter + local_iter;
for (i = start_iter; i < end_iter; i++)
    a[i] = b[i] + c[i];
barrier;

for (i = start_iter; i < end_iter; i++)
  if (a[i] > 0) {
    lock(mylock);
      sum = sum + a[i];
    unlock(mylock);
  }
barrier;                     // necessary
end parallel                 // kill child
print sum;
Pluses Communicates directly through memory; little code modification vs. the serial version.
Minus Requires privatization of loop indices before the parallel region.
Three primitives appear
  • Scope: private vs. shared
  • Lock: protects the sum reduction
  • Barrier: all threads finish a phase before the next

These three primitives map directly onto OpenMP — the subject of the shared-memory programming lectures.

Worked Example: Message Passing


// parent and child already spawned
id = getpid();
local_iter = 4;
start_iter = id * local_iter;
end_iter   = start_iter + local_iter;

if (id == 0) send_msg(P1, b[4..7], c[4..7]);
else         recv_msg(P0, &b[4..7], &c[4..7]);

for (i = start_iter; i < end_iter; i++)
    a[i] = b[i] + c[i];

local_sum = 0;
for (i = start_iter; i < end_iter; i++)
    if (a[i] > 0) local_sum += a[i];

if (id == 0) {
  recv_msg(P1, &local_sum1);
  sum = local_sum + local_sum1;
  print sum;
} else send_msg(P0, local_sum);
Plus Communication only through messages — no shared state, no locks, no barriers.
Minuses Message send/receive overhead; requires algorithm and program changes (distribute the input, then gather partial sums).
Notice the reshape The reduction becomes an explicit scatter the data → compute local sums → gather the partials dance. Message passing rewrites the algorithm; shared memory mostly annotates it.

Development Effort vs. Tuning Effort

Easier to develop: shared memory
  • Transparent data layout
  • Transparent inter-processor communication
  • Code structure changes little
  • Parallelizing / directive-driven compilers help (e.g. OpenMP)
Harder to tune: shared memory
  • Data layout must be tuned by hand
  • Communication pattern must be tuned
  • Machine topology matters for performance
The catch Shared memory's transparency is also its trap: what's hidden during development — where data lives and how it moves — is exactly what you must expose again to scale.

Module 2.2 — Review

1. What primitives does shared-memory parallel programming require?

Variable scope (shared vs. private) and synchronization primitives — locks and barriers.

2. How does the reduction differ between the two models?

Shared memory: a single shared sum guarded by a lock. Message passing: each worker computes a local sum, then partials are gathered by messages.

3. Why is shared memory easy to develop but hard to tune?

It hides data layout and communication (easy to write), but those same hidden details — layout, communication pattern, topology — must be tuned for scalability.

Beyond the Two Pillars

Many models exist, but most build on shared memory or message passing. We look at four:

PGASPartitioned Global Address Space
Shared address space, but with locality exposed.
Data ParallelOne op, many data
The programming model for SIMD / vector hardware.
MapReduceKey-based, not location-based
Map produces pairs; Reduce aggregates by key.
Plus a fourth Transactional memory raises the abstraction of shared memory: mark a region atomic and let hardware/software handle the rest — no explicit locks.

PGAS: Partitioned Global Address Space

The problem Plain shared memory is too simple for NUMA machines: data layout is hidden, yet thread–data proximity drives performance.
The PGAS idea Keep a global shared address space, but partition it so each thread has an affinity for part of it — the model exposes both shared and private regions.

Languages: UPC, Coarray Fortran, Chapel, Titanium.
Libraries: OpenSHMEM, NVSHMEM (multi-GPU), Global Arrays.

PGAS Example: UPC Matrix Multiply


shared [N*P/THREADS] double A[N][P]; // rows of A
shared [N*P/THREADS] double C[N][M]; // rows of C
shared [M/THREADS]   double B[P][M]; // cols of B

void main(void) {
  ... // matrices initialized
  upc_forall (i=0; i<N; i++; &A[i][0]) {
    for (j=0; j<M; j++) {
      C[i][j] = 0;
      for (l=0; l<P; l++)
        C[i][j] += A[i][l] * B[l][j];
    }
  }
  upc_barrier;
}
Distribution Every node holds N*P/THREADS rows of A and C — the shared [blocksize] declares the layout.
Affinity expression &A[i][0] in upc_forall assigns iteration i to the thread where A[i][0] lives — computation follows the data.

Data-Parallel Model

Data parallel = programming model for SIMD Either a true vector unit, or a scalar unit with lanes.
  • Requires packing data into a wide register
  • Once packed, you compute multiple items at once
One register, packed into lanes of varying width.

Data-Parallel Example: SSE Vector Add

C += pack 4 floats, add in one instruction

; Vector4: four 32-bit floats x,y,z,w
MOVUPS XMM0, [EAX]   ; load A[0..3]
MOVUPS XMM1, [EBX]   ; load B[0..3]
ADDPS  XMM0, XMM1    ; 4 adds at once
MOVUPS [Result], XMM0; store C[0..3]
ADDPS: one instruction, four parallel adds.

MapReduce

Key idea Data is accessed by key rather than by location (like a database). It can be built on shared memory or message passing.
Map Each worker processes its input and emits <key, value> pairs.
Reduce For each key, aggregate all the values produced for it.
Why it caught on The runtime handles distribution, fault tolerance, and the shuffle — the programmer writes only two pure functions. The modern descendants are Hadoop and Spark.

MapReduce Example: Inverted Index

  • Files are distributed over map workers
  • Each map worker emits <LinkX, DocY> when it sees LinkX on DocY
  • A reduce worker aggregates all Docs that contain the same Link
Result An inverted index: link → list of documents. The classic web-search building block.

Transactional Memory

Transaction A code region with the database ACID property: Atomicity, Consistency, Isolation, Durability.
TM keeps two of the four Transactional memory adopts Atomicity and Isolation — enough to let us remove locks and stop worrying about deadlocks.
ACIDIn TM?
AtomicityYes
Consistency—
IsolationYes
Durability—

Durability/consistency are database concerns; in memory we just need the appearance of an all-or-nothing, isolated update.

Locks vs. Transactional Memory

With locks

lock(mylock);
  sum = sum + a[i];
unlock(mylock);
  • Must pick the right lock granularity
  • Risk of deadlock with multiple locks
  • Locking overhead even with no conflict
With transactional memory

atomic {
  sum = sum + a[i];
}
  • HW or SW ensures atomicity & isolation
  • No locks, no locking overhead, no deadlock
  • SW TM: flexible but slow · HW TM: fast but costly
The pitch The programmer states what must be atomic; the system figures out how — higher abstraction, simpler reasoning.

Closing Comments

Many modelsLots of programming models exist in the wild.
Two rootsMost are built on shared memory or message passing.
Always a trade-offMore control buys performance but adds complexity.
The honest truth Whatever model you choose, parallel programs still require a lot of tuning. The abstraction makes the program easier to write — it does not make it easy to make fast.

Module 2.3 — Review

1. What are the two basic parallel programming models?

Shared memory and message passing.

2. Key advantages and disadvantages of shared memory over message passing?

Pluses: implicit communication, lower development effort, finer-grained communication. Minuses: explicit synchronization, higher tuning effort, requires hardware support.

3. How does transactional memory simplify parallel programming?

Higher abstraction (simpler coding and reasoning) and it removes lock-related problems — no explicit locks, no deadlocks.
